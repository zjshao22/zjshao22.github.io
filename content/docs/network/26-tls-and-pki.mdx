# 第二十六节：TLS 与证书——加密还要确认对方

你连上了一个“能把内容加密”的服务。如果中间人把自己的公钥发给你，再分别与真实服务通信，你也可能在两段加密连接之间泄露内容。**加密通道必须同时解决密钥、身份和完整性**，才能支撑 HTTPS 的安全目标。

本节讨论常见的 TLS 1.3 服务器证书认证模式。会话恢复、客户端证书和其他模式有所不同，不能把一张简化握手表当成全部 TLS。

## 一、六种工具不是六个同义词

| 工具       | 基本输入与作用                             | 不能单独保证什么                         |
| ---------- | ------------------------------------------ | ---------------------------------------- |
| 对称加密   | 使用共享秘密密钥保护数据内容               | 对方身份；某些加密模式也不单独保证完整性 |
| 非对称加密 | 使用公钥加密、相应私钥解密的方案           | 收到的公钥确实属于目标服务               |
| 密钥协商   | 双方用各自秘密及交换的公开信息导出共享秘密 | 未认证交换时抵抗中间人                   |
| 密码学哈希 | 把任意长度数据映射为固定长度摘要           | 身份认证；攻击者也能重新算摘要           |
| MAC        | 用共享秘密计算并校验消息认证码             | 对第三方证明究竟是哪一方生成消息         |
| 数字签名   | 用私钥签名，使用公钥验证                   | 消息保密；公钥与真实身份的绑定           |

“文件附带 SHA-256，所以来自老师”是一个失败方案。攻击者若能同时替换文件与无认证的摘要，可以给修改后的文件计算新摘要。若摘要通过可信渠道取得，或清单有可验证的签名，比较摘要才形成更有意义的检查。

数字签名也不宜理解成“把消息用私钥加密”。签名与加密是用途及算法条件不同的密码学构造；某些密钥算法根本不提供加密操作。

现代 TLS 的记录保护使用认证加密（AEAD）等机制，既保护内容，也检测未经许可的修改。对称操作适合持续传输大量数据；公钥工具主要参与认证和建立密钥，而不是把整个网页逐字用公钥加密。

## 二、公开交换怎样产生共同秘密

想象客户端保留一个临时秘密 `a`，服务器保留一个临时秘密 `b`。它们交换分别由秘密生成的公开份额，再各自结合对方份额与自己的秘密，得到相同的共享秘密；被动监听者只获得公开份额，不能轻易求出这个秘密。

TLS 1.3 常用的临时椭圆曲线 Diffie–Hellman 密钥协商遵循这种思路。这里不是要求用小整数实现真实密码学，而是理解**秘密没有直接在网上发送，公开份额也不等于证书公钥**。

但未认证的协商仍会失败：中间人分别与两端建立两个秘密，转发并修改内容。因此还要证明握手里的服务器身份，并把认证绑定到这次握手，而非只展示一张可复制的证书。

## 三、TLS 1.3 的一次完整新握手

下表是教学简化：已经建立 TCP，使用服务器证书、临时密钥协商，没有恢复、0-RTT、客户端证书或重试请求。实际握手消息可以组合在记录中，不能把每一行都当成独立 IP 包。

| 次序 | 方向与消息                                            | 双方取得什么能力                                                |
| ---- | ----------------------------------------------------- | --------------------------------------------------------------- |
| 1    | 客户端发 ClientHello                                  | 提供支持的版本、算法、临时公开份额及扩展信息                    |
| 2    | 服务器发 ServerHello                                  | 选择参数，并提供服务器临时公开份额                              |
| 3    | 双方导出握手阶段密钥                                  | 后续握手内容可被加密；身份验证仍需完成                          |
| 4    | 服务器发加密的扩展、证书、CertificateVerify、Finished | 证书给出身份绑定；签名证明私钥持有并绑定握手；Finished 校验握手 |
| 5    | 客户端验证上述内容，发 Finished                       | 客户端完成相应握手确认                                          |
| 6    | 使用派生的应用流量密钥交换数据                        | HTTP 等应用消息在受保护通道内传输                               |

ClientHello 和 ServerHello 在通常的 TLS 1.3 新握手中仍可见；服务器后续证书等握手消息被加密。握手密钥与应用流量密钥不是简单地“同一个密码一直用到底”。密钥派生依赖协商所得秘密及握手上下文。[TLS 1.3 规范](https://www.rfc-editor.org/rfc/rfc8446.html)

这里没有“服务器用证书公钥解密客户端发来的网页密钥”这一步。那种说法容易把旧式 RSA 密钥传输模型误套到 TLS 1.3。

握手认证失败时，客户端应停止将敏感应用数据送给该连接。为了“先能打开网页”而绕过证书错误，会移除原本用来阻止中间人的检查。

## 四、证书怎样建立信任链

证书把公钥、服务身份、有效时间、用途等信息放在一起，并由签发者签名。客户端通常从服务器证书，经中间 CA，构造到**本地已信任根**的路径。根证书自签名不是它天然可信的原因；信任来自客户端的信任库或明确配置。

现代服务身份验证主要按证书 SAN 中的相应名字类型匹配；不应把证书主体中的 Common Name 当成通用兜底。URL 使用主机名时检查 DNS 身份，使用 IP 字面量时需要相应 IP 身份，不能因为二者指向同一机器就自动互换。[服务身份验证规范](https://www.rfc-editor.org/rfc/rfc9525.html)

| 教学情境                                           | 链是否可信 | 目标名字是否匹配 | 能否仅凭这两项通过身份检查         |
| -------------------------------------------------- | ---------- | ---------------- | ---------------------------------- |
| 可信 CA 签发，有 `notes.study.example`，访问该名字 | 是         | 是               | 仍须继续检查时间、用途等及握手证明 |
| 可信 CA 签发，只有 `other.study.example`           | 是         | 否               | 不能                               |
| 自签名且客户端未显式信任，名字正确                 | 否         | 是               | 不能                               |
| 证书与名字都正确，但对方没有相应私钥               | 是         | 是               | 无法完成握手认证                   |

证书失效、撤销以及检查策略也是验证的一部分；不同客户端的撤销处理与离线行为可能有差异，不应仅凭某个工具输出一行“成功”就概括所有浏览器的策略。[证书路径处理基础](https://www.rfc-editor.org/rfc/rfc5280.html)

## 五、恢复、前向保密与 0-RTT

**会话恢复**可利用先前建立的状态或票据减少新连接的认证开销。它不等于把旧 TCP 连接复活，也不等于所有恢复方式都具有相同的安全属性。

普通临时密钥协商在正确实现、临时秘密及时销毁等条件下提供前向保密：后来泄露证书长期私钥，不应直接使已记录的旧会话明文可恢复。它不保护正在被攻陷的终端，也不消除临时密钥本身泄露的后果。

部分恢复支持 **0-RTT early data**，客户端可更早发送应用数据。但早期数据有重放风险，不能把它当成“与普通握手后数据完全相同，只是更快”。服务器和应用需要共同确定可接受的操作，并实施相应的防重放策略。

例如“取得公开课程封面”与“提交一次扣款”不能使用同一种未经分析的重放容忍策略。请求即使经过加密，也可能被攻击者重放已有密文；保密性没有自动提供业务层的恰好执行一次。

## 六、HTTPS 隐藏了什么，哪些信息仍有边界

连接直接终止于目标服务且验证正确时，路径、查询参数、HTTP 字段和正文在该 TLS 通道内受到保护。但是通信端点仍能读取应用明文；浏览器扩展、服务端日志和被攻陷的终端也是可能的泄露位置。

网络观察者通常仍可看到目标 IP、连接时间、流量大小与方向。普通 ClientHello 中的 SNI 也可能暴露名字；ECH 等机制会改变这一点，但不能假定所有连接已经部署它。DNS 查询是否可见，要看 DNS 的独立传输方式。

HTTPS 不保证页面内容诚实，不替应用检查访问权限，也不能自动防止诈骗网站。可信证书通常证明服务能按规则控制相应名字及持有密钥，不能证明网站业务值得信任。

如果 CDN 或公司代理终止 TLS，就出现新的信任端点。客户端到代理、代理到源站是两段需要分别分析的连接，而不能说“一把锁保证所有中间设备都看不到”。

## 七、观察证书与协商结果

在自己的电脑用浏览器打开 `https://example.org/`，从安全信息中记录访问名字、证书 SAN、签发者、有效时间和协议。记录实际值；公网证书及协商参数会变化，不需要与课堂截图相同。

若已有 curl，可运行：

```bash
curl -Iv --connect-timeout 5 --max-time 15 https://example.org/
```

Windows 使用 `curl.exe`。输出可能包含 TLS 版本、验证信息及 HTTP 协商，也可能受工具编译方式或代理影响。`-I` 请求头部，`-v` 展示诊断；它们没有关闭证书验证。

若已有支持相应参数的 OpenSSL，还可运行以下命令，结果取得后 Ctrl+C 退出：

```bash
openssl s_client -connect example.org:443 -servername example.org -verify_hostname example.org -verify_return_error
```

检查自己的工具是否真的完成路径与主机名验证；系统信任库加载失败时应记录该限制。`-servername` 设置 SNI，不等于 `-verify_hostname` 的主机名验证。不要用忽略验证错误的参数把失败实验改成“安全成功”。

交出“证书字段、握手检查、传输可见信息”三类记录，并注明哪些来自实际观察、哪些是协议模型推断。
