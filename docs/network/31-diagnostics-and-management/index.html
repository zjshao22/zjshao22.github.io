第三十一节：网络诊断与管理

同学说“网络坏了”，管理员立刻重启交换机。页面恢复了一会儿，后来又失败：重启清掉了什么状态？故障是否真正找到？没有证据，这个过程无法回答。

排查要把一句模糊抱怨变成可以检验的假设。管理则持续保存正常与异常的状态，让故障发生时有可比较的记录。

一、先定义失败，建立基线

记录具体目标、时间、范围和成功标准。例如“宿舍 A 在 10:02 打开某 URL，名称解析成功，TCP 连接超时；同一时刻实验室 B 成功”。这比“校园网很慢”多了位置、阶段和对照组。

需要确认示例问题作用
范围一台设备、一网段、一个服务还是所有目标？缩小共同故障部分
时间持续失败、间歇失败还是只有高峰？对照负载与变更
阶段解析、连接、认证、首字节还是下载？找到要检验的机制
对照同机另一目标、另一机器同目标是否正常？控制变量
基线正常 RTT、吞吐、错误计数是多少？判断变化是否异常

不要用“直接访问 HTTPS 的 IP”简单替代域名：证书和虚拟主机也使用名称。应使用保持主机名的解析覆盖方式，例如 curl 的 --resolve，并解释改变了哪一项。

三、ping 和 traceroute 不能证明什么

ping 常用 ICMP Echo 检验可达性和往返时间。成功说明该次探测得到回应，不说明 HTTP 服务可用；失败也可能是过滤或不响应，不一定是 IP 路径全断。

traceroute 利用逐步增大的 TTL/Hop Limit 和中间节点的超时响应推测路径。UDP、ICMP、TCP 探测版本不同；ECMP 可能让不同探测走不同路径；回程也可能与去程不同。星号表示没有在等待期限内得到预期回应，不能直接把该节点叫断点。

构造记录：网关 ping 成功，第三跳无响应，第四跳和目标响应正常。请先判断第三跳是否必然阻止数据通过。

核对探测边界

后续节点已响应，不能据第三跳星号断言它阻止所有数据通过。它可能没有发送预期 ICMP、限速，或回应没有到达。要结合目标应用、重复探测和路径变化判断。

四、一份故障证据怎样推进判断

以下都是构造记录，不是实际学校日志。

检验结果
本机地址192.168.30.10/24，网关 .1
ping 网关有响应
查询服务域名返回 203.0.113.20
TCP 443三次 SYN，无 SYN-ACK
另一个获准测试的客户端同服务连接成功
服务端同时抓包看到本机 SYN，发出 SYN-ACK
本机抓包未看到 SYN-ACK

第一步，SYN 已到服务端，支持该次去程到达。第二步，服务端已发送 SYN-ACK，说明不能只归因于“没有监听”。第三步，本机没看到返回报文，应检查返回路径、过滤规则或中间转换状态，还应核对抓包接口与是否漏抓。

它没有确定唯一原因。 一个更小的下一步检验是：沿返回路径检查路由和防火墙计数，或在有权限的两个相邻观察点对照同一五元组。

提示：为什么先找缺失的返回证据

把握手三个动作分别写出发送者和接收者，再标记“发送已观察”“接收已观察”。停在尚缺证据的那一段，避免重查已经得到支持的假设。

变式：若服务端收到 SYN 后立即发 RST，本机也收到 RST，下一步是否仍优先检查断开的回程？

核对变式

该次 RST 已返回，说明至少这个响应的回程成立。应先检查监听端口、主动拒绝规则及服务状态；RST 也可能由中间设备产生，需要确认来源。它与完全无响应有不同的排查起点。

五、慢在哪里：拆分一次请求的时间

对自己获准访问的 HTTP 服务，可记录以下时间；macOS/Linux 用 curl，PowerShell 可用 curl.exe。

Windows 将 /dev/null 改为 NUL。这些值是从请求开始累计的时刻，不能把它们直接相加。缓存、代理、连接复用、协议版本会影响解释；比较时记录工具输出和运行条件。

构造的一次新建 TCP/TLS 连接输出为 dns=0.020 connect=0.060 tls=0.100 first=0.300 total=0.500，单位秒。DNS 阶段约 20 ms，DNS 后连接额外约 40 ms，连接后 TLS 额外约 40 ms，TLS 后到首字节约 200 ms，首字节后传输约 200 ms。

首字节前的 200 ms 包含请求传送、服务处理和返回等，不能仅据它断言服务器 CPU 用了 200 ms。总耗时也不是单纯的传播时延。

任务：选本机实验服务，连续运行三次，记录是否使用缓存/新连接，解释变化；不得用一次最快结果代表稳定性能。

六、用管理数据看见趋势

SNMP 用管理站查询设备代理暴露的对象；MIB 定义对象和组织方式，OID 标识对象。Get 读取、Set 修改，通知可用 Trap 或 Inform；Inform 有确认。读计数器与修改设备配置是不同权限，学习计数不需要获得写权限。

SNMPv3 提供安全框架，可按配置选择认证和隐私保护；“用了 v3”不自动表示启用了所有保护。流式遥测可按订阅推送状态；流量记录如 IPFIX 汇总通信流，通常不包含完整应用负载。日志记录事件，抓包记录具体报文，它们是互补证据。

构造计数器：一接口在 10:00:00 发出累计 1,000,000,000 字节，10:00:10 累计 1,100,000,000 字节。区间平均速率为：

(100,000,000 × 8) / 10 = 80,000,000 bit/s = 80 Mbit/s。

若接口额定 100 Mbit/s，该口径区间平均约 80%。必须核对计数层次、是否重置/回绕和采样间隔；它不告诉你每毫秒的峰值，也不等于应用 goodput。

迁移：计数器突然变小能否计算负吞吐

不能。先查设备重启、计数器重置与位宽回绕。若不知道原因，这段差值应标为不可直接比较，而不是解释成网络发送了负字节。

七、为什么日志时间也需要协议

不同设备的钟有偏移和漂移，直接按日志时刻排序可能误判先后。NTP 使用交换的时间戳估计往返延迟和时钟偏移。设客户端发送 t1、服务器接收 t2、服务器发送 t3、客户端接收 t4，简化模型中：

  • 往返网络延迟约为 (t4 − t1) − (t3 − t2)。
  • 服务器相对客户端的偏移约为 [(t2 − t1) + (t3 − t4)] / 2。

构造 t1=100 ms、t2=140 ms、t3=150 ms、t4=130 ms，得网络往返 20 ms、偏移 +30 ms。服务器时间比客户端快，所以原始数字不能直接按大小判断真实先后。公式假设路径大致对称；不对称会引入误差。测本机经过的时长应优先用单调时钟，系统日历时钟可能被调整。

八、提交一份可复验的排查记录

选择实验一或实验二的一次失败，记录：目标和时间、正常基线、三个候选原因、每项最小检验、实际证据、排除/保留的假设、一次修复、原场景与正常对照的复验结果。

不要在共享报告中保留账号令牌、密码、私人流量或完整敏感日志。若只完成构造题，标题就写“故障推演”；实际运行报告写清自己的环境和观察点。

协议依据：SNMP 管理框架、NTPv4。
