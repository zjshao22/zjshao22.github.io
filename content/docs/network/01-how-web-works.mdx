# 第一节：网络应用怎样通信

手机上的浏览器与远处的服务器各运行一个程序。浏览器不能直接读取服务器的硬盘，却能向它提出请求并收到数据。**网络的价值，是让不同主机上的程序交换信息。** 先从应用想完成的事出发，再追问网络如何做到。

## 两个程序之间发生了什么

设想你打开一篇在线文章。浏览器发出“我要这篇文章”的请求，服务器读出内容并回送。双方都可以发送数据，也都可以接收数据。许多应用希望得到一种简单的服务：像读写文件一样，在两个程序之间**双向读写字节流**。

“字节流”只表示连续的字节序列，**不保留应用每次写入的边界**。例如程序先写入 HELLO，再写入 WORLD，另一端可能一次读到 HELLOWORLD，也可能分几次读到；应用若要区分两条消息，需要自己约定格式。常用的 TCP 服务会尽力让字节按序、无重复地交付，但连接也可能中断，所以应用仍要处理失败。

### 三种应用，三种组织方式

| 应用情境                | 谁向谁要数据                       | 共同点与差别                                                                      |
| ----------------------- | ---------------------------------- | --------------------------------------------------------------------------------- |
| 浏览网页                | 浏览器向网站服务器请求资源         | 典型的客户端—服务器方式；HTTP 规定请求和响应的含义。                              |
| BitTorrent 文件共享     | 多个对等节点互相请求文件片段       | 一个文件可从多个节点取得；节点之间仍需要传输数据。                                |
| 讲义中的 Skype 通话案例 | 用户端尝试直接通信，也可能借助中继 | 展示了应用如何改变通信拓扑；这是原讲义的历史案例，不能当作今日 Skype 的实现说明。 |

同样是“发送与接收”，应用可以安排成一对一、一对多或多对多。**网络提供通信能力，应用决定谁与谁交流、交流什么。** BitTorrent 的“文件片段”属于应用组织数据的办法，不要与网络层的“IP 数据报”混为一谈。

### 对比：同一个文件怎样交付

假设三名同学都要取得同一份大文件。网站下载的基本画法是：三台电脑分别向同一台服务器提出请求，服务器各发送一份。BitTorrent 的基本画法是：文件先被分成若干片段；同学甲拿到片段 1 后也可能把片段 1 提供给乙，乙再向丙提供自己已有的片段。请在纸上画出两种图，并标出**谁拥有数据、谁正在请求、谁正在发送**。

两张图并不是在比较“哪个一定更快”。速度还受上传带宽、节点数量、连接质量及应用规则影响。它们说明的是：相同的底层通信能力，能支撑不同的**应用组织方式**。

## 读懂一次网页请求

下面是简化的 HTTP/1.1 文本示意。尖括号中的内容代表正文，不是必须逐字输入的协议文本。

```text
浏览器 → 服务器    GET /article HTTP/1.1
服务器 → 浏览器    HTTP/1.1 200 OK
                   <文章内容>
```

GET /article 表示请求一个资源；200 OK 表示服务器成功处理了这次请求。实际请求还包含更多首部。今天多数网站使用 HTTPS，HTTP 内容会经过 TLS 保护；这里展示可读文本，是为了看清**应用层在说什么**。

请注意“请求网页”与“网页已经显示”不是同一瞬间。浏览器取得 HTML 后，还可能根据其中的引用再次请求样式、图片和脚本。一个页面通常对应多次资源请求。HTTP 告诉双方如何表达请求与响应；它本身不负责选择每个数据包经过哪台路由器。

## 用一个新应用检验这个模型

设计一个“多人共同编辑便签”的应用。先不要选协议名称，回答三个问题：

1. 哪些程序需要互相发送数据？只需要一台中心服务器，还是允许设备互相连接？
2. 一个人修改便签后，其他人需要收到什么？怎样区分“一次修改”和连续字节流？
3. 如果连接中断或重复发送一次修改，应用怎样避免内容错乱？

你应该能看出：应用层要定义消息的含义；传输服务能帮它传字节，但不能替它决定“这次修改应该如何合并”。
