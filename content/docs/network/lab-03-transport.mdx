# 实验三：UDP 可靠性与 TCP 消息边界

“收到就确认，没确认就重发”似乎已经可靠。可是 ACK 丢了，接收方会不会把同一份作业收两次？换成 TCP 之后，两次发送是不是就对应两次读取？本实验分别检验这两个问题。

## 一、准备与三类证据

需要 Python 3.9 或以上，不需要第三方包或管理员权限。下载 [UDP 与可靠性实验](/network-labs/transport-lab.py) 和 [TCP 消息实验](/network-labs/tcp-message-lab.py)，保存为同名文件。在所在目录运行命令；Windows 可将 `python3` 换成 `py -3`。

| 模式                        | 是否创建真实套接字 | 能检验什么                                |
| --------------------------- | ------------------ | ----------------------------------------- |
| `transport-lab.py udp`      | 是，仅 `127.0.0.1` | UDP 报文边界、端点与零长度数据报          |
| `transport-lab.py simulate` | 否，虚拟时间模型   | 在给定丢失条件下推演停等、ACK、超时与去重 |
| `tcp-message-lab.py`        | 是，仅 `127.0.0.1` | TCP 读取块与应用消息边界、断流检测        |

不要把 simulate 输出写成抓到的网络报文；也不要根据 localhost 正常收发就推断公网没有丢包。

## 二、先观察 UDP 的报文边界

```bash
python3 transport-lab.py udp
```

程序创建两个真实 UDP 端点，分别发送 3、6、0 字节的数据报，接收方记录来源和实际长度。端口由操作系统分配，每次可能变化。

先预测：最后一份 0 字节数据报表示“连接关闭”吗？UDP 两次发送会不会被接收方当成同一份 9 字节报文？

<details>
<summary>提示：空内容与没有报文是两件事</summary>

UDP 的每份报文有边界。一个有效数据报的负载可以为空；TCP 的 `recv` 返回空字节表示流结束，是另一套语义。

</details>

<details>
<summary>核对预期观察</summary>

在这个正常本机运行中，接收长度应为 3、6、0，回送的长度说明也对应这三项。UDP 保留报文边界，本实验缓冲足够容纳它们。真实网络仍可能丢失、乱序；本实验并未验证这些性质的保证。

</details>

若程序超时，记录错误、系统防火墙和运行限制。不能用模型成功掩盖真实套接字实验未完成。

## 三、先运行朴素重传，再加入重复抑制

下面两次运行都故意抛弃消息 0 的第一次 ACK。数据与 ACK 的单程延时默认分别 20 ms，超时默认 100 ms；时间是模型虚拟时间。

```bash
python3 transport-lab.py simulate --drop-ack 0 --naive
python3 transport-lab.py simulate --drop-ack 0
```

先写出事件预测：消息 0 第一次何时到达？哪个时刻触发超时？重传何时到达？接收方怎样判断该不该再交给应用？

<details>
<summary>提示一：ACK 丢失不意味着数据也丢失</summary>

分别标记“接收方已得到数据”和“发送方已知道接收成功”。这两个状态之间的反馈可能丢失。

</details>

<details>
<summary>提示二：观察两种模式的应用交付表</summary>

查 `DELIVER_DUPLICATE`、`DISCARD_DUPLICATE` 和末尾 `application_deliveries`。网络里收到两次，并不要求应用也收到两次。

</details>

<details>
<summary>核对默认时序</summary>

消息 0 在 0 ms 发出、20 ms 到达并交付；第一次 ACK 被模型丢弃。100 ms 超时触发重发，120 ms 重传到达，140 ms ACK 到发送方。

朴素模式重复交付 0；去重模式记住已接受的编号，丢弃重复交付但仍重新确认。模型用不回绕编号和单一发送者，未实现 TCP 字节流或完整序号空间规则。

</details>

把两次 JSONL 输出保存为文件，比较“数据传输次数”和“应用交付次数”。只看发送端完成不足以证明应用没有重复。

## 四、数据丢失与超时过短

分别运行：

```bash
python3 transport-lab.py simulate --drop-data 1 --drop-ack 0
python3 transport-lab.py simulate --ack-delay 120 --timeout 100
```

第一项同时有一次数据丢失和一次 ACK 丢失。第二项没有故意丢弃报文，但 ACK 往返慢于超时。请独立解释为什么仍会重传，为什么重传出现本身不能证明真实丢包。

<details>
<summary>核对第二项</summary>

数据单程 20 ms，ACK 单程 120 ms，第一次确认共需 140 ms；100 ms 已触发超时。旧 ACK 到达时，发送方若还在等待该编号，可以接受它；后来的重复 ACK 不能推进另一条消息。过短超时带来不必要的重传，这也是实际计时需要估计 RTT 和变化的原因。

</details>

**迁移：**将 `--timeout` 改为 200，先预测第一条消息的重传次数再运行。说明这解决了哪个模型问题，又为什么不能得出“200 ms 是所有网络的最佳值”。

## 五、TCP 可靠传输没有替应用定义消息

运行真实本机 TCP 实验：

```bash
python3 tcp-message-lab.py --chunk 1
python3 tcp-message-lab.py --chunk 7
python3 tcp-message-lab.py --chunk 64
```

发送方构造两条应用消息，每条以四字节网络字节序长度开头，再发送内容；两个 `sendall` 故意在第一条首部中间断开。接收方每次最多读取 chunk 字节，先加入缓冲，再解析完整应用消息。

程序打印本次实际读取块长度与最终消息。chunk 是应用读取的最大块，不是 MSS、网络分段大小或 TCP 窗口。实际读取块可能因调度而变化，不能要求每次完全相同。

| 解码步骤 | 条件                 | 动作                               |
| -------- | -------------------- | ---------------------------------- |
| 等长度   | 缓冲少于 4 字节      | 继续读取，不猜字段                 |
| 读长度   | 至少 4 字节          | 按大端解释，检查上限 4096          |
| 等内容   | 少于 `4 + 长度`      | 留在缓冲等待                       |
| 交付     | 内容已完整           | 交付一条，移去已用字节，再查下一条 |
| EOF      | 读取返回空且仍有半条 | 报告应用消息不完整                 |

多字节 UTF-8 字符可能跨读取块，所以先重建消息字节再解码；直接对每个碎片单独解码可能失败。

<details>
<summary>核对 TCP 实验的结论</summary>

三种读取上限都应恢复“第一份课件”和 `second message`。读取块的数量不等于应用消息数；程序能恢复是因为显式长度协议与缓冲解析，不是 TCP 替它记住了两次发送边界。

</details>

## 六、让应用检测一条不完整消息

```bash
python3 tcp-message-lab.py --chunk 7 --truncate
```

程序故意少发最后一个字节后关闭发送方向。第一条仍完整，第二条只在缓冲中残留，程序应报告不完整消息。

TCP 可以可靠传送已经交给它的字节，却不能凭空补出应用从未发送的那个字节。正常流结束与应用协议完成也要分别判断。

独立改进题：若长度字段声明 1 GB，而你的客户端只有有限内存，应何时拒绝？如果连接在半条消息处关闭，应重试整项操作还是直接报告失败？写清幂等性、重复提交和应用确认的约束，不能一律“自动重试”。
