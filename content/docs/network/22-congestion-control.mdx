# 拥塞控制：让发送速率适应路径

接收服务器还有大量缓冲，学生一起上传作业时却越来越慢。瓶颈可能在共享出口：数据到达速度超过出口发送速度，队列增长，最终丢包。如果发送方只因“确认没到”而更猛烈地重发，额外流量会继续压垮路径。

朴素办法“把接收窗口设大”解决不了这种竞争。**流量控制保护接收方；拥塞控制让发送方适应路径容量与竞争情况**。同一条连接需要同时遵守两个限制。

## 一、两扇门：rwnd 与 cwnd

rwnd 是接收方通告的窗口；cwnd 是发送方根据拥塞控制算法维护的拥塞窗口，它通常不作为 TCP 报头字段直接发送给对方。两者都常以字节表示，但来源与目的不同。

在没有重传恢复等额外复杂状态的简化发送判断中，允许的在途量受 `min(rwnd, cwnd)` 限制。已经发出而尚未确认的 FlightSize 也占用这个预算。

| 给定状态               | 限制在途量 | 已有在途 | 可新发量     |
| ---------------------- | ---------- | -------- | ------------ |
| rwnd=64000，cwnd=12000 | 12000      | 8000     | 4000         |
| rwnd=6000，cwnd=12000  | 6000       | 4000     | 2000         |
| rwnd=0，cwnd=12000     | 0          | 4000     | 不能普通新发 |

第二行受接收能力限制；第一行受拥塞窗口限制。零窗口不会把已经发出的数据抹掉。应用若没有新数据，窗口再大也不会自动产生流量。

## 二、发送方怎样获得路径反馈

发送方不直接知道所有路由器的队列和其他流量。它从确认到达节奏、RTT、丢失与显式拥塞标记等反馈推断状态，调整在途量或发送节奏。

丢失常作为拥塞反馈，但不是每次丢失都由拥塞造成；无线损坏、路由变化也会影响传送。反过来，队列能持续积压而尚未丢包，因此“没有丢包”不能证明延时良好。

## 三、慢启动：名称慢，增长并不慢

先研究经典 Reno 风格机制。为便于算例，**课堂设初始 cwnd=2 MSS、阈值 ssthresh=8 MSS**，每个段大小为一个 MSS，每个段均有及时确认，无丢失，接收窗口足够，应用持续供给数据。这里的初始值是题目条件，不是当代所有 TCP 的默认值。

慢启动阶段，每得到新数据确认，窗口增加；在本题每个段都确认的理想模型下，一轮 RTT 约翻倍。到达阈值后进入拥塞避免，改为每轮约加一个 MSS。

| 轮次开始 | cwnd  | 本轮规则         | 下一轮近似 cwnd |
| -------- | ----- | ---------------- | --------------- |
| 0        | 2 MSS | 慢启动           | 4 MSS           |
| 1        | 4 MSS | 慢启动，达到阈值 | 8 MSS           |
| 2        | 8 MSS | 本题采用拥塞避免 | 9 MSS           |
| 3        | 9 MSS | 拥塞避免         | 10 MSS          |

慢启动的“慢”指相对一开始就把大量数据灌入网络；其早期增长实际上很快。延迟 ACK、应用受限、接收窗口与实现算法会改变精确增长，不能把所有抓包都强行配成 2、4、8。

### 拥塞避免的加性增长

经典模型在每次新确认上增加约 `MSS²/cwnd` 字节；一轮约收到 cwnd/MSS 次确认，因此一轮总增量约为一个 MSS。真实实现可使用累计确认字节等方法，重点是理解从快速探索转向较缓增长的原因。[经典 TCP 拥塞控制规范](https://www.rfc-editor.org/rfc/rfc5681.html)描述了慢启动与拥塞避免。

## 四、三次重复 ACK 为什么提示一个缺口

发送方发出连续数据，接收方反复回同一个累计 Ack，同时报告后续新数据已经到达，可能说明缺口处的段丢了。经典快速重传在满足条件的三次重复 ACK 后重传疑似缺失段，不必一直等 RTO。

这是一种基于反馈的推断，不是数学上证明“这个段永远不会到”。严重乱序也可能造成重复 ACK，现代恢复机制会采用更多信息。重复 ACK 的条件也不等同于随便三个具有相同 Ack 字段的包。

### 一次 Reno 风格快速恢复算例

设 MSS=1000 字节，检测丢失时 FlightSize=12000 字节，rwnd 足够。经典规则令 `ssthresh=max(FlightSize/2, 2×MSS)=6000` 字节。

| 事件                          | ssthresh | cwnd 与动作                                 |
| ----------------------------- | -------- | ------------------------------------------- |
| 收到第 3 次符合条件的重复 ACK | 6000     | 快重传；进入快速恢复，cwnd=6000+3000=9000   |
| 再来 1 次重复 ACK             | 6000     | 窗口按模型再增加 1000，满足条件时可发新数据 |
| 收到完成本轮恢复的新 ACK      | 6000     | 本例退出恢复，cwnd 回到 6000，进入拥塞避免  |

恢复时的临时“膨胀”反映已有数据离开网络的反馈，不是宣布可用带宽突然增加了三倍。多处丢失、SACK 和不同恢复算法会改变过程；本表是明确给定条件下的经典示范。

## 五、超时为何通常比重复 ACK 更严厉

若没有足够的后续段产生反馈，发送方只能等重传超时。经典规则更新阈值并把 cwnd 降到一个 MSS 的丢失窗口，从慢启动重新探索，同时 RTO 按计时算法退避。

假设 FlightSize 仍为 12000 字节，阈值是 6000，超时后 cwnd 为 1000。若后续无丢失，则先逐步增长，再转入拥塞避免。**初始连接窗口与超时后的丢失窗口是不同概念**，不能因为某个系统初始允许多段，就说超时后也一定保留相同窗口。

## 六、队列越大越好吗：缓冲膨胀

出口只有 10 Mbit/s，队列积压 4 MiB 数据，仅把这些数据发出去约需 `4×1048576×8/10000000≈3.36 秒`。刚到队尾的小语音包可能承受很大的排队延时，即使它只有几十字节。

扩大队列能吸收短暂突发，但长期把队列维持在满附近，会让交互变迟缓。吞吐量高与延时低是不同指标，需要同时观察。

**主动队列管理 AQM**尝试在队列完全溢出前，通过丢弃或标记给端点反馈，抑制持续积压；RED、CoDel、PIE 等采用不同信号和算法。它与包调度、不同流的隔离又是不同机制，组合使用需要具体设计。[AQM 建议](https://www.rfc-editor.org/rfc/rfc7567.html)强调控制过度排队与端点反馈。

### ECN：可以不丢掉包就报告拥塞

在双方协商支持且路径具备相应能力时，发送的 IP 包可以标为允许 ECN。路由器发现拥塞可把 ECN 字段标为 CE；接收方将拥塞信息反馈给发送方，发送方按规则响应并降低负载。

经典 TCP ECN 使用 ECE、CWR 等标志进行反馈；更新的反馈扩展可能不同。ECN 是拥塞信息通道，不是“让网络不拥塞”的魔法；发送方仍必须采取行动，也不代表所有丢失都能被标记替代。[经典 ECN 机制](https://www.rfc-editor.org/rfc/rfc3168.html)定义了端点和路由器协作。

## 七、公平共享与不同拥塞算法

经典 AIMD 把加性增加与乘性减少结合。两个同 RTT、类似条件的长期流，如果都每轮增加相近绝对量、拥塞时按相近比例减小，窗口差距有机会缩小。这个模型解释了一种公平性趋势，但现实 RTT 不同、并发连接数不同或算法不同，结果不保证简单均分。

假设两条流的窗口是 20 和 10 MSS。各增加 1 后为 21、11，差仍为 10；若共同按一半下降，则为 10.5、5.5，差缩为 5。这个几何效果不证明任意网络最终一定完全公平。

| 算法思路       | 使用的关键线索                           | 本课需要理解的边界                       |
| -------------- | ---------------------------------------- | ---------------------------------------- |
| Reno 风格 AIMD | ACK、丢失、窗口增长                      | 基础模型便于推演，不代表所有系统默认     |
| CUBIC          | 随距上次拥塞的时间调整三次函数窗口       | 在先前窗口附近较谨慎，随后探索更高窗口   |
| BBR 类模型     | 估计瓶颈交付速率与最小 RTT，结合节奏控制 | 依赖测量和探测，并非“从不丢包”或普遍最优 |

CUBIC 的标准描述见[相应规范](https://www.rfc-editor.org/rfc/rfc9438.html)，BBR 的测量与模型思路可见[作者团队的原始论文介绍](https://research.google/pubs/bbr-congestion-based-congestion-control/)。选择哪种算法会影响延时、吞吐与其他流的竞争；版本、队列管理、无线条件等都要纳入实验，不能只背一个“最好”的名称。

## 八、动手推演一个可核对的窗口轨迹

**分支 A：**发生一次经典快速恢复，题目简化为恢复完成后窗口减半，随后每轮加 1。**分支 B：**发生超时，阈值改为事件前窗口的一半，cwnd 回到 1，再按慢启动与拥塞避免规则推进。本段是轮次模型，不能把它当成完整 RFC 算法代码。

## 九、独立迁移：不要仅凭一个指标下结论

文件下载速率很高，但视频会议延时从 30 ms 上升到 800 ms，丢包率仍低。给出至少两个可检验的假设，以及各自需要的观测。若 rwnd=100000、cwnd=18000、FlightSize=15000，简化规则允许新发多少？若链路从有线切到无线，为什么此前测得的发送节奏可能需要重新适应？
