第一节：从校园生活认识网络应用

早上，你在班级微信群里看到通知；到学校课程平台打开课件；晚上在哔哩哔哩看视频。三个动作都要联网，却不是“手机把整个互联网装进来了”。你的设备运行一个程序，远处的设备也运行程序，双方按约定交换数据。计算机网络首先连接的是运行在设备上的程序。

本节提到的产品只用来说明你能观察到的使用场景，不推断它们未公开的内部实现。下面的“校园课程平台”是一个简化教学模型，便于把每一步说清楚。

一、谁在请求，谁在回应

假设学校的课程平台里有一页“网络基础”。你在宿舍用笔记本打开它：笔记本上的浏览器是客户端，提供页面的计算机运行服务器程序。客户端提出请求，服务器程序处理后返回结果。这里的“服务器”既可能指设备，也可能指设备上的程序；谈通信时，最好说明指的是哪一个。

浏览器不能直接读取远处计算机的硬盘。它只能按双方约定的格式请求资源。服务器可以返回页面，也可以返回“没有这个资源”“暂时无法处理”等结果。能收到错误响应，仍说明双方至少完成了一次应用层交谈。

把“打开页面”拆开，可以得到一条可检查的过程：

  1. 浏览器确定要访问哪个站点、哪个资源。
  2. 它把请求交给本机的网络功能，数据经过若干网络设备。
  3. 服务器程序收到请求并生成响应。
  4. 响应回到浏览器；浏览器解析内容，可能继续请求图片、样式和脚本。

这是一条帮助理解的路径。真实网站可能有缓存、代理和多台服务器；不能把示意图当成某个学校平台的真实网络拓扑。

二、不同应用要交换什么

你看到的动作程序需要表达的内容你会关心的结果
在班级群发送“明天带电脑”谁发给哪个群、消息内容是什么消息有没有成功送出，是否重复显示
在铁路 12306 查询车次出发地、目的地、日期等查询条件返回的信息是否对应这次查询
在课程平台打开课件要哪一门课、哪一份资源页面和配图能否完整出现
在国内视频平台播放课程视频需要哪段视频数据播放是否连续、等待是否过长

这些例子的共同点是发送与接收数据；差别在于应用怎样解释数据、怎样处理失败。比如查询条件和聊天消息都能变成字节，但“查询成功”与“消息发送成功”不是由字节本身决定的。应用必须定义消息格式和处理规则。

三、数据怎样变成“可以传送的东西”

文字、图片、声音在计算机里最终都表示为字节。一个字节是由 8 个二进制位组成的单位。应用把“我要课件”这样的意思编码成字节，网络负责搬运；接收方再按约定解释这些字节。发送方和接收方必须使用兼容的约定，否则即使数据到达，也不一定能正确理解。

许多应用使用传输层提供的双向字节流：两边都可以写入字节，也都可以读取对方送来的字节。“流”强调连续顺序，不自带一句话或一张图片的边界。假如程序先写入“明天”，再写入“带电脑”，另一端可能一次读到“明天带电脑”，也可能分几次读取。应用要靠自己的格式判断一条完整消息在哪里结束。

常见的 TCP 服务为使用它的程序提供可靠、有序的字节流。这里的“可靠”有边界：它会处理一些丢失和乱序情况，但连接仍可能中断，应用仍须面对失败。视频、实时通话等应用对等待和完整性的取舍也可能不同；现在先记住：应用需求不同，不代表底层网络必须为每种应用重新造一套。

HTTP 是应用层协议，规定请求和响应如何表达。GET 表示获取资源；200 表示这次请求成功处理；404 表示被请求的资源未找到。实际请求还会有其他首部。网站通常使用 HTTPS，用 TLS 保护传输内容；示意中写出可读文本，是为了让你看清应用在“说什么”。

一张页面也可能不是一次请求就完成：浏览器收到页面主体后，发现还需要校徽图片和样式文件，就会继续发出请求。因此“页面出现”与“只传了一个包”完全不是一回事。
