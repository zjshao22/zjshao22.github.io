# 第二十八节：网络安全——从威胁到边界

“所有连接都加密”仍不能回答谁能访问数据库、设备被盗怎么办、出口被流量压满怎么办。安全设计首先要说明保护对象、攻击者能力与信任边界，然后选择针对性的机制。

本节只对自己的本机服务、教学记录或明确授权的实验环境进行观察。攻击推演用于识别防护条件，不把校园网络、同学设备或公网服务当成攻击练习对象。

## 一、先写清楚威胁模型

一个教学作业系统的资产包括学生身份、未公开作业、评分结果、服务可用性与日志。威胁模型要回答：谁可能做什么，能接触哪一段，失败的后果是什么？

| 目标       | 可能的攻击者能力                             | 需要保护的边界                         |
| ---------- | -------------------------------------------- | -------------------------------------- |
| 保密性     | 同一链路监听者能观察帧；服务端管理员能读磁盘 | 链路、端到端通道、服务存储分别分析     |
| 完整性     | 可伪造部分消息或修改应用请求                 | 身份认证、传输校验、应用权限与输入处理 |
| 可用性     | 发起大量请求或占满上游带宽                   | 出口、连接状态、应用计算与依赖服务     |
| 追溯与恢复 | 误操作、凭据泄露或节点损坏                   | 日志、时间、备份、密钥轮换和恢复流程   |

“在内网”不是完整威胁模型。内网设备也可能被入侵，访客网络与服务器区也可能有不同信任级别；网段分离应该配合实际访问规则，不能只换一个地址前缀就宣称隔离完成。

朴素方案是在出口放一台防火墙，然后信任所有内部设备。它会在内部凭据泄露、恶意软件横向访问、应用越权或加密流量中的业务攻击面前失效。防护必须分层。

## 二、欺骗攻击利用了什么未经认证的信息

| 情境           | 失败机制                             | 有针对性的改进与边界                              |
| -------------- | ------------------------------------ | ------------------------------------------------- |
| 明文嗅探       | 链路或路径观察者取得内容             | TLS 等保护相应通道；终端明文仍需保护              |
| ARP 欺骗       | 接受未认证的 IP—MAC 映射             | 交换机检查、隔离与准入；端到端认证仍有价值        |
| 伪造 DNS 回答  | 客户端采用错误名字记录               | DNSSEC 验证数据；加密 DNS 保护特定传输段          |
| 源 IP 欺骗     | 包中的源字段未必是真实身份           | 边界源地址检查、协议认证；IP 地址不应代替用户认证 |
| 伪装 DHCP 服务 | 客户端接收错误配置                   | 接入控制、DHCP 防护及可信配置来源                 |
| 合法账号越权   | 服务器只验证“已登录”，未检查资源权限 | 对每个操作检查主体、对象和权限                    |

ARP 的攻击影响通常起于本地链路；DNS 结果的作用范围则不同。攻击者即使改变了路径，正确验证的 TLS 仍可阻止其冒充服务读取应用内容，但攻击者还可能使连接中断。**保密性没有自动保障可用性。**

密码应配合适当的认证存储、强度和多因素策略；私钥、令牌和管理员凭据要有权限、有效期、轮换与撤销。把秘密直接放在公开代码、页面或共享日志中，会绕开许多网络层防护。

## 三、无状态过滤与状态防火墙

无状态过滤可按方向、地址、协议、端口等字段判断每个包。朴素规则“允许所有带 ACK 的 TCP 包，因为它们一定是回包”会失败：字段可以伪造，单个标志不证明本机曾建立连接。

**状态防火墙**跟踪连接及其状态，使已允许连接的合法后续流量按状态规则通过，包括双向数据与必要返回流量。连接键通常包括源/目标地址、源/目标端口与协议，同时还要考虑方向、生命周期和实现的校验规则。[防火墙策略基础](https://csrc.nist.gov/pubs/sp/800/41/r1/final)

以下为**教学策略模型**：按顺序采用第一条匹配规则；已允许连接的双向后续包由当前状态校验；不考虑相关连接、分片和复杂辅助协议。

| 顺序 | 条件                                                            | 动作       |
| ---- | --------------------------------------------------------------- | ---------- |
| 1    | 属于已允许连接的合法后续流量（双向，按当前状态校验）            | 允许       |
| 2    | 管理网 `192.0.2.0/28` 到服务器 `198.51.100.10` 的新 TCP 22 连接 | 允许并跟踪 |
| 3    | 任意来源到该服务器的新 TCP 443 连接                             | 允许并跟踪 |
| 4    | 服务器向外发起的新 TCP 443 连接                                 | 允许并跟踪 |
| 5    | 其他流量                                                        | 拒绝       |

地址使用文档示例段，没有代表真实学校设备。`192.0.2.0/28` 包含 .0–.15；题目中的管理客户端取 .5。

| 教学事件                               | 决策及理由                                      |
| -------------------------------------- | ----------------------------------------------- |
| .5 发起到服务器 22 的连接              | 命中规则 2；建立相应状态                        |
| .50 发起到服务器 22 的连接             | 不属管理前缀，命中规则 5                        |
| 外部客户端发起到服务器 443 的连接      | 命中规则 3                                      |
| 该 HTTPS 连接建成后客户端发送请求      | 依据规则 1 校验后续状态，不再作为新连接匹配     |
| 该 HTTPS 连接的合法响应返回客户端      | 依据规则 1 与相应状态，不需开放所有客户端高端口 |
| 陌生设备伪造一个 ACK，但不存在匹配状态 | 不能仅凭 ACK 命中规则 1                         |

规则顺序有意义：若在最前面放“允许所有来源”，后面的限制可能永远不执行。地址路由的最长前缀匹配，不能直接代替本题的防火墙第一匹配策略；不同设备还可能使用不同策略语法。

NAT 改写地址或端口，与访问控制是不同机制。有些 NAT 行为间接限制未经请求的入站，但不能由“使用私网地址”得出服务安全。应用授权、服务补丁、最小权限和日志仍不可省略。

这张表只用于检验所列 TCP 情境，不能直接当作生产环境完整规则。实际服务还可能需要 DNS、时间同步和必要的 ICMP/ICMPv6 反馈；一概丢弃反馈可能破坏路径 MTU 发现等功能。应把依赖通信逐项写进策略，而不是在故障后临时开放全部端口。

## 四、拒绝服务可能耗尽哪一种资源

攻击或异常负载可能耗尽链路带宽、连接状态、CPU、内存、线程或数据库连接。先找到资源瓶颈，才能判断缓存、限速、扩容或流量清洗是否有意义。[拒绝服务的机制与约束](https://www.rfc-editor.org/rfc/rfc4732.html)

教学容量例：某请求消耗 CPU 5 ms，服务只有一核、其他开销忽略。理论上最多约 `1000 / 5 = 200 次/s`。若合法和异常请求合计 600 次/s，队列增长并不能创造 CPU，等待会增大或请求被丢弃。

连接建立阶段的攻击可能让服务保存大量未完成状态；某些实现可采用 SYN cookie 等方式降低这类状态开销。但它们不把带宽、后续应用成本或所有攻击都变成零。

限速要选择合适的单位和主体：按 IP 限制可能影响共享同一出口的合法学生，也未必阻挡分布式来源。扩容、CDN、上游防护、超时和资源预算需要结合业务；若上游链路已经被占满，本机应用的限速无法收回已经占用的上游带宽。

## 五、VPN 的隧道保护到哪里结束

隧道把一个内部包装进外层包，外层地址使网络可以把它送到隧道端点。**隧道本身不等于加密**：是否认证和加密，要看所用协议与配置。

VPN 可以把远程设备与组织网络连接，或连接两个站点。以教学远程接入为例：电脑的内部包目标为 `10.20.0.8`；加密隧道外层目标为 VPN 网关的公网位置；网关解封装后按内部路由继续发送。

| 位置               | 看到的关键地址与内容                             | 信任边界                              |
| ------------------ | ------------------------------------------------ | ------------------------------------- |
| VPN 前的应用       | 内部目标及应用内容                               | 终端必须可信，应用仍需认证            |
| 隧道传输的中间网络 | 外层端点和流量形态；受保护的内部内容不可直接读取 | 保护取决于正确的隧道加密与认证        |
| VPN 网关           | 解封装后的内部包                                 | 网关是新的可信端点                    |
| 网关到应用服务     | 内部流量按相应路由继续                           | 是否另外使用 TLS 或其他保护需单独判断 |

**全隧道**将按策略选定的绝大部分流量送入 VPN；**分流隧道**只把部分前缀或应用流量送入。路由、DNS 设置与具体客户端行为决定结果，不能仅凭一个 VPN 图标断言每个 DNS 查询或所有 IPv6 流量都经过隧道。

IPsec 在 IP 层定义安全关联、策略与处理。ESP 可按配置提供加密、完整性、认证与防重放等服务；AH 不提供内容加密。传输模式与隧道模式的保护范围和包组织不同；隧道模式用新的外层 IP 首部承载内部包。[IPsec 架构](https://www.rfc-editor.org/rfc/rfc4301.html)、[ESP](https://www.rfc-editor.org/rfc/rfc4303.html)

封装增大包长，所以还需要考虑路径 MTU。VPN “能登录但大文件卡住”可能与路径 MTU 和反馈有关，并不只可能是密码错误。

## 六、本机观察：服务暴露在哪个地址

在一个只放教学文件的临时目录中运行 Python 3 服务：

```bash
python3 -m http.server 8766 --bind 127.0.0.1
```

另开终端，用 `curl -I http://127.0.0.1:8766/`（Windows 可用 `curl.exe`）访问。记录服务实际响应，再检查本机的监听地址。

| 系统               | 可尝试的本机观察命令                                 |
| ------------------ | ---------------------------------------------------- |
| Linux              | `ss -ltn`                                            |
| macOS              | `lsof -nP -iTCP:8766 -sTCP:LISTEN`                   |
| Windows PowerShell | `Get-NetTCPConnection -LocalPort 8766 -State Listen` |

你应依据实际输出判断进程是否监听在 loopback，而不是把一个预期截图当结果。若端口冲突，程序和 URL 一起换空闲端口；完成后 Ctrl+C 关闭服务。

`127.0.0.1` 的监听范围与 `0.0.0.0` 不同；本实验无需改成向所有接口开放。观察到本机连接成功，仅证明这条本机路径可用，不能证明公网可访问、防火墙安全或服务已具备用户认证。

写出四个区别：进程正在运行、端口正在监听、网络路径允许访问、请求通过了应用授权。为每个状态写一种可以支持它的证据。

独立迁移：设计“访客可访问公开网站，只有管理网能管理服务器，数据库只允许应用服务访问”的最小分区与策略。再加入“应用服务被攻陷”这一变化，指出网络控制仍能限制什么、哪些数据与权限已在攻击者可达范围内。

交出资产、攻击者能力、允许流量、拒绝流量、失效情境和可验证证据。安全结论应绑定这些条件，不以“装了防火墙”“开了 VPN”作为最终证明。
