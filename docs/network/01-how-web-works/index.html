从校园生活认识网络应用

用班级群、课程平台和视频播放理解程序怎样交换数据

第一节：从校园生活认识网络应用

早上，你在班级微信群里看到通知；到学校课程平台打开课件；晚上在哔哩哔哩看视频。三个动作都要联网，却不是“手机把整个互联网装进来了”。你的设备运行一个程序，远处的设备也运行程序，双方按约定交换数据。计算机网络首先连接的是运行在设备上的程序。

本节提到的产品只用来说明你能观察到的使用场景，不推断它们未公开的内部实现。下面的“校园课程平台”是一个简化教学模型，便于把每一步说清楚。

一、谁在请求，谁在回应

假设学校的课程平台里有一页“网络基础”。你在宿舍用笔记本打开它：笔记本上的浏览器是客户端，提供页面的计算机运行服务器程序。客户端提出请求，服务器程序处理后返回结果。这里的“服务器”既可能指设备，也可能指设备上的程序；谈通信时，最好说明指的是哪一个。

浏览器不能直接读取远处计算机的硬盘。它只能按双方约定的格式请求资源。服务器可以返回页面，也可以返回“没有这个资源”“暂时无法处理”等结果。能收到错误响应，仍说明双方至少完成了一次应用层交谈。

把“打开页面”拆开，可以得到一条可检查的过程：

  1. 浏览器确定要访问哪个站点、哪个资源。
  2. 它把请求交给本机的网络功能，数据经过若干网络设备。
  3. 服务器程序收到请求并生成响应。
  4. 响应回到浏览器；浏览器解析内容，可能继续请求图片、样式和脚本。

这是一条帮助理解的路径。真实网站可能有缓存、代理和多台服务器；不能把示意图当成某个学校平台的真实网络拓扑。

二、不同应用要交换什么

你看到的动作程序需要表达的内容你会关心的结果
在班级群发送“明天带电脑”谁发给哪个群、消息内容是什么消息有没有成功送出，是否重复显示
在铁路 12306 查询车次出发地、目的地、日期等查询条件返回的信息是否对应这次查询
在课程平台打开课件要哪一门课、哪一份资源页面和配图能否完整出现
在国内视频平台播放课程视频需要哪段视频数据播放是否连续、等待是否过长

这些例子的共同点是发送与接收数据；差别在于应用怎样解释数据、怎样处理失败。比如查询条件和聊天消息都能变成字节，但“查询成功”与“消息发送成功”不是由字节本身决定的。应用必须定义消息格式和处理规则。

三、数据怎样变成“可以传送的东西”

文字、图片、声音在计算机里最终都表示为字节。一个字节是由 8 个二进制位组成的单位。应用把“我要课件”这样的意思编码成字节，网络负责搬运；接收方再按约定解释这些字节。发送方和接收方必须使用兼容的约定，否则即使数据到达，也不一定能正确理解。

许多应用使用传输层提供的双向字节流：两边都可以写入字节，也都可以读取对方送来的字节。“流”强调连续顺序，不自带一句话或一张图片的边界。假如程序先写入“明天”，再写入“带电脑”，另一端可能一次读到“明天带电脑”，也可能分几次读取。应用要靠自己的格式判断一条完整消息在哪里结束。

常见的 TCP 服务为使用它的程序提供可靠、有序的字节流。这里的“可靠”有边界：它会处理一些丢失和乱序情况，但连接仍可能中断，应用仍须面对失败。视频、实时通话等应用对等待和完整性的取舍也可能不同；现在先记住：应用需求不同，不代表底层网络必须为每种应用重新造一套。

四、看懂一个简化的网页对话

假设校园课程平台有一个资源路径为 /courses/network 的页面。以下只是教学用的 HTTP/1.1 示意，不代表任何学校平台真实发出的报文：

HTTP 是应用层协议，规定请求和响应如何表达。GET 表示获取资源；200 表示这次请求成功处理；404 表示被请求的资源未找到。实际请求还会有其他首部。网站通常使用 HTTPS，用 TLS 保护传输内容；示意中写出可读文本，是为了让你看清应用在“说什么”。

一张页面也可能不是一次请求就完成：浏览器收到页面主体后，发现还需要校徽图片和样式文件，就会继续发出请求。因此“页面出现”与“只传了一个包”完全不是一回事。

如果浏览器已经收到 HTTP 404，最该先核对哪一项？

进阶：应用协议怎样规定一次对话

“能把字节送到对方”只是通信的起点。应用协议还须规定消息类型、字段含义、交互次序和错误处理。以教学用的课件服务为例，客户端发出“读取课程 42 的第 3 份课件”，服务端要判断资源是否存在、访问者是否有权读取，再给出结果。把课件编号错写成其他编号，网络仍可能成功送达，但应用得到的是另一份资源或错误响应。

HTTP 请求通常由方法、目标路径、协议版本、首部和可选的正文组成；响应有状态码、首部和可选的正文。方法说明希望对资源做什么，路径定位资源，状态码描述这次请求的处理结果。HTTP 200 只表示本次 HTTP 请求成功处理，不保证浏览器随后请求的所有图片、脚本也成功。HTTP 404 表示当前请求的目标资源未找到；单凭它不能判断是输入路径错误、资源被迁移，还是服务端有意隐藏某些资源。

对教学网址 https://course.example.com:443/courses/network 而言，course.example.com 是主机名，443 是端口，/courses/network 是资源路径。浏览器通常先获取可用于连接的地址，然后通过传输连接与服务端交谈；域名解析、连接建立、请求发送是不同阶段。实际 HTTPS 还要经过 TLS 握手，浏览器也可能复用已有连接，因此一次点击未必对应一次新 DNS 查询和一次新连接。

进阶：字节流为什么需要消息边界

假设你编写一个基于 TCP 的校园签到服务。客户端依次写入两条消息：“签到”和“查询结果”。服务端的一次读取可能得到半条、一条或两条消息的字节。一次写入不对应一次读取；TCP 保证字节流的顺序，不保留应用调用写入时的边界。程序必须自己定义完整消息怎样识别。

先试不添加任何边界信息：收到连续的 ABCDE，发送者可能原本分成 AB + CDE，也可能分成 ABC + DE，接收方能判定吗？在纸上提出一条两端共同遵守的结束位置规则，再读下面的方案。

一种办法是在每条消息前放固定长度的“正文长度”字段。例如长度字段占 2 字节，数值 5 表示后面要继续读取 5 个字节。接收方先读满长度字段，再读满指定长度的正文，才能处理消息。另一种办法是规定分隔符，但还需说明正文出现分隔符时如何转义。真实 HTTP 有自己的报文定界规则；HTTP/2、HTTP/3 的表达形式又不同，这只是用来理解协议设计的例子。

例题：传送成功与业务成功

同学从课程平台下载课件，浏览器收到 HTTP 200 和文件数据，但打开后发现不是要的章节。必须区分三个判断：

  1. 网络传送：本次通信已经把数据送到浏览器。
  2. 协议处理：服务端用 HTTP 200 表示这次请求成功处理。
  3. 业务结果：文件是否符合学习需求，还需检查请求路径、课程编号、内容和版本。

“下载到了文件”不能证明“拿到了正确课件”。需要把请求的资源、收到的内容和自己的目标逐项核对。

观察任务：一张页面用了哪些资源

  1. 打开本课程的一页，在浏览器开发者工具中切到“网络（Network）”面板，再刷新页面。
  2. 找到页面主体和一项图片、样式或脚本资源，各记录请求路径、资源类型、状态码；若面板标注来自缓存，也记下这一点。没有获得记录时，直接使用下面的教学数据。
  3. 写出两条结论：这些记录能证明什么？还不能证明什么？每条结论都指出依据的是哪一行记录。不要公开含账户凭证或个人信息的请求截图。

查看观察任务的判断示例

教学数据有 3 个资源请求，主体和样式返回 200，图片返回 404。“主体已显示”不能证明图片成功，第三行就是反例。图片得到错误响应也不能直接解释为整条网络断开。实际观察若所有记录都成功，可以说明这些记录的结果；若有缓存标记，须注明内容可能来自缓存，不能把它直接当作本次从服务端新传回的内容。

独立迁移题：改为图片已经显示，但记录明确注明“直接使用本地缓存，本次未向服务端发送图片请求”。能否据此证明服务端现在仍可访问？写出理由，并说明还需要哪种证据。

查看迁移题参考答案

不能。显示的是先前保存的图片，没有本次与服务端通信的证据。需要取得本次实际发往服务端的请求结果，再判断这一项通信是否成功；也不能由单个资源成功推断所有服务都正常。

练习与解析

题 1：服务端先读取到 2 字节，随后又读取到 3 字节。客户端是否一定调用了两次写入？

题 2：网页主体返回 HTTP 200，但一张图像请求返回 HTTP 404。能否说“整个页面只有一个请求且全部成功”？

查看两题解析

题 1：不能确定。 这 5 字节可能来自一次写入，也可能来自多次写入；读取返回的分段由缓冲和当时可用数据决定。

题 2：不能。 主体与图像是不同资源，浏览器为图像又发出了请求；两次请求有各自的状态。

自己解释一次熟悉的操作

选“打开课程平台课件”或“在 12306 查询车次”，用四句话写出：哪个程序发起、请求包含什么、哪个程序回应、回应如何被你看到。如果你选的是 12306，只描述用户能观察到的查询与结果，不猜测其内部服务器数量或具体协议实现。
