# 第二十五节：HTTP、缓存与内容分发

前面的课程已经能解释一份数据怎样可靠到达。现在换一个问题：课程首页没有变化，为什么每次刷新还要传同样的一份正文？反过来，成绩页面已经更新，为什么旧内容有时仍会出现？

速度优化不能只靠“把东西存起来”。应用必须定义请求的含义、数据何时可复用，以及怎样判断缓存仍然正确。

## 一、请求与响应是一份应用协议

HTTP 请求包括方法、目标、字段和可能的内容；响应包括状态、字段和可能的内容。URL 中的协议、主机、端口和路径分别帮助选择通信方式、服务位置与资源，不能把路径当成 IP 路由。

| 方法   | 常见语义                          | 对重试的影响                                     |
| ------ | --------------------------------- | ------------------------------------------------ |
| GET    | 取得资源的表示                    | 应是安全方法；重复请求本身不应要求改变资源状态   |
| HEAD   | 取得对应 GET 的字段信息，不传正文 | 可检查元信息，不能从“没有正文”推断资源为空       |
| POST   | 让资源按其定义处理提交的内容      | 默认不能假定重复提交没有额外效果                 |
| PUT    | 按请求内容创建或替换目标状态      | 具有幂等语义；多次同样请求的预期效果应与一次相同 |
| DELETE | 删除目标的相关关联                | 具有幂等语义；第二次的状态码可以和第一次不同     |

**安全**谈请求的预期语义，不代表“没有日志”等任何副作用；**幂等**谈重复请求的预期效果，不保证响应逐字相同。网站把购买操作藏在 GET 中，不能反过来改变 GET 的协议语义，而是应用设计出了问题。[HTTP 语义规范](https://www.rfc-editor.org/rfc/rfc9110.html)

常见状态可分成五类：1xx 为中间信息，2xx 为成功，3xx 为重定向或缓存相关处理，4xx 为请求侧问题，5xx 为服务侧失败。`200`、`201`、`204`、`301/302`、`304`、`400`、`401`、`403`、`404`、`429`、`500`、`503` 不应只背中文名称：要说明请求到达了哪一层、客户端下一步能否重试、是否需要凭据或等待。

例如收到 404，只能说明回应这次请求的服务没有给出所请求的资源；反向代理、CDN 和源站都可能生成它，仍需根据字段和日志确定是哪一环。DNS 失败则通常连 HTTP 响应都还没有得到。

Cookie 可以让浏览器在之后的请求中带回状态标识，服务器再关联登录会话；连接复用与登录状态是两件事。`Secure`、`HttpOnly`、`SameSite` 各有作用，不能把“有 Cookie”视为身份已可信，也不能把一个 TCP 连接等同一个用户。

## 二、连接如何从反复建立变成复用

朴素方案是每下载一个对象就创建一次连接。如果页面包含 HTML、样式、脚本和许多图片，多次建立连接及等待就会增添开销。

| 协议版本 | 主要组织方式                                             | 一个需要保留的边界                                                  |
| -------- | -------------------------------------------------------- | ------------------------------------------------------------------- |
| HTTP/1.1 | 通常使用持久连接，可顺序复用；报文以文本起始行及字段组织 | 不等于所有资源能在一条连接上自由并发                                |
| HTTP/2   | 把消息拆成帧，以流编号在一条 TCP 连接上复用；压缩字段    | TCP 字节流缺失仍可能阻塞多个 HTTP 流                                |
| HTTP/3   | 在 QUIC 上使用多个流；QUIC 通常承载于 UDP                | 某流丢失不必像 TCP 缺口那样阻塞其他流，但共享拥塞和带宽仍会影响它们 |

三个版本保留 HTTP 的请求语义。HTTP/3 使用 UDP，不能推出“浏览器自己不需要可靠传输”；QUIC 实现可靠流、拥塞控制和加密等功能。版本选择取决于客户端、服务、网络和协商条件。[HTTP/2](https://www.rfc-editor.org/rfc/rfc9113.html)、[HTTP/3](https://www.rfc-editor.org/rfc/rfc9114.html)

教学估算：假定每次新连接的额外等待为 100 ms，某组请求必须串行完成，传输正文的总时间为 60 ms。六次单独建立连接需要约 `6 × 100 + 60 = 660 ms`；复用一次连接约为 `100 + 60 = 160 ms`。这只比较给定模型中的建立成本，不是所有真实页面的加载公式；并行连接、TLS、缓存、服务器处理和丢包都可能改变结果。

## 三、缓存首先回答“可否直接复用”

缓存保存的是某个请求对应的**表示及其元信息**。浏览器有私有缓存；代理、CDN 可能有共享缓存。能否保存与能否不联系源站直接使用，是两个判断。

| 字段或指令                  | 解决的问题                        | 常见误读                               |
| --------------------------- | --------------------------------- | -------------------------------------- |
| `Cache-Control: max-age=60` | 允许的 freshness lifetime 为 60 s | 不意味着从每次点击时重新获得 60 s      |
| `Age: 20`                   | 指示缓存响应已经经历的年龄信息    | 不是正文中的业务时间戳                 |
| `no-cache`                  | 复用前通常须验证                  | 不是“绝对不能存储”                     |
| `no-store`                  | 不应存储请求或响应的相应信息      | 不是服务端数据删除命令                 |
| `private`                   | 限制共享缓存存储                  | 不自动加密内容或限制页面截图           |
| `ETag`                      | 表示的验证标识                    | 不是客户端自行计算后就被源站信任的凭据 |
| `Last-Modified`             | 最近修改时间验证信息              | 秒级时间可能不适合所有变更精度         |
| `Vary: Accept-Language`     | 缓存选择还须考虑该请求字段        | 不能只按 URL 混用中英文版本            |

在简化模型中，缓存取得响应时年龄为 20 s，`max-age=60`；又经过 15 s，年龄为 35 s，剩余新鲜时间为 25 s。真正的年龄计算还考虑响应时间等信息，但不能从“我刚打开浏览器”重置已存在响应的年龄。[HTTP 缓存规范](https://www.rfc-editor.org/rfc/rfc9111.html)

## 四、过期后怎样验证，而非必然重传正文

缓存有 `ETag: "course-v1"`，过期后可以发送条件请求 `If-None-Match: "course-v1"`。若资源仍是该版本，服务回复 304，缓存更新相关元信息并复用原来的正文；若已变为 v2，通常回复 200 与新的表示及 ETag。

下面是教学构造，假定网络无额外等待、每个时刻已完成对应请求，且所有响应都允许存储。

| 时刻 | 服务状态         | 缓存行为                           |
| ---- | ---------------- | ---------------------------------- |
| 0 s  | v1，`max-age=30` | 下载 v1 并缓存                     |
| 10 s | v1               | 新鲜命中，不联系服务器             |
| 20 s | 源站变成 v2      | 源站变更不会主动删除所有缓存       |
| 25 s | v2               | 仍可能使用尚新鲜的 v1              |
| 31 s | v2               | 用 v1 的 ETag 验证，收到 200 与 v2 |

因此需要强及时性的个人结果不能随意沿用公开静态资源的缓存策略。常见办法是公开版本化资源使用长缓存，个人响应使用明确的私有与验证策略；具体策略须匹配应用正确性要求。

## 五、代理、CDN 与负载均衡解决不同位置的问题

正向代理代表客户端访问外部服务；反向代理代表后端服务接收请求。CDN 把内容副本部署在多个边缘位置，结合 DNS 或其他调度把用户引向合适节点。节点没有可用副本时可能回源；命中时减少源站工作和远距离传输。

负载均衡把流量分给多台后端。四层负载均衡主要基于连接及地址端口处理；七层负载均衡能按 HTTP 主机、路径等语义选择后端。HTTPS 若在边缘终止，边缘会接触明文，再到源站的一段需单独决定如何保护。

给一个教学例子：源站每秒能处理 100 次下载，客户端产生 600 次/s 请求。若适合共享缓存且边缘命中率为 90%，期望回源约 `600 × 10% = 60 次/s`。若全部是不能共享的个人响应，不能凭同样的命中率估算；CDN 也不会自动把源站的计算能力变成无限大。

后端健康检查可以移除故障节点，但已经发出的请求仍可能失败。需要会话的服务还要考虑共享状态、亲和性和重试；盲目把失败的 POST 再发一遍，可能产生重复提交。

## 六、本机实验：看到 200 与 304 的区别

有 Python 3 的电脑可在临时目录保存下面程序为 `cache_demo.py`。它只监听本机；正文及固定 ETag 是教学实现，省略生产服务器的大量处理。

```python
from http.server import BaseHTTPRequestHandler, HTTPServer

BODY = "课程缓存实验 v1\n".encode("utf-8")
ETAG = '"demo-v1"'

class Handler(BaseHTTPRequestHandler):
    def do_GET(self):
        if self.path != "/":
            self.send_error(404)
            return
        same = self.headers.get("If-None-Match") == ETAG
        self.send_response(304 if same else 200)
        self.send_header("ETag", ETAG)
        self.send_header("Cache-Control", "max-age=5")
        if not same:
            self.send_header("Content-Type", "text/plain; charset=utf-8")
            self.send_header("Content-Length", str(len(BODY)))
        self.end_headers()
        if not same:
            self.wfile.write(BODY)

HTTPServer(("127.0.0.1", 8765), Handler).serve_forever()
```

运行 `python3 cache_demo.py`，另开终端执行：

```bash
curl -i http://127.0.0.1:8765/
curl -i -H 'If-None-Match: "demo-v1"' http://127.0.0.1:8765/
```

Windows 可使用 `curl.exe`，避免某些 PowerShell 环境中同名别名的差异。记录两次状态、ETag、正文长度和服务端日志；停止服务使用 Ctrl+C。若 8765 已被使用，给程序和 URL 换同一个空闲端口。

第二次显式设置条件字段，所以这个实验检验的是**服务器验证分支**；curl 本身没有因此自动实现浏览器缓存。再用浏览器开发者工具观察本机页面的普通刷新与后续访问，记录真实的网络请求、缓存标识和工具设置；强制刷新、禁用缓存会影响结果，不能事先编造一定出现几次 304。
