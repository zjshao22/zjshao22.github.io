从一个网页理解计算机网络

两小时入门：分组交换、分层、DNS、IP、TCP/UDP 与 HTTP

第一课：从一个网页理解计算机网络

情境：你在浏览器输入 https://media.example/intro，按下回车。几秒后页面出现。浏览器怎么知道该找谁？信息又是怎样穿过不同网络到达你的？

media.example 是专门用于教学示例的虚构域名。本课不要求它真的能打开。我们只用它建立一个可解释、可检查的过程模型。

本课目标与路线

学完后，你应该能：

  1. 区分主机、链路、路由器在一次通信中的任务，并说明为什么数据会被分成包。
  2. 用应用、传输、网络、链路四层模型解释“谁负责什么”，不把 DNS、IP 地址、端口和 URL 混成一个概念。
  3. 在简化的首次网页访问情境中，说出名称解析、转发、传输、HTTP 请求与页面呈现的大致先后关系。
  4. 面对“找不到地址”“连接失败”“返回 404”等现象，指出最可能先检查的阶段，并说明证据。

前置知识：会使用浏览器、知道文件与网址的基本概念即可；不要求学过编程。今天重点是建立模型，不背协议字段或 OSI 七层名称。

0–10 分钟｜先画一张“猜测图”

个人 3 分钟：在纸上写出“我的电脑”和“网页所在的服务器”，画出它们之间可能经过的设备。你可以写上 Wi-Fi、路由器、域名、运营商等词，不确定的地方画一个 ?。

两人 4 分钟：互相解释自己的箭头。哪一个箭头表示“找地址”？哪一个表示“传数据”？如果你们画法不同，先保留差异。

全班 3 分钟：收集两个最常见的疑问。本课结尾再回到这张图，检查哪些地方需要修改。

此时无需猜对所有细节。我们要记录的是：你当前用什么模型解释网页出现。

10–25 分钟｜网络不只是一根线

计算机网络是让多个设备依照约定交换信息的系统。这里有三类角色：

  • 主机：发起或接收通信的设备，例如你的笔记本、提供网页的服务器。
  • 链路：相邻设备之间传输数据的连接，可以是 Wi-Fi、网线、光纤等。
  • 路由器：连接不同网络，依据目标地址和转发表，把数据交给合适的下一跳。
你的电脑
创建要发送的数据
本地网络
把数据送到下一台设备
若干路由器
逐跳转发
服务器
接收请求并回应

这条线是示意路径，不是“互联网永远只有这些设备”。真实访问可能经过更多网络、代理或缓存节点；来回路径也不一定完全相同。你家里的无线路由器可能同时承担接入与路由等功能，模型先把任务分开看。

为什么要分成包？

网络不会为了每一个网页长期占用一条端到端的专用线路。发送方通常把要传的信息分成适合传输的单位，每份附上控制信息；不同用户的包可以共享链路，设备按规则逐个处理。我们把这种思路称为分组交换。

想象三个人要共用一条走廊传递很多页资料：如果一个人占住走廊直到全部送完，其他人只能等。按页分批递送，走廊便可交替服务不同任务。不过，分批不保证零等待，也不保证每份都到达；排队、丢失和重传会影响速度。

两人活动，5 分钟：一人扮发送方，一人扮路由器。把一条长句写在三张纸上，给每张标序号。先按 1、3、2 的顺序递过去，再讨论：路由器是否必须理解整句？接收者要恢复原顺序，需要哪类额外信息？

一个路由器把数据包转给下一跳时，最直接需要看的是哪类信息？

25–45 分钟｜用分层模型分清职责

当每个设备都要处理各种应用时，如果所有细节混在一起，协议很难设计和排错。分层是把不同职责放在不同位置：上层使用下层提供的服务，下层无需理解上层的全部含义。今天采用便于入门的四层视图：

层次今天关心的任务例子
应用说清楚要什么资源、得到什么结果HTTP 请求与响应；DNS 名称查询
传输把通信交给目标主机上的合适服务；按需要提供可靠传输TCP、UDP、端口
网络让数据跨网络朝目标主机前进IP 地址、路由器转发
链路在相邻设备之间传输Wi-Fi、以太网

这是一张任务地图，不是说真实网络每一步都只运行一种协议。DNS 是应用层协议，它的查询消息也要借助下层传输。链路层在每一跳可能改变；目标 IP 地址所描述的端到端目标通常保持其意义。

一份请求怎样“套上外衣”？

浏览器先形成“我要 /intro”这样的应用请求。传输层给通信加上端口等信息；网络层加上供转发使用的地址；链路层在当前一跳传送。到达目标设备后，接收方按相反方向处理。这个逐层附加控制信息的过程称为封装。

把四个问题放在不同层次
要哪个页面？应用层的资源请求
交给哪个程序？传输层的端口
送到哪台主机？网络层的地址
这一跳怎么传？链路层的连接

小组任务，6 分钟：把下面四张任务卡放入上表的层次，并写出理由：①“查询域名记录”；②“决定下一个路由器”；③“在当前 Wi-Fi 链路上传一帧”；④“把收到的数据交给监听某端口的程序”。和相邻小组交换，其中有争议的卡片先说任务边界，不只报层名。

45–65 分钟｜网址、域名、IP 地址和端口

把示例地址拆开：

URL 是资源的位置写法。人容易记住域名，网络转发却主要依靠 IP 地址。浏览器通常先查本地可用结果；需要时再通过 DNS 解析主机名，取得可用的地址记录。解析器也可能从缓存回答，因此“每次打开页面都向远端 DNS 服务器查询”并不准确。

IP 地址指向网络中的目标接口或节点位置。它不是人的用户名，也不等于网页路径。一个域名可能得到不止一个地址；大型网站也可能根据用户位置和服务状态给出不同结果。端口则帮助目标主机把到达的通信交给正确的服务。HTTP 的网页内容由应用处理，路由器通常只负责把包往目标方向送。

DNS 查询得到可用地址后，后续跨网络转发主要依据什么？

75–95 分钟｜传输：TCP、UDP 与“可靠”的含义

IP 尽力把数据包朝目标送去，却不承诺每个包都成功、按顺序抵达。应用需要不同的传输服务：

协议给应用的基本服务不应误解为
TCP面向连接、可靠且按序的字节流；用确认与重传等机制处理丢失“永远不会断开”或“零延迟”
UDP较小的传输层机制，保留报文边界；自身不保证交付、去重或顺序“任何用 UDP 的应用都不可靠”

端口号在这里出现：同一台主机可以同时提供不同服务，传输层借助端口区分通信端点。浏览器访问 HTTPS 服务时，经常连接到目标的 443 端口，但真实服务也可以配置其他端口。

如果一条消息被拆成三份，1、3、2 先后到达，使用 TCP 的应用看到的是按序的字节流；若第 2 份一直没来，交付后续数据可能要等恢复。这能保护需要完整内容的传输，也会带来等待。UDP 自身不做同样的可靠有序交付；应用可以按需要在其上增加自己的机制。

重要例外：HTTP/3 使用基于 UDP 的 QUIC。QUIC 自己提供可靠传输、拥塞控制与加密。因此不能把“UDP 不保证交付”推成“HTTP/3 的网页内容不可靠”。今天的逐步演示选择较容易观察的基于 TCP 的 HTTPS，不是所有网页访问的唯一实现。

两人选择题，6 分钟：场景甲是下载一份必须逐字正确的文档；场景乙是每隔几十毫秒发送一次实时位置，过期的旧位置未必还要显示。分别写下你希望传输服务具备什么性质，再讨论一种权衡。不要只写“TCP”或“UDP”三个字母。

简化模型：首次访问、无可用缓存、基于 TCP 的 HTTPS

HTTP 与 HTTPS 在哪里？

HTTP 是应用层的请求—响应规则：浏览器请求资源，服务器返回状态码、元数据和内容。例如，GET /intro 表示获取一个资源；200 表示请求成功，404 表示目标资源未找到。收到 404 说明已经得到了 HTTP 响应，不能把它等同于 DNS 解析失败。

HTTPS 使用 TLS 保护通信内容并验证服务器身份等；它不是“网页的所有信息对所有旁观者都不可见”。例如，通信目标、流量大小和时序等元数据仍可能暴露。今天只认识其位置与作用，加密原理留待后续课程。

观察活动，5 分钟：在你已经打开的真实网页上打开浏览器开发者工具的“网络 / Network”面板，刷新页面，找到一条“文档 / Document”请求。记录它的主机名、状态码，再找一条 CSS 或图片请求。若设备无法使用开发者工具，可在上方演示中记录“请求资源”和“呈现页面”两个阶段，说明为什么页面通常不止一次请求。

观察结果会受浏览器、缓存、代理和协议版本影响。请报告你看到的内容，不要把示例中的 200、404 或 TCP 当成实际抓到的值。

110–120 分钟｜用新情境检验模型

现在换一个未演示过的地址：https://notes.example/chapter1。这仍是虚构域名，只用于推理。

个人 5 分钟，不看同伴答案：

  1. 画出至少四个阶段，标出“名称”“地址”“目标服务”“资源路径”分别在哪一步发挥作用。
  2. 情境 A：浏览器报告无法解析 notes.example。你认为请求是否已经得到该站点的 HTTP 404 响应？写出理由。
  3. 情境 B：浏览器收到了该站点的 HTTP 404。指出至少两项已经成功进行的事情，以及接下来应检查什么。
  4. 情境 C：同一站点首页能打开，但 /chapter1 一直无法打开。你会先比较哪些可观察信息？写一个能区分两种可能原因的检查办法。

同伴互查 3 分钟：互相追问“你从哪个现象推断这一阶段已经发生”，把只有术语、没有证据的句子补完整。

出口条 2 分钟：回看开头的猜测图，圈出一个你现在会改的箭头，再写下仍不确定的一件事。下一课将从这些疑问进入更具体的网络结构与性能。
