UDP 与套接字：把数据交给应用

校园电脑同时打开课程网页、进行语音通话、接收实验程序的数据。IP 能把数据报送到这台电脑，却没有说明应交给其中哪个应用。把所有到达的数据都交给浏览器，显然无法同时支持这些任务。

这一页解决两个问题：操作系统怎样区分应用端点；应用得到的是一条消息，还是一串字节。我们先用 UDP 实际观察端点与消息，再研究怎样补上可靠性。

一、一个 IP 地址为何还不够

一个应用可以创建多个 socket；多个客户端也可以同时访问同一台服务器。同一个进程不一定只有一个端口，一个端口也不能脱离协议与本地地址单独解释。

socket 是应用使用网络服务的接口及其相关状态。在常见 Internet socket 中，地址族选择 IPv4 或 IPv6，socket 类型选择数据报或字节流，绑定地址与端口指定本地接收端点。它不是网线上的另一层报头。

这五项通常称为五元组。同样的 IP 和端口在 TCP 与 UDP 中属于不同协议空间。单向数据流有方向；反向回复会交换源、目的地址与端口。

服务器端口与客户端端口

服务器通常先绑定一个约定端口，客户端才能找到服务。客户端可以让操作系统分配临时端口，因此两个客户端能用不同源端口访问同一服务器端口。

端口号只是约定入口，并不证明运行的是哪种软件。看到 TCP 443 不足以证明业务内容安全；看到 UDP 443 也不能直接说“这是普通 HTTP”。必须结合协议、握手与应用证据。

二、UDP 加了什么，没有保证什么

UDP 报头固定为 8 字节，四个字段各占 16 位。数据来自应用，封装后成为 IP 的负载。

UDP 报头的四个字段
16 bit源端口
16 bit目的端口
16 bit长度
16 bit校验和

UDP 长度包含报头和负载。应用发送 12 字节，UDP 长度便是 20 字节；这不是链路帧的总长度。UDP 协议本身没有建立连接的握手，也没有给数据报增加自动重传、顺序恢复或重复消除。UDP 的基本定义明确区分了消息传递与可靠传递。

朴素想法是：“没有握手，所以 UDP 一定更快。”问题在于，如果应用需要完整文件，它仍要自行解决丢失、重复、排序和发送速率。省下某种机制并不等于完成相同任务所需的总时间必然更短。

有校验和为何仍会丢数据

校验和帮助接收方检测传输中的某些损坏，不负责让损坏或丢失的数据重新出现。检测到错误可以丢弃数据报；路径队列溢出、应用接收缓冲不足等也可能造成丢失。

计算范围包括 UDP 报头、数据，以及含 IP 地址等信息的伪报头。伪报头用于计算，不是在 UDP 数据前额外发送的一段新报头。IPv4 的 UDP 允许用零表示未使用校验和；IPv6 的 UDP 通常要求校验和，特定隧道例外另有严格规则。实际应用应按对应规范使用，不能把“可选”当成“应关闭”。UDP 使用指南讨论了这些限制。

反码加法的一个小算例

这里只练习运算，不是完整 UDP 数据报的校验和。两个 16 位字为 0x1234 与 0xF234：普通相加得到 0x10468，把超过 16 位的进位加回低位，得到 0x0469，逐位取反得到 0xFB96。

接收方把原来的两个字与校验字一起按同样方法相加，结果为 0xFFFF。这种检查仍可能漏掉特定组合的变化，也不是密码学认证；攻击者可以改写数据并重新计算校验和。

三、消息边界：两次发送怎样被接收

假设应用分别发送 abc 和 123456。UDP 保留这两个数据报的边界；在足够大的接收缓冲下，接收调用分别得到一条 3 字节消息和一条 6 字节消息，不能凭空合并成一条 9 字节 UDP 数据报。

但是，“保留边界”不意味着“完整消息永远都在”。如果接收调用给的缓冲区小于数据报，常见 socket 行为是截断或报告长度错误，剩余部分不会成为下一次接收的第二半条消息。具体错误和截断标志随 API、操作系统而异。

六、报文多大才合适

“一次发送整个文件”会遇到长度上限和路径 MTU。在 IPv4 报头 20 字节、无选项、路径 MTU 1500 字节的假设下，避免 IP 分片的 UDP 应用负载最多为 1500 − 20 − 8 = 1472 字节。隧道、IPv6、选项或更小 MTU 会改变这个值。

IP 分片并没有把大数据报变成多条可独立交付的 UDP 消息；目的端须先完成 IP 重组，才能向 UDP 交付整个数据报。少一个分片可能损失整条 UDP 消息，因此通常应避免依赖分片。

UDP 也不是“可以无限发”。面向共享网络的应用需要适当的拥塞响应、速率管理和消息大小选择；这些责任可能由应用上层协议承担。UDP 使用指南将拥塞控制列为关键要求。
