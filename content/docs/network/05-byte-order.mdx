# 第五节：协议字段为什么要约定字节序

前一节把请求装进了 TCP 段、IP 数据报和链路帧。它们的首部不只是“写着一些信息”——每个字段占多少位、放在什么位置、如何把多个字节解释成一个数，通信两端都必须同意。否则包虽然到达，接收方仍可能读错。

## 一、字节与多字节数值

一个**位**只能是 0 或 1；8 位组成一个**字节**。一个字节可表示 0～255。协议里常用两个或四个字节保存更大的数字。十六进制常用前缀 0x 表示：一个字节可写成两位十六进制数，例如 0x04。

假设某个协议字段占两个字节，数值为十进制 1024。1024 = 4 × 256 + 0，因此写成十六进制是 **0x0400**，需要两个字节：0x04 和 0x00。关键问题来了：这两个字节按什么顺序放进消息？

<ByteOrderFigure />

**大端**把高位字节放在前面：0x04、0x00；**小端**把低位字节放在前面：0x00、0x04。它们代表的数可以相同，但字节排列不同。如果一端按大端发送，另一端却按小端解释，1024 就可能被读成 4。这个错误来自格式约定不一致，不是网络把某个字节“弄坏了”。

## 二、什么是网络字节序

不同设备的处理器内部怎样安排多字节数值，可能不同。联网时不能让接收方猜发送方的内部表示。许多互联网协议规定：多字节整数字段按**网络字节序**编码，也就是大端顺序。发送程序把自己的数值转成协议规定的字节排列；接收程序按同一规定还原。

例如 TCP 端口是一个 16 位字段。端口 443 写成十六进制是 0x01BB，因此按网络字节序会依次放入 0x01、0xBB。这里讲的是**字段如何编码**，不意味着用户要在浏览器里手写这些字节；浏览器和操作系统会处理这些细节。

| 要表达的数      | 高位字节 | 低位字节 | 网络字节序中的排列 |
| --------------- | -------- | -------- | ------------------ |
| 1024，即 0x0400 | 0x04     | 0x00     | 0x04、0x00         |
| 443，即 0x01BB  | 0x01     | 0xBB     | 0x01、0xBB         |

## 三、为什么协议还要规定字段位置

仅约定字节序还不够。接收方必须知道“前几个字节属于什么字段，后面哪些字节是负载”。一份网络消息就像一张结构固定的表单：如果发送方把“目标端口”写在接收方认为是“来源端口”的位置，双方仍无法正确沟通。协议格式同时规定**字段顺序、长度、含义和编码方式**。

校园网络里的笔记本、路由器与课程平台设备未必使用相同硬件。共同的格式让它们能解释同一份数据报。这也是网络协议能够跨设备厂商运行的一个基础。

## 四、亲手编码和解码 16 位、32 位字段

对一个无符号 16 位整数 n，按网络字节序发送时，前一个字节是 n 除以 256 后的整数部分，后一个字节是 n 除以 256 的余数。例如 443 = 1 × 256 + 187，而 187 的十六进制写法是 0xBB，于是得到 **0x01、0xBB**。反过来，收到字节 0x01、0xBB，按大端解释就是 1 × 256 + 187 = 443。

对 32 位整数 0x12345678，四个字节依次是 **0x12、0x34、0x56、0x78**。如果收到这四个字节，要计算整数，可以写成 0x12 × 256³ + 0x34 × 256² + 0x56 × 256 + 0x78。这个方法无须猜测本机处理器内部是大端还是小端。

| 字段宽度 | 数值       | 网络上的字节顺序       |
| -------- | ---------- | ---------------------- |
| 16 位    | 0x1234     | 0x12、0x34             |
| 16 位    | 0x01BB     | 0x01、0xBB             |
| 32 位    | 0x12345678 | 0x12、0x34、0x56、0x78 |

## 五、读协议时还要区分“位序”和“字节序”

字节序只解决**多字节整数在消息中的排列**，不自动解决字段宽度、符号、单位、位标志的定义。例如同样的两个字节 0x01、0xBB，若协议规定该字段是无符号 16 位大端整数，它是 443；若协议规定它是两个独立的 8 位字段，就不能把两者拼成一个端口。解析报文必须先知道协议布局，再按指定规则解释。

另一个常见陷阱是把十六进制字符串与实际字节混淆。屏幕上显示的文字“0x01BB”包含可见字符；协议首部里的端口 443 通常是两个二进制字节 0x01 和 0xBB。若把字符“4”“4”“3”直接发出去，收到的将是三个文本字符的编码，而不是 16 位整数 443。

在 C 的套接字编程中，常用 htons、htonl 以及对应的 ntohs、ntohl 处理主机表示与网络表示。这里的 s 和 l 指 16 位与 32 位整数接口，**不是要求先判断机器是哪种端序再手动倒转字节**。更高层的网络库一般已经代为处理；写协议解析器时仍要核对每个字段的宽度与顺序。

### 练习与解析

**题 1：**收到两个字节 0x12、0x34，协议说明它是网络字节序的无符号 16 位字段。十进制值是多少？

## 六、动手推演：按布局拆出一份消息

以下是一个**教学协议**，不是 TCP 首部。字节位置从 0 开始计数；所有整数字段均为无符号数。消息恰好由下面 10 个字节组成，每个两位十六进制数表示一个实际字节：

`02 00 03 00 00 01 02 41 42 43`

| 字节位置 | 字段     | 约定                                   |
| -------- | -------- | -------------------------------------- |
| 0        | 版本号   | 一个字节                               |
| 1～2     | 负载长度 | 两字节大端整数，单位为字节，只计算负载 |
| 3～6     | 消息编号 | 四字节大端整数                         |
| 7 起     | 负载     | 字节数由负载长度指定                   |

在纸上完成三个步骤：按位置给这 10 个字节划分字段；把版本号、负载长度和消息编号换成十进制；检查声明的负载长度是否等于实际剩余字节数。**交出一张字段表**，列出每个字段的位置、原始字节和解释结果。验证时用“首部长度 + 负载长度 = 消息总字节数”，再把编号拆回四个字节核对。

<details>
<summary>卡在拆字段时：先看位置</summary>

给每个字节依次标上 0～9。先圈出位置 0，再圈 1～2 和 3～6；不要因为相邻字节同为 00，就把它们都当成一个字段。

</details>

<details>
<summary>已经拆开但不会求值：再看位权</summary>

两字节大端数是“前字节 × 256 + 后字节”；四字节则从左到右使用 256³、256²、256、1 的位权。先求字段数值，再检查剩余字节是否够作负载。

</details>

<details>
<summary>完成后核对字段表</summary>

| 字段     | 位置 | 字节        | 结果              |
| -------- | ---- | ----------- | ----------------- |
| 版本号   | 0    | 02          | 2                 |
| 负载长度 | 1～2 | 00 03       | 3 字节            |
| 消息编号 | 3～6 | 00 00 01 02 | 1 × 256 + 2 = 258 |
| 负载     | 7～9 | 41 42 43    | 三个原始字节      |

首部有 1 + 2 + 4 = 7 字节，7 + 3 = 10，长度一致。258 = 0 × 256³ + 0 × 256² + 1 × 256 + 2，拆回得到 `00 00 01 02`。负载按这里给出的协议保持为原始字节，不需要猜它代表什么文字。

</details>

### 换一个条件：只有长度字段改变端序

新格式把**负载长度改为小端**，消息编号仍为大端，字段位置不变。收到完整消息 `02 03 00 00 00 01 02 41 42 43`。它声明多少字节的负载，消息编号是多少，长度是否一致？如果仍按旧格式读取长度，会出现什么结果？先写出计算和长度检查，再打开解析。

<details>
<summary>查看迁移题解析</summary>

小端长度 `03 00` 表示 3 + 0 × 256 = 3，编号仍由 `00 00 01 02` 得到 258。首部仍为 7 字节，总长 7 + 3 = 10，符合收到的完整消息。

旧格式会把 `03 00` 读成 3 × 256 + 0 = 768，期望总长 7 + 768 = 775 字节，与题设完整消息的 10 字节不一致。修改一个字段的编码规则，不意味着其他多字节字段也一起倒序；解析器必须逐字段遵守布局。

</details>
