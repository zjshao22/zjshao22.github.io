关系模型、数据表与基本操作

在关系数据库中，一切数据都以二维关系表（Table）的形式组织。表中的每一行称为一条元组（Tuple / 记录），代表现实世界中的一个具体对象或一次关联；每一列称为一个属性（Attribute / 字段），具有固定的数据类型与约束。

本节我们将深入剖析教学选课系统的四表结构，掌握 DDL 建表与完整性约束语法，理解并导入基准数据 p1data.sql，并完成带安全条件的增删改操作。

一、核心概念：实体表与联系表

在校园选课场景中，我们定义了四张核心业务表：

1. 为什么不能把成绩直接放在学生表或课程表？

  • 如果放在学生表：一名学生会选多门课，难道要在学生表中预留 score1, score2, score3... 吗？这不仅限制了选课门数，更破坏了第 1 范式的原子性与结构稳定性。
  • 如果放在课程表：一门课程有几十名学生选修，同样无法用单行记录容纳不同学生的成绩。
  • 正解：“选课”是学生实体与课程实体之间的多对多联系（M:N）。“成绩（score）”既不属于单纯的学生，也不属于单纯的课程，而是学生在某门特定课程上的评价属性。因此必须设立独立的**联系表（t_student_course）**来承载这一关联。

2. 为什么选课表需要联合主键（Composite Primary Key）？

  • 一名学生可以选多门课程（sid 重复出现）；一门课程可以被多名学生选修（cid 重复出现）。因此单独的 sid 或 cid 均不能唯一标识一行选课记录。
  • 业务规则：在同一个学期内，一名学生不能重复选修同一门课程多次。因此，sid 与 cid 的组合（sid, cid）才能唯一确定一条选课记录。这就是联合主键（复合主键）。

二、三类完整性约束（Integrity Constraints）

关系模型的核心优势在于通过 DBMS 严格保障数据完整性，主要分为三类：

  1. 实体完整性（Entity Integrity）：
    • 规定每个表的主键列不能取空值（NOT NULL），且必须唯一。它保证了关系中的每个元组都是可唯一寻址和区分的。
  2. 参照完整性（Referential Integrity）：
    • 如果表 A 中的字段引用了表 B 的主键，则表 A 中的该字段称为外键（Foreign Key）。
    • 外键的值必须要么是被参照表主键中已存在的实际值，要么取空值（NULL）（若业务允许未分配）。
    • 例如：t_student_course.cid 不能随意填入一个不存在的课程号 c999；同时，如果某门课程已被选修，直接在父表 t_course 中删除该课程将触发参照完整性报错（Cannot delete or update a parent row）。
  3. 用户定义完整性（User-defined Integrity）：
    • 针对具体业务领域的约束。例如年龄 age >= 0、成绩 score BETWEEN 0 AND 100（CHECK 约束）、字段非空（NOT NULL）、默认值（DEFAULT）等。

[!TIP] 外键级联选项解析

  • ON DELETE RESTRICT（或 NO ACTION）：当尝试删除父表行时，如果子表有引用则拒绝删除（保护课程不被误删）。
  • ON DELETE CASCADE：当父表行被删除时，子表中所有引用它的行自动跟随删除（例如学生退学注销学号，其历史选课记录一并清除）。
  • ON UPDATE CASCADE：父表主键值若发生更新，子表外键自动同步变动。
