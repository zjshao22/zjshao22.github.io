QUIC 与实时通信：为不同目标选择机制

比较多流可靠传输、连接迁移与实时媒体的延时、抖动及恢复取舍

QUIC 与实时通信：为不同目标选择机制

浏览器同时下载课件、图片与脚本。如果所有应用数据复用同一条 TCP 字节流，一处缺口会阻止其后连续字节向应用交付；另一个本来已经到达的资源也可能等着。另一方面，实时语音的旧片段即使最终完整到达，也可能已经错过播放时刻。

“所有业务都用可靠字节流”与“所有业务都不重传”都过于粗糙。我们需要先明确目标：某条消息必须完整；某条消息必须及时；多条独立任务不应因无关缺口互相等待。

一、UDP 上能运行可靠协议吗

UDP 本身不负责顺序恢复与拥塞控制，并不禁止上层实现这些机制。QUIC 基于 UDP，在端点实现连接、可靠流、丢失恢复、流量控制、拥塞控制和加密等机制。QUIC 的基础规范将它定义为安全的多路复用传输。

因此“QUIC 用 UDP，所以没有可靠性”是错误推断。“UDP 协议没有这项保证”与“这个基于 UDP 的完整协议也没有”是两件事。QUIC 不是把 TCP 报头原样塞进 UDP，也不是将 TCP 握手简单删掉。

层次这一层承担什么
IP跨网络的数据报转发
UDP数据报端点、边界与校验等基础服务
QUIC加密连接、多流、恢复、窗口与拥塞控制
HTTP/3 等应用协议请求、响应与应用消息语义

二、多个流怎样减少无关等待

QUIC 的可靠流各有自己的字节偏移和交付顺序。同一流内仍需按序交付，但流 A 丢失的字节不必强迫独立流 B 的已到字节等待。

给定一个双向 QUIC 连接，应用使用两个不同流。下面是构造的事件，不是实际抓包。为便于推演，流号取 0 和 4；同一客户端创建的双向流使用这一类编号。

发送包携带的应用字节结果
包号 10流 0 的偏移 [0,1000)丢失
包号 11流 0 的 [1000,2000)，流 4 的 [0,200)到达
包号 12恢复流 0 的 [0,1000)到达

包 11 到达后，流 0 的后半块仍等自己的缺口；流 4 没有缺口，可以交付其 200 字节。包 12 补上后，流 0 才能连续交付 2000 字节。

QUIC 报告已收到的包号范围，可靠流使用流偏移识别应用数据。恢复丢失信息时使用新包号，不重新使用已经发送过的包号；因此不能把包号直接等同于 TCP 的字节 Seq。QUIC 的丢失检测与恢复规范独立描述恢复和拥塞机制。

它没有消除一切队头阻塞

同一可靠流仍按序等待缺失字节；多个流还共享连接和路径上的资源。拥塞窗口不足、连接级流量限制或应用之间有依赖，都可能造成等待。HTTP/3 的头部压缩也有自己的依赖管理，不能简单宣称“换 QUIC 后任何任务都不会阻塞”。

三、TLS 如何进入 QUIC

QUIC 与 TLS 1.3 集成，用 TLS 握手建立加密密钥和身份认证等安全状态，并保护传输数据；不是在已有 QUIC 连接外再叠一条传统 TLS-over-TCP 字节流。TLS 与 QUIC 的集成规范定义了这种关系。

正常的新连接需要握手；具备先前连接信息时可以尝试 0-RTT 应用数据，以减少等待，但服务端可以拒绝，且这类早期数据存在重放风险。不能把“支持 0-RTT”写成“任意第一次连接都不需要握手”，也不能未经应用判断就重放会产生副作用的操作。

加密并不代替业务核验

传输安全帮助防止窃听和篡改、验证对应身份等，却不能自动证明课件内容正确、服务器无漏洞或提交动作只发生一次。涉及扣费、修改或提交的业务，仍需要应用协议与服务端状态保证。

四、连接迁移与五元组

普通 TCP 连接通常由两端地址与端口等信息定位。手机从宿舍 Wi-Fi 切到蜂窝网络，本地 IP 或 NAT 外部端口改变，会影响原连接的继续使用。

QUIC 可以通过连接 ID帮助端点识别同一连接，并在规则允许时迁移到新路径。对新路径的验证、抗放大限制与拥塞状态调整仍然必要；知道连接 ID 不等于任意新地址都是可信接收者。

五、HTTP/3 到底改变了什么

HTTP/3 是 HTTP 语义到 QUIC 的映射，仍有请求方法、状态码、字段和消息体。改变的是承载与编码等机制，不是把“404 文件不存在”改成别的业务含义。HTTP/3 规范定义了它与 QUIC 流的关系。

看到 UDP 443 不足以单独证明使用 HTTP/3，QUIC 也可以承载别的应用。浏览器开发者工具的网络表若实际显示 h3，可以作为该请求所用 HTTP 版本的观察；显示 h2 则应如实记录，而不是按课程预期改写成 h3。

六、实时语音：迟到也可能等于没用

一次语音通话每 20 ms 产生一个音频包。若包丢了，等 500 ms 后完整重传回来，播放时刻可能早已过去。文件传输重视最终完整，实时媒体还必须考虑时限、连续性与交互延时。

实时系统可能丢弃过期数据、隐藏损失、降低编码速率、适当重传或使用前向纠错。实时并不等于完全不可靠；可靠也不等于无限等到旧消息到达。

RTP 提供哪些定位信息

RTP 常承载实时音视频，序号帮助发现缺失与乱序，时间戳描述媒体采样时间，SSRC 等标识媒体源；RTCP 可携带反馈和统计。RTP 本身不保证送达、准时或加密。RTP 基础规范定义了这些字段和配套控制。

以采样时钟 48000 Hz、每包 20 ms 的音频为例，时间戳通常每包推进 48000×0.02=960。这是媒体时钟刻度，不是以毫秒为单位的墙上时间；视频常用不同刻度。16 位包序号会回绕，接收方要结合序列进度处理，不能看到 0 就断定是新会话。

七、抖动缓冲的定量取舍

抖动是到达时间相对预期节奏的变化，不是平均延时的另一种名字。接收端留一段播放缓冲，吸收这种变化；缓冲越大，一些迟到包更可能赶上，却增加交互等待。

八、重传与前向纠错怎样取舍

若某包距离播放时限还剩 30 ms，而往返恢复估计需要 80 ms，单纯请求重传很难及时补救。若还剩 200 ms，则重传可能划算，但必须计入发送与排队时间，不能只比较一个理想 RTT。

前向纠错 FEC预先发送冗余，不必等缺失反馈才行动。比如对四个等长数据块加一个按位异或校验块，若只丢一个数据块且其他三块与校验块都到达，可通过异或恢复缺失块；额外负载占原四块总量的 25%。如果同组丢两个数据块，一份异或校验通常不够。

更多冗余也消耗瓶颈容量，可能增加拥塞。实时协议必须适当降低发送速率或媒体质量；“不能重传”不能成为忽略拥塞控制的理由。

QUIC 也有不可靠数据报扩展

QUIC 的可靠流适合需要完整有序的内容；QUIC DATAGRAM 扩展提供不要求重传的应用数据报，同时继续受到连接的安全与拥塞控制等规则约束。它不把所有流都改成不可靠，也不保证时限。

WebRTC 又是另一套包含媒体传输、协商、连通性与安全机制的体系；常见媒体使用安全 RTP 及相应反馈，不能把“实时网页通话”统称为 HTTP/3 视频下载。WebRTC 媒体传输要求说明了它与 RTP 的关系。

十、独立迁移：先写目标，再选机制

独立设计三个小方案：课件文件下载、多人语音、课程平台提交操作。分别写出“完整性、顺序、时限、安全、拥塞响应”的需求；指出哪些由传输提供，哪些仍必须由应用解决。

再修改播放模型：包 2 的延时改为 70 ms，缓冲仍为 60 ms。若有重传请求，来回还需 80 ms，重传可能赶上吗？若用四块加一份异或冗余同时丢两块，为什么不能承诺恢复？

完成后核对迁移要点

文件通常要求最终完整，可使用可靠传输与应用文件校验；语音重视时限、抖动处理与适应速率；提交业务还要应用层确认与重复请求处理。包 2 的目标时限是 100 ms，原到达时刻 110 ms，本来就晚；事后再等 80 ms 无法回到过去。一个异或关系通常不足以确定两个未知数据块，冗余能力必须匹配损失模式。
