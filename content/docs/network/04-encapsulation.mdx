# 第四节：从课件请求看封装

你在宿舍点击“打开网络基础课件”，浏览器发出了请求。上一节看到 IP 数据报会逐跳前进；现在追问：**一个数据报里装的是什么，接收方怎样把内容交给正确的程序？**

本节选择“浏览器通过基于 TCP 的 HTTPS 请求校园课件”作为教学模型。真实网站也可能使用 HTTP/3 等方式，学校平台的部署也各不相同。模型用来解释分层与封装，不宣称抓到了某所学校的真实通信记录。

## 一、从浏览器向下装入

**封装**就是：上层交给下层的数据，成为下层的负载；下层再加上自己需要的控制信息。浏览器生成“获取课件”的应用数据；TCP 把它作为传输数据并附加传输信息；IP 再附加网络层信息；当前链路最后把数据报放进一帧。

| 名称      | 在这个模型里的作用                         | 主要由谁使用       |
| --------- | ------------------------------------------ | ------------------ |
| 应用数据  | 表达要获取哪份课件，以及服务器给出的内容   | 浏览器与服务器程序 |
| TCP 段    | 带着端口等传输信息，支持端到端的有序字节流 | 两端主机的传输功能 |
| IP 数据报 | 带着源、目标 IP 等信息，供跨网络转发       | 主机与沿途路由器   |
| 链路帧    | 让数据越过当前一段连接                     | 当前一跳的相邻设备 |

**一个链路帧里包含一个 IP 数据报的情境示意**，不是说四层各自单独发一份互不相关的数据。平时把它们统称为“网络包”可以交流，但分析故障和协议时，要说清具体是哪种单位。

## 二、到了路由器，会换哪一层“外壳”

你的笔记本先用 Wi-Fi 把帧交给相邻网络设备。路由器接收当前链路的帧，取得其中的 IP 数据报，依据目标 IP 信息选择下一跳，再用**下一段链路适用的帧**发送。若下一段是有线连接，链路帧的形式会与第一跳不同。

普通转发路由器不必理解“网络基础课件”的标题，也不必把 HTTP 请求交给浏览器。它承担的是跨网络转发。源、目标 IP 在一次端到端通信里仍描述通信两端；途中某些设备可能做地址转换等处理，因此不能说实际报文中的地址在任何网络场景都绝不改变。

## 三、接收方怎样找到正确的程序

服务器主机收到最后一跳的帧后，从中取出 IP 数据报，再把其中的传输数据交给相应处理功能。传输层利用端口等信息找到目标通信端点，应用程序最终取得请求并作出响应。响应返回时也经历相似的逐层处理。

端口可以理解成“同一台主机上，通信要交给哪个服务端点”的标记。它不是楼宇的物理门牌，也不是 IP 地址。以常见的基于 TCP 的 HTTPS 为例，服务常使用 443 端口；这只是常见约定，不代表所有校园平台的实际配置。**IP 找到网络位置，端口帮助找到端点，课件路径指出具体资源。**

拿到页面主体之后，浏览器还可能继续请求图片和样式，所以从点击到页面完整显示，通常包含多次请求和许多数据报。前面画的一份请求只代表其中一个片段。

## 四、用现象判断先查哪里

| 看到的现象                         | 已知信息                         | 合理的第一步                                 |
| ---------------------------------- | -------------------------------- | -------------------------------------------- |
| 笔记本没有连上宿舍 Wi-Fi           | 第一段接入尚未建立               | 检查设备 Wi-Fi、校园网接入状态。             |
| 平台能打开，但某份课件显示“找不到” | 至少已得到平台给出的应用层结果   | 核对课程、资源路径、权限或资源状态。         |
| 页面主体出现，图片长期不显示       | 主体请求成功，附加资源可能出问题 | 查看图片请求结果，不能直接断定整条网络断开。 |

这些只是**排查起点**，不是凭一个现象就能锁定唯一故障。比如“加载慢”可能是本机、无线网络、沿途拥堵或服务端处理造成，需要更多证据。

## 五、用字节数检查封装是否理解正确

设一段教学数据的 **TCP 负载为 1000 字节**；暂不考虑 TLS、TCP 选项和 IP 选项，TCP 首部取 20 字节，IPv4 首部取 20 字节。则 TCP 段长为 1020 字节，IP 数据报总长度为 1040 字节。若在普通以太网上承载它，以太网首部按 14 字节、帧校验序列按 4 字节计算，帧从首部到尾部共 **1058 字节**。这里不计前导码、帧间隔等物理链路开销，也不计可能存在的 VLAN 标记。

| 封装到哪一层 | 本层新增字节 | 累计长度 |
| ------------ | ------------ | -------- |
| TCP 负载     | 1000         | 1000     |
| TCP 段       | 20           | 1020     |
| IPv4 数据报  | 20           | 1040     |
| 以太网帧     | 14 + 4       | 1058     |

这张表有两个边界：其一，HTTPS 的应用数据在真实网络里经过 TLS，实际协议开销会增加；其二，以太网有最小帧长，短负载可能需要填充。不能把 **1058** 当成所有“1000 字节文件”的固定网络成本。

## 六、MTU 与 MSS：为什么文件会分成许多包

**MTU** 是某段链路允许承载的最大网络层数据报大小。常见以太网 MTU 为 1500 字节。若 IPv4 首部和 TCP 首部各 20 字节，且没有选项，单个 TCP 段通常最多可装 **1500 − 20 − 20 = 1460 字节**的 TCP 负载；这是 MSS 的一种典型计算。TLS、隧道或其他封装会改变实际应用数据与帧大小之间的关系。

假设应用要发送 3000 字节数据，且教学模型固定每段 TCP 负载最多 1460 字节，那么可分成 1460、1460、80 字节三段。每段各有 TCP 和 IP 首部，经过当前链路时各自进入帧。直接拿**文件字节数 ÷ 1500**取整会遗漏首部，也把应用数据、IP 数据报和帧的大小混在一起。

IPv4 允许一定条件下的分片，但分片并非日常传输中希望依赖的常规办法；实际系统通常努力选择合适的包大小。这里先掌握为什么上层数据需要分段，以及每层长度的口径。

### 练习与解析

**题 1：**上述 3000 字节分成 1460、1460、80 字节三段。第三个 IP 数据报的总长度是多少？**答：120 字节。**80 字节 TCP 负载加 20 字节 TCP 首部、20 字节 IP 首部。

**题 2：**路由器从一侧以太网收帧、从另一侧以太网发帧，源与目标 MAC 地址可能改变吗？IP 目标必然变成下一跳吗？**答：**新帧的链路地址按下一跳重写；普通 IP 转发中，目标 IP 仍是最终目标。IPv4 TTL 会改变，首部校验和也需相应更新。

## 把四节课连起来

请用自己的话完成这段话，再对照答案：浏览器要获取课件，这是**应用层**的要求；数据交给服务器上的合适端点，涉及**传输层**；数据报跨网络寻找目标，涉及**网络层的 IP**；每一跳实际把数据交给相邻设备，涉及**链路层**。这些信息逐层装入，就是**封装**；路由器逐份选择下一跳，是**分组交换网络中的转发**。

如果你能解释“为什么页面 404 不能证明 Wi-Fi 断了”“为什么 Wi-Fi 帧到了路由器后可能换成另一种链路帧”，就已经能用模型分析真实的校园网络现象。
