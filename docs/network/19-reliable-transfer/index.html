可靠传输：确认、重传与滑动窗口

你用数据报传送作业文件，每一块都要完整、按序地交给接收应用。IP 和 UDP 没有给这件事通用的保证。最直接的办法是：“接收方收到后回一个确认；发送方等不到就再发。”

先设一个反例：数据已经到达，确认在途中丢了。发送方会重发；接收方如果每次都把数据交给应用，同一块便出现两次。因此可靠性不能只在发送方加一个循环，还要让两端区分“新数据”和“重发”。

本页先研究抽象的可靠传输模型。它不等同于 TCP 的全部实现；TCP 使用字节序号、连接状态、流量控制与拥塞控制，会在后面分别展开。

一、把“收到”改成可识别的确认

给每块消息一个序号。发送方保留尚未确认的内容，接收方保留“下一块期望的序号”。确认必须说明确认的是哪块，不能只是一个没有编号的 OK。

停止等待协议每次只允许一块未确认消息。没有有效确认便不能推进；超时重发相同内容和相同序号。检测到损坏的数据不能作为有效确认推进状态，因而校验也参与可靠性。

如果发送方仅记“我发过了”，无法重发原内容。如果接收方不记进度，无法消除重复。一次成功实验不能证明在任意延时、崩溃或无限报文寿命下都正确；模型假设也必须写清楚。

超时只表示“规定时间内没得到有效确认”，不能确定是数据丢了、确认丢了，还是延时过大。接收方再次发送确认非常关键：若它只丢重复数据、不回确认，发送方可能一直无法推进。

三、序号为何可以少，却不能随便复用

在每次只有一块未确认、旧报文不会在许多轮以后复活的模型中，0、1 交替的交替位协议就能区分当前新消息与上一条重发。编号不是“给文件命名”，而是消除当前允许出现的歧义。

一旦允许多块同时在路上，或者旧报文可能存在更长时间，只用一个位就不够。现实协议还会通过连接标识、序号空间、最大报文生存时间等办法避免旧连接数据污染新连接。不能把“0 和 1 够用于这个模型”推广为“所有可靠协议只需要一位”。

下面实验为方便阅读使用不回绕的消息编号，不实现有限序号空间。后面的窗口推演会单独检验回绕约束。

五、停等正确，为何吞吐量仍很低

设每块 1000 字节，链路速率 100 Mbit/s，传播等造成的往返时间 RTT 为 40 ms，忽略 ACK 发送时间。发送一块花 1000 × 8 / 100000000 = 0.08 ms。

每轮约花 0.08 + 40 = 40.08 ms，发送端忙于发数据的比例为 0.08 / 40.08 ≈ 0.20%。应用数据速率约为 8000 / 0.04008 ≈ 0.20 Mbit/s，远低于 100 Mbit/s 链路速率。

同一条链路，差距来自等待
0.08 ms一块的发送时间
40 ms给定 RTT
0.20%停等模型的利用率

改进是流水线：第一块的确认还没回来，继续发后面的块。窗口 W 限制同时未确认的块数，并使两端需要维护更多状态。理想、无丢失、无其他瓶颈时，利用率近似为 min(1, W × T发送 / (RTT + T发送))。

本例 W 为 100 时利用率约 19.96%；覆盖整轮等待需至少 501 块。带宽时延积 R × RTT = 500000 字节 是“链路路径上可同时在途多少数据”的重要尺度；精确模型还要计入发送时间等因素。

六、流水线丢一块：回退 N 与选择重传

发送窗口为 4，先发送块 0、1、2、3；块 1 丢失，其他到达。以下使用两种明确的课堂模型，不能把确认编号约定混用。

回退 N（GBN）模型：接收方只按序接收，丢弃乱序块；ACK k 表示“下一块期望 k”，即已连续收到 k 之前的块。对最早未确认块计时，超时把窗口内未确认块一起重传。

选择重传（SR）模型：接收方缓存窗口内的乱序块，逐块确认；每块有独立的逻辑计时，发送方只重传缺失块。连续缺口填好后，再向应用按序交付。

事件GBN 的接收与确认SR 的接收与确认
收到 0交付 0，ACK 1交付 0，确认块 0
块 1 丢失期望仍为 1连续交付仍缺 1
收到 2丢弃，重复 ACK 1缓存 2，确认块 2
收到 3丢弃，重复 ACK 1缓存 3，确认块 3
1 超时重传 1、2、3只重传 1
再收到 1交付 1，后续还待 2、3交付 1，并释放已缓存的 2、3

在这个给定丢失场景中，GBN 共发送 7 次数据，SR 共发送 5 次。SR 节约重传，但增加缓存、位图、计时与窗口管理复杂度；并非只把 GBN 的代码里“重发全部”改成“重发一个”便足够。

七、窗口必须与序号空间匹配

设序号字段为 k 位，共有 N = 2^k 个序号。经典 GBN 接收窗口为 1 时，发送窗口最多 N−1；经典 SR 两端窗口相同且为 W 时，需 2W ≤ N。这些限制属于给定模型，用于避免新旧窗口重叠带来的歧义。

以两位序号为例，N 为 4。若 SR 的窗口也取 4，接收方接收并交付 0、1、2、3 后，窗口又回到 0、1、2、3。若这批确认全部丢失，发送方重发旧 0；接收方可能把它误认为下一轮的新 0。取 W 为 2，使当前接收窗口与仍可能重发的旧窗口区分开。

这不意味着现实 TCP 把 32 位序号简单看成 SR 块号。TCP 按字节编号，还有报文寿命、连接状态等额外条件。可靠字节流的序号定义将在下一页具体使用。

八、独立迁移：延时误判与窗口取舍

先定位一个状态机错误

某人把发送程序写成下面的规则：“每收到任意 ACK，就把当前序号加一。”设消息 0 因确认太迟被发送了两次，接收方对两次到达都回 ACK 0。第一个 ACK 0 到来后，发送方已经开始发送消息 1；第二个 ACK 0 此时到来。

当前事件正确的发送方状态推进错误规则造成什么
第一个 ACK 0结束等待 0，开始等待 1暂时看不出错误
迟到的第二个 ACK 0识别为旧确认，仍等待 1错把 1 当成已确认，跳到 2

错误规则让未确认的消息被遗忘。确认编号不是输出日志的装饰，而是决定状态是否可以推进的依据。

再看计时器：消息 0 成功后，它以前启动的定时事件可能仍在事件队列里。若不核对当前等待消息与定时尝试，旧定时器可能错误重发下一条或重复启动已经结束的传输。实验脚本用尝试代号识别过期计时事件。

完成后核对两个不变量

只有确认当前等待序号的 ACK 才能推进；只有仍对应当前等待消息、当前尝试的计时器才能触发重发。它们共同避免迟到的旧事件改变新传输状态。本模型没有实现攻击防护与有限序号回绕，这些还需要更多约束。
