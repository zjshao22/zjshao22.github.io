# 数据库设计：ER 模型与模式规范化

数据库设计是整个软件系统工程的基石。如果初期表结构设计混乱、依赖关系不合理，后期写出的 SQL 查询不仅繁冗低效，还会遭遇**插入异常、删除异常和更新异常**等致命灾难。

本节我们将从业务需求出发，掌握 ER 图绘制与文字表达规范，理解 ER 转关系模式的核心规则，并建立一套严密的**规范化推理与分解框架**。

- **数据流图（DFD）**：强调业务中**数据的流动过程与加工处理逻辑**（数据从哪来、经过什么处理、流向哪去），属于需求分析工具。

## 二、概念设计：ER 模型要素与机考文字表达规范

<NormalizationFlowFigure />

### 1. ER 模型的四大要素

1. **实体（Entity）**：现实中可相互区分的事物（如学生、教师、图书、商品）。
2. **属性（Attribute）**：实体所具有的特征（如学生姓名、学号）。其中能唯一标识实体的属性称为**主键 / 标识（Identifier）**。
3. **联系（Relationship）**：实体型之间的对应关系：
   - **1:1（一对一）**：如班级与班长；
   - **1:N（一对多）**：如教师与课程（一名教师讲授多门课，一门课由一名教师主讲）；
   - **M:N（多对多）**：如学生与课程、读者与图书。
4. **联系属性（Relationship Attribute）**：产生于联系本身的属性。例如“成绩”产生于学生与课程的联系，“借阅日期/归还状态”产生于读者与图书的联系。

### 2. 机考文字表达规范（无图形客户端标准）

机考明确说明：**由于考试环境限制，答题时用文字描述 ER 图要素即可**。必须按下列标准格式组织，涵盖实体、属性、标识、联系类型及联系属性：

> **机考标准作答模板示例（图书借阅系统）**：
>
> 1. **实体与属性**：
>    - **读者（Reader）**：读者证号（标识/主键）、姓名、读者类别、联系电话。
>    - **图书（Book）**：图书编号（标识/主键）、书名、作者、出版社、定价、库存数量。
> 2. **联系与基数**：
>    - 读者与图书之间存在**借阅（Borrow）**联系，联系类型为**多对多（M:N）**（一名读者可借阅多本图书，一本图书也可被多名读者先后借阅）。
> 3. **联系属性**：
>    - “借阅”联系包含联系属性：**借阅日期、应还日期、实际归还日期、罚款金额**。

## 三、逻辑设计：ER 图转换为关系模式的规则

将概念 ER 模型落地为关系模式（表结构）时，必须严格执行以下三条基本规则：

### 规则 1：每个实体转换为一个独立的关系模式

- 关系的属性即实体的属性，**实体的主键即关系的主键**。
- 例：`学生(学号, 姓名, 性别, 年龄, 专业)`，主键为 `学号`。

### 规则 2：1:1 与 1:N 联系的转换

- **1:1 联系**：可单独建表；但通常**将任意一方的主键作为外键放入另一方**，并合并联系属性。
- **1:N 联系**：**在 N 端实体对应的关系模式中，加入 1 端实体的主键作为外键**，并将联系属性也放入 N 端。
  - 例：教师（1）与课程（N）是一对多联系。直接在 `课程` 关系中添加 `教师工号` 作为外键：`课程(课程号, 课程名, 教师工号)`。无需单独建表！

### 规则 3：M:N 联系必须转换为独立的关系模式

- 该独立模式的属性为：**参与该联系的各实体的主键**，加上**联系本身的属性**。
- **主键确定**：由各实体的主键共同组合构成**联合主键**。
- **特别注意（带业务重复发生条件）**：
  - 如果读者借阅图书可以发生多次（读者 A 在 3 月借了图书 B，还书后 5 月又借了图书 B），则单纯的 `(读者证号, 图书编号)` 组合在第 2 次借阅时会发生主键冲突！
  - **纠正**：必须将**借阅日期**纳入联合主键：主键为 `(读者证号, 图书编号, 借阅日期)`！

## 四、关系规范化理论：1NF 至 BCNF 推理框架

规范化是利用**函数依赖（Functional Dependency, FD）** 消除数据冗余与操作异常的数学化方法。

### 1. 核心概念速查

- **函数依赖（$X \to Y$）**：若属性集 $X$ 的值一旦确定，$Y$ 的值就唯一确定，称 $X$ 函数决定 $Y$。
- **候选键（Candidate Key）**：能够函数决定关系中所有属性，且其任何真子集都不能决定的最小属性组。
- **主属性 vs 非主属性**：包含在任何一个候选键中的属性称为**主属性**；其余属性为**非主属性**。
- **部分函数依赖**：非主属性依赖于候选键的某个**真子集**（例如候选键为 $(A, B)$，但 $A \to C$）。
- **传递函数依赖**：$X \to Y$ 且 $Y \to Z$（其中 $Y$ 不能决定 $X$），则 $X \to Z$ 是传递依赖。

### 2. 范式等级与分解标准

| 范式     | 定义与核验条件                                       | 消除的缺陷                         | 典型反例与问题                                                |
| -------- | ---------------------------------------------------- | ---------------------------------- | ------------------------------------------------------------- |
| **1NF**  | 关系中每个属性都是**不可分割的原子数据项**           | 消除表中包含子表、数组或复合列     | “联系方式”同时包含手机和邮箱，需拆为独立字段                  |
| **2NF**  | 满足 1NF，且每个非主属性**完全函数依赖于整个候选键** | 消除非主属性对候选键的**部分依赖** | 在 `(学号, 课程号)` 选课表中存放 `学生姓名`（姓名仅依赖学号） |
| **3NF**  | 满足 2NF，且任何非主属性**不传递依赖于候选键**       | 消除非主属性之间的传递依赖         | 在学生表中存放 `系主任`（学号 $\to$ 所在系 $\to$ 系主任）     |
| **BCNF** | 关系模式中**每一个决定因素都包含候选键**             | 消除主属性对候选键的部分/传递依赖  | 复合候选键交叉重叠且主属性决定其他属性                        |

### 3. 解题范式推导标准四步法

在机考与实验报告中，请使用统一推理模板组织答案：

**经典题目**：给定关系 `R(学号, 姓名, 课程号, 课程名, 成绩)`。

1. **写出业务函数依赖集 $F$**：
   - $\text{学号} \to \text{姓名}$
   - $\text{课程号} \to \text{课程名}$
   - $(\text{学号}, \text{课程号}) \to \text{成绩}$
2. **求解候选键**：
   - 能够决定全属性的最小属性组为 `(学号, 课程号)`。主属性为 `{学号, 课程号}`，非主属性为 `{姓名, 课程名, 成绩}`。
3. **范式判定与异常分析**：
   - 因为存在 $\text{学号} \to \text{姓名}$ 和 $\text{课程号} \to \text{课程名}$，非主属性依赖于主键的一部分，存在**部分函数依赖**，因此最高仅达到**1NF**，不满足 2NF。
   - **导致的异常**：
     - _插入异常_：新开一门课若暂无学生选修，由于学号为主键不能为空，导致课程无法录入；
     - _删除异常_：某门课的学生全部毕业删除后，该课程名称也随之丢失；
     - _更新异常_：某学生改名需要修改多行选课记录中的姓名，容易产生数据不一致。
4. **无损分解方案**：
   - 分解为三个满足 3NF/BCNF 的子模式：
     - `学生(学号, 姓名)`，主键：`学号`；
     - `课程(课程号, 课程名)`，主键：`课程号`；
     - `选课(学号, 课程号, 成绩)`，联合主键：`(学号, 课程号)`，外键分别引用学生与课程。

### 实验二标杆全案示范（以场景 4 图书借阅系统为例）

为帮助大家规范组织实验报告与机考作答，以下给出完整的满分示范全案：

#### 1. 需求分析与数据流简述（20 分）

- **业务背景**：图书馆面向师生读者提供借还书服务。每位借书人持有一张借书证，可借阅多种馆藏图书；一本图书可在不同时间借给不同的借书人。出版社向图书馆提供正版图书，每本书籍仅由一家出版社正式出版。
- **核心数据项字典**：
  - `reader_id`（借书证号）：主键，格式为字母加数字（如 `R2024001`）；
  - `book_id`（书号）：主键，如 ISBN 或内部馆藏条码（如 `B1001`）；
  - `publisher_name`（出版社名）：主键，出版社全称；
  - `borrow_time`（借阅时间）：DATETIME 类型，精确记录借书时间戳。

#### 2. 概念结构设计与机考文字规范（40 分）

- **实体与属性**：
  - **出版社（Publisher）**：出版社名（标识/主键）、地址、电话、Email。
  - **借书人（Reader）**：借书证号（标识/主键）、姓名、单位。
  - **图书（Book）**：书号（标识/主键）、书名、数量、位置。
- **联系与基数**：
  - 出版社与图书存在 **1:N（一对多）** 出版联系（一家出版社出版多种图书，一本书仅由一家出版社出版）。
  - 图书与借书人存在 **M:N（多对多）** 借阅联系。
- **联系属性**：
  - 借阅联系拥有联系属性：**借阅时间（borrow_time）**。

#### 3. 逻辑设计与模式规范化（30 分）

依据 ER 转表规则，概念模型映射为 4 个关系模式：

1. **出版社表**：`出版社(出版社名, 地址, 电话, Email)`，主键：`出版社名`。
2. **借书人表**：`借书人(借书证号, 姓名, 单位)`，主键：`借书证号`。
3. **图书表**（1:N 联系融入 N 端）：`图书(书号, 书名, 数量, 位置, 出版社名)`，主键：`书号`，外键：`出版社名`（引用出版社表）。
4. **借阅记录表**（M:N 联系独立建表）：`借阅(借书证号, 书号, 借阅时间)`。
   - **主键确定要点**：由于同一位读者可以在不同时间重复借阅同一本书，主键不能仅由 `(借书证号, 书号)` 构成，必须将业务发生时间纳入联合主键：**联合主键为 `(借书证号, 书号, 借阅时间)`**。
   - **外键**：`借书证号` 引用借书人表；`书号` 引用图书表。

**规范化验证（3NF 论证）**：

- 在上述 4 个关系中，每个字段均是不可再分的原子数据项，满足 **1NF**；
- 出版社、借书人、图书均为主键为单属性的关系模式，不存在部分函数依赖；借阅表中非主属性集为空，全属性构成主属性，不存在非主属性对候选键的部分依赖，因此全部满足 **2NF**；
- 在各个表中，非主属性均直接依赖于候选键，不存在类似 $X \to Y \to Z$ 的传递依赖，因此所有关系模式均达到 **3NF**，消除了插入、删除和更新异常。

#### 4. 物理结构设计：MySQL Workbench DDL 脚本

```sql
-- 创建图书借阅管理数据库
CREATE DATABASE IF NOT EXISTS library_db CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;
USE library_db;

-- 1. 出版社表（被引用父表，优先建立）
CREATE TABLE t_publisher (
  pub_name VARCHAR(100) NOT NULL COMMENT '出版社全称 (主键)',
  address VARCHAR(200) DEFAULT NULL COMMENT '社址',
  phone VARCHAR(30) DEFAULT NULL COMMENT '联系电话',
  email VARCHAR(100) DEFAULT NULL COMMENT '电子邮箱',
  PRIMARY KEY (pub_name)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='出版社信息表';

-- 2. 借书人表（被引用父表）
CREATE TABLE t_reader (
  reader_id VARCHAR(20) NOT NULL COMMENT '借书证号 (主键)',
  name VARCHAR(50) NOT NULL COMMENT '读者姓名',
  unit VARCHAR(100) NOT NULL COMMENT '所属学院/工作单位',
  PRIMARY KEY (reader_id)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='借书人信息表';

-- 3. 图书表（包含外键 pub_name）
CREATE TABLE t_book (
  book_id VARCHAR(30) NOT NULL COMMENT '书号/ISBN (主键)',
  title VARCHAR(150) NOT NULL COMMENT '书名',
  stock INT NOT NULL DEFAULT 0 COMMENT '库存余量',
  location VARCHAR(50) DEFAULT NULL COMMENT '馆藏架位',
  pub_name VARCHAR(100) NOT NULL COMMENT '外键：出版机构',
  PRIMARY KEY (book_id),
  CONSTRAINT fk_book_publisher FOREIGN KEY (pub_name)
    REFERENCES t_publisher(pub_name) ON UPDATE CASCADE ON DELETE RESTRICT,
  CONSTRAINT chk_book_stock CHECK (stock >= 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='图书资料表';

-- 4. 借阅流水表（M:N 联系独立建表，联合主键）
CREATE TABLE t_borrow_record (
  reader_id VARCHAR(20) NOT NULL COMMENT '外键：借书证号',
  book_id VARCHAR(30) NOT NULL COMMENT '外键：书号',
  borrow_time DATETIME NOT NULL COMMENT '借阅时间戳',
  return_time DATETIME DEFAULT NULL COMMENT '实际归还时间',
  PRIMARY KEY (reader_id, book_id, borrow_time),
  CONSTRAINT fk_borrow_reader FOREIGN KEY (reader_id)
    REFERENCES t_reader(reader_id) ON UPDATE CASCADE ON DELETE RESTRICT,
  CONSTRAINT fk_borrow_book FOREIGN KEY (book_id)
    REFERENCES t_book(book_id) ON UPDATE CASCADE ON DELETE RESTRICT
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='图书借阅流水记录表';
```

#### 5. ER 转换规则总结与心得（10 分）

1. **1:1 联系**：可单独建表，但通常将其中一方的主键作为外键放入另一方，并合并联系属性。
2. **1:N 联系**：在 N 端实体对应的关系中，添加 1 端实体的主键作为外键，并将联系属性归入 N 端实体表中。
3. **M:N 联系**：必须转换为独立的物理表。主键为各参与实体的主键组合（若有重复业务发生条件则加上时间等识别属性），联系属性放入该独立联系表中。外键分别引用各实体主键。
