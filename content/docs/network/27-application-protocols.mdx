# 第二十七节：应用协议、表示与分布式失败

TCP 能把字节按序交付，但它不知道“这段字节是邮件附件、中文名字还是一次转账”。应用还需要约定结构、意义、参与者和失败处理。

本节从“把内存直接发出去”这个朴素方案出发，解释应用协议为什么需要自己的消息格式与状态，并比较邮件、文件分发和远程调用。

## 一、同一组字节怎样得到相同的意义

发送端把某个内存结构直接复制到网络，接收端按自己的结构读取，可能遇到字节序、整数宽度、填充、指针地址和字符编码的差异。指针在另一台机器上尤其没有原来的意义。

**序列化**是把数据转换成约定的可传输表示；**反序列化**是按规则恢复数据。协议至少应说明字段类型、范围、长度、编码、版本以及错误处理，而不只是选择 TCP 或 UDP。

| 选择                 | 适合的用途                   | 需要处理的边界                           |
| -------------------- | ---------------------------- | ---------------------------------------- |
| 文本格式，例如 JSON  | 跨语言交换、易观察的结构数据 | 解析成本、数字范围、编码和字段版本       |
| 定义明确的二进制格式 | 紧凑表示、稳定字段类型       | 字节序、长度、未知字段和版本兼容         |
| 固定长度消息         | 结构简单、长度预先可知       | 扩展与可变长度字段不方便                 |
| 分隔符消息           | 逐行文本等简单协议           | 内容中出现分隔符时的转义规则             |
| 长度前缀消息         | 任意内容的明确边界           | 长度合法性、最大值、未收到完整消息的处理 |

Unicode 定义字符相关的编码空间，UTF-8 定义一种把码点编码成字节的方式；字符数不等于字节数。常见汉字在 UTF-8 中占多个字节，某些看起来“一个字符”的显示单元还包含多个码点。若协议长度用字节计，就必须先编码再计算长度。[JSON 的互操作编码要求](https://www.rfc-editor.org/rfc/rfc8259.html)

用整数金额表示分是一个可选设计：`amount_cents=1099`。如果随意用不同语言的浮点数表示 `10.99`，可能引入舍入差异。网络协议的表示选择会影响业务正确性，不能把格式问题推给可靠传输。

## 二、TCP 没有应用消息边界

发送端依次发两条消息，不保证接收端两次 `recv` 恰好各得到一条。一次读取可能取得半条、两条的拼接或其他分段；TCP 只提供有序字节流。

设应用格式为“4 字节无符号大端长度 + UTF-8 JSON 正文”，长度不含这 4 字节。接收端需要保存缓冲区：不足 4 字节时等待；读到长度后验证上限；不足完整正文时继续等待；完整后取出一条消息，再检查剩余字节是否组成下一条。

不能相信对方发来的长度就立即申请无限内存。消息上限、读取截止时间和解析失败处理，同样属于协议与服务设计。

下面程序只在内存中构造分段，**不是一次真实抓包**。有 Python 3 时直接运行，观察缓冲区怎样恢复两条消息：

```python
import json
import struct

def frame(value):
    data = json.dumps(value, ensure_ascii=False,
                      separators=(",", ":")).encode("utf-8")
    return struct.pack("!I", len(data)) + data

wire = frame({"name": "网络"}) + frame({"id": 7})
chunks = [wire[:2], wire[2:9], wire[9:17], wire[17:]]
buffer = bytearray()
for chunk in chunks:
    buffer.extend(chunk)
    print("本次加入", len(chunk), "字节")
    while len(buffer) >= 4:
        size = struct.unpack("!I", buffer[:4])[0]
        if size > 4096:
            raise ValueError("消息过大")
        if len(buffer) < 4 + size:
            break
        value = json.loads(bytes(buffer[4:4+size]).decode("utf-8"))
        del buffer[:4+size]
        print("恢复消息", value)
print("剩余字节", len(buffer))
```

先预测每次加入后是否能恢复消息，再核对运行结果。将分段位置改成每次 1 字节，或一次交付全部 `wire`，结果的消息意义应保持一致。接收端若在流结束时仍有不完整消息，还必须报告截断，不能把它当作正常完成。

## 三、压缩与媒体编码以什么为代价

**无损压缩**要求解压后恢复原数据，适合程序、结构数据和不能改变的文本；**有损压缩**允许按一定质量目标丢弃细节，常用于音频、图片和视频。压缩比不是固定常数，数据已经压缩或接近随机时，再次压缩可能没有收益。

教学计算采用十进制速率：采样率 48,000 次/s、每次 16 bit、双声道的未压缩音频速率是 `48,000 × 16 × 2 = 1,536,000 bit/s`，即 1.536 Mbit/s。还没有计算网络首部与容器开销。

若未压缩视频为 1920 × 1080 像素、每像素 24 bit、每秒 30 帧，速率约为 `1920 × 1080 × 24 × 30 = 1.493 Gbit/s`。假定某编码目标为 6 Mbit/s，这是教学参数，不保证任意内容都能以同样质量达到该值。

媒体编码会利用帧内或帧间冗余，取舍包括质量、带宽、运算量、随机访问和恢复错误的速度。长距离参考其他帧能提高效率，却可能增加恢复和延迟的复杂度；实时互动不能只选择“压得最小”的方案。

播放器的**抖动缓冲**用额外等待吸收到达时间波动。增加缓冲可能减少卡顿，却增加互动延迟。点播可按 HTTP 分段、自适应选择码率；实时音视频常使用媒体传输及反馈机制，不能把二者简单等同成“视频必用 UDP”。

## 四、邮件为什么不是收发者同时在线聊天

邮件采用存储转发。发送者把邮件交给发送服务，邮件服务器根据收件域的 MX 等信息找到对方邮件服务，完成服务器之间的传递；接收者稍后从邮箱访问它，不必与发送者同时在线。

SMTP 对话中的信封发送者、收件者决定投递；正文里的 `From`、`To` 等邮件头用于展示和其他处理。二者不必相同，显示“From: 老师”不能单独证明身份。`Bcc` 的设计也体现了展示收件人和投递收件人的区别。[SMTP 规范](https://www.rfc-editor.org/rfc/rfc5321.html)

IMAP 支持邮箱、标记及多个客户端的同步，不能说“读了邮件就必然从服务器删除”。邮件是否已读、是否移动或删除，由协议状态与客户端动作决定。[IMAP 规范](https://www.rfc-editor.org/rfc/rfc9051.html)

MIME 描述内容类型、字符集、多个部分及传输编码，使邮件能够包含文本和附件。Base64 是编码，**不是加密**：每 3 字节通常转为 4 个编码字符，忽略换行时，3000 字节附件会变成 4000 字节编码数据，还要加上邮件字段及边界。[MIME 基础](https://www.rfc-editor.org/rfc/rfc2045.html)

传输中的 TLS 保护相应一段连接，邮件服务器仍可能读到正文。要让中间邮件服务也不能读正文，需另外分析端到端内容加密与密钥管理。

## 五、文件传输与分发怎样选择架构

FTP 分开控制连接与数据连接，涉及主动或被动方式；它不是“所有文件数据都走同一条 21 端口连接”。传统 FTP 的明文认证和内容会带来风险，FTPS 是使用 TLS 的 FTP 方案。[FTP 基础规范](https://www.rfc-editor.org/rfc/rfc959.html)

SFTP 是经 SSH 通道工作的文件传输协议，**不是 FTP 简单增加 TLS**；SSH 还承担服务器认证、加密及完整性等功能。默认端口只是惯例，不能仅凭某个端口号证明应用的真实协议。[SSH 传输安全机制](https://www.rfc-editor.org/rfc/rfc4253.html)

| 架构          | 谁向谁提供内容               | 适合考虑的条件                           |
| ------------- | ---------------------------- | ---------------------------------------- |
| 客户端—服务器 | 服务集中接受请求             | 管理与权限清晰；中心能力和可用性是约束   |
| CDN           | 多个受管理边缘节点提供副本   | 可共享内容、地域分布、回源与缓存一致性   |
| P2P           | 参与节点既下载也提供已有片段 | 上行容量、节点离线、发现、可信校验和激励 |

教学下界估算：10 个客户端下载 100 MB 文件，源站上行 10 MB/s，各客户端下载至少 10 MB/s；不计协议开销。纯中心分发至少受总上行 `10 × 100 / 10 = 100 s` 限制。若各节点还能贡献 2 MB/s，P2P 总上行有机会达到 `10 + 10 × 2 = 30 MB/s`，总分发量给出约 33.3 s 的容量下界；还要同时满足源站至少先提供一份文件和单个下载能力等约束。

这不是保证 P2P 一定在 33.3 s 完成。早期片段尚未分散、拓扑、调度、节点退出和校验开销都可能使实际时间更长。P2P 也不意味着取消协调服务器或认证需求。

## 六、RPC 把调用藏起来，也藏不住失败

远程过程调用（RPC）把方法名、参数、请求标识等编码发送给远端，远端执行后再发送结果。它让程序看起来像本地调用，却多了延迟、超时、部分失败与版本兼容问题。[RPC 的协议基础](https://www.rfc-editor.org/rfc/rfc5531.html)

考虑以下教学时序：客户端请求 `addCredit(100)`；服务器已经写入数据库；响应在途中丢失；客户端超时。客户端只能知道“没有在期限内取得结果”，不能由此断言“服务器没有执行”。

| 朴素策略          | 可能后果                 | 可以改进的机制                       |
| ----------------- | ------------------------ | ------------------------------------ |
| 永不重试          | 请求丢失时业务可能未完成 | 查询结果状态、给出可恢复的业务流程   |
| 超时就原样重试    | 同一增量可能执行两次     | 稳定请求 ID、服务端去重与原结果返回  |
| 每次重试生成新 ID | 去重无法识别同一业务意图 | 重试同一操作时复用相应 ID            |
| 只在内存去重      | 服务重启可能丢失记录     | 按业务要求持久化去重状态并设计有效期 |

“至少一次”“至多一次”等语义都带条件；恰好一次的业务效果需要把请求识别、状态更新和故障恢复一起设计，不能只由 TCP 的可靠性得出。读操作和幂等状态设置可能更易重试，但授权和版本冲突仍要处理。

任务 A：应用长度字段写的是字符数，正文用 UTF-8。ASCII 测试都通过，加入中文后接收端解析失败。解释为什么，以及应在哪一步计算长度。

<details>
<summary>核对解释</summary>

中文编码后通常比字符数占更多字节，接收端过早切断正文，使后续字节也错位。应先生成确定编码的正文，再以字节数填写长度；还要校验上限与完整性。
