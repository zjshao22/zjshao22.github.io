数据库应用开发与系统集成

脱离具体应用程序的数据库是静态的“数据仓库”；只有与业务应用层深度集成，才能真正释放数据的业务价值。

本节我们将深入剖析应用与数据库的通信协议与驱动层，掌握参数化预编译查询与安全防注入，设计身份认证与严格的业务数据范围隔离，并提供一套可直接运行的最小应用工程骨架。

一、应用与数据库通信架构

外部程序访问 MySQL 时，绝不是由前端页面直接连数据库，而是采用经典的三层分工：

  1. 展示层（UI / Web / 客户端）：负责收集用户输入的账号、密码、学号、成绩，渲染列表表格与操作反馈。
  2. 应用业务层（Application Server）：维护会话状态（记录当前登录的教师工号 current_teacher_id），执行参数化校验，构造并执行业务 SQL。
  3. 数据库存储层（MySQL）：执行 SQL，维护外键参照约束与 ACID 事务，返回结果集或受影响行数。

二、安全红线：参数化查询（Prepared Statement）与防注入

在构造动态 SQL 时，初学者最容易犯的错误是字符串直接拼接：

如果攻击者在密码框输入 ' OR '1'='1，SQL 就会变成 ... WHERE username = 't001' AND password = '' OR '1'='1'，导致认证逻辑被彻底绕过！这就是臭名昭著的 SQL 注入漏洞。

标准解决方案：参数化预编译占位符（?）

所有语言的现代数据库驱动（Node.js mysql2、Python pymysql/sqlite3、Java PreparedStatement）均支持参数化查询。SQL 结构预先发送给 MySQL 编译，输入参数仅作为纯数据传递，从语法层面彻底消除了 SQL 注入风险：

1. 登录与身份映射

  • 认证规则：教师输入工号（如 t001）与密码（教学实验统一支持预设凭证验证，如默认口令 123456，或经哈希比对）。
  • 状态维持：认证通过后，服务端生成随机安全凭证（Token / Session），后续所有请求必须携带该凭据，由服务端解析出 current_teacher_id 作为不可篡改的查询上下文。

五、实验四现场答辩与验收准备清单

现场验收不仅看系统能否运行，更侧重考察个人对底层数据库交互的理解。教师现场将随机抽取以下任务进行现场问答：

  1. 现场切换教师：先以李明（t001）登录，展示课程 c001、c003；注销后以陈军（t003）登录，检查界面是否仅显示大学英语（c002），证明数据范围隔离机制生效。
  2. 非法输入拦截：在成绩输入框输入 120 或 -5，检查系统是前端校验还是捕获了 MySQL CHECK 约束异常。
