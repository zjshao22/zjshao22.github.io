# 前三节回顾：把一次访问讲清楚

先关掉前三节正文，用自己的话完成任务。遇到困难再返回 [网络应用](/docs/network/01-how-web-works/)、[四层分工](/docs/network/02-four-layers/) 或 [IP 与分组交换](/docs/network/03-ip-and-packets/) 对应部分。

参考用于订正。看完答案能复述，和隔一段时间独立解决新问题，是不同的结果。

## 一、一份访问记录

以下是构造的课程平台记录。笔记本已接入网络，浏览器向 HTTPS 服务发出请求。

| 请求                | 类型     | 状态 | 已返回的内容       |
| ------------------- | -------- | ---- | ------------------ |
| `/course/network`   | 页面文档 | 200  | 课程目录 HTML      |
| `/assets/site.css`  | 样式     | 200  | 页面样式           |
| `/slides/week1.pdf` | 课件     | 404  | “资源不存在”的响应 |

写出你的判断和依据：

1. 至少有几个应用请求？“打开页面”为什么不等于只有一个包？
2. 404 能说明什么？它能证明无线连接断了吗？
3. 判断第三项为什么失败，还需要哪些应用层信息？

<details>
<summary>提示：把请求结果和底层可达性分开</summary>

先找哪条记录证明有服务返回了响应，再看失败的是连接还是某份资源。状态码属于应用约定，不能代替每条链路的检查。

</details>

<details>
<summary>完成后核对</summary>

至少三个请求；每个请求或响应又可能分成许多传输数据和 IP 数据报。浏览器通常还会请求样式、图片等资源。

404 表示有 HTTP 服务对该请求返回了“找不到”这一语义。它支持先检查路径、资源发布状态等解释，不支持仅凭它断言 Wi-Fi 已断。结果也可能来自代理或缓存，还应辨明响应者。

可以检查请求 URL、最终重定向地址、权限相关响应、服务日志或资源状态。目录成功不能保证所有请求成功，也不能证明下一时刻仍可达。

</details>

## 二、重建标识与职责

教学情境：浏览器访问 `https://course.example.net/slides/week1.pdf`。解析给出服务器地址 `203.0.113.20`，应用采用基于 TCP 的 HTTPS，目标端口 443。本机为 `192.168.20.10`，链路接入已经建立。

域名与文档专用 IP 用于表达角色，没有要求访问真实校园服务器。

| 信息                 | 它解决的问题 | 主要使用者 |
| -------------------- | ------------ | ---------- |
| `course.example.net` | 自己填写     | 自己填写   |
| `203.0.113.20`       | 自己填写     | 自己填写   |
| TCP 443              | 自己填写     | 自己填写   |
| `/slides/week1.pdf`  | 自己填写     | 自己填写   |
| 当前链路的地址       | 自己填写     | 自己填写   |

<details>
<summary>核对标识表</summary>

| 信息     | 它解决的问题                               | 主要使用者            |
| -------- | ------------------------------------------ | --------------------- |
| 域名     | 使用可管理的名称，借助名称系统取得连接信息 | 应用与名称解析系统    |
| 目标 IP  | 标识网络层目标，供跨网络转发               | 主机与沿途路由器      |
| TCP 443  | 区分主机上的传输端点                       | 两端 TCP 与套接字功能 |
| 资源路径 | 指明请求哪个应用资源                       | 浏览器与 HTTP 服务    |
| 链路地址 | 在当前链路交付一帧                         | 相邻链路设备          |

域名可有多个地址；主机可提供多个端口上的服务；同一服务可有许多路径。这些关系不能互相替代。

</details>

再回答：普通路由器需要理解 PDF 排版吗？第一段和第二段链路类型不同，浏览器是否要重新定义课件内容？

<details>
<summary>核对分层理由</summary>

普通 IP 转发依据网络层信息，不需要读取 PDF 排版。下一跳换用适合该链路的帧，应用仍按自己的协议交换内容。具体首部变化将在封装与 IP 章节推演。

</details>

## 三、重新运行一个小队列

出口按 FIFO 发送完整数据报，不在中途抢占。速率 **8 Mbit/s**，每份数据报 **1000 字节**，暂不计帧开销。A、B、C 在时刻 0、0.25、1.25 ms 到达。开始时出口空闲。

写出各数据报的开始、完成和排队等待时间。C 到达时 B 是否已发送完成？

<details>
<summary>提示一：统一单位</summary>

1000 字节是 8000 位。发送时延是“位数 / 位速率”；所有时刻和时长都换成 ms 再比较。

</details>

<details>
<summary>提示二：每份从两个时刻中较晚者开始</summary>

开始时刻是“自己到达”与“前一份完成”的较晚者；排队时间是开始减去到达。

</details>

<details>
<summary>核对队列过程</summary>

每份发送时延为 8000 / 8,000,000 = **1 ms**。

| 数据报 | 到达    | 开始 | 完成 | 排队    |
| ------ | ------- | ---- | ---- | ------- |
| A      | 0 ms    | 0 ms | 1 ms | 0 ms    |
| B      | 0.25 ms | 1 ms | 2 ms | 0.75 ms |
| C      | 1.25 ms | 2 ms | 3 ms | 0.75 ms |

C 到达时 B 正在发送。这里只算一个出口，没有包括传播、接收端处理或其他链路；3 ms 不能直接叫整次网页访问时间。

</details>

**独立变式：**C 改在 3.5 ms 到达，其他不变。它何时完成？这一变化会改变传播速度吗？

<details>
<summary>核对变式</summary>

B 在 2 ms 已完成，C 在 3.5 ms 开始，4.5 ms 完成，排队为 0。到达间隔影响等待，不改变介质中的传播速度。

</details>

## 四、哪些性质不是 IP 的保证

构造记录：发送三份 IP 数据报，顺序为 1、2、3；完整观察接收入口，只出现 1、3，稍后又出现一份 1。

先区分观察现象、IP 服务边界与所需补充功能，不把它直接称为“TCP 失效”；记录尚未说明传输协议和应用最终交付。

<details>
<summary>核对服务边界</summary>

模型中观察到 2 未交付、1 重复。真实抓包还要考虑抓包点是否遗漏、观察是否完整。

IP 不保证交付、顺序或只出现一次。可靠传输需要序号、确认、重传、重复抑制等机制；这些机制如何配合将在传输章节从失败情形推导。

</details>
