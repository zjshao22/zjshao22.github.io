# TCP 窗口、流量控制与计时

服务器的网络能很快收到数据，磁盘写入却很慢。如果发送方只根据“数据都到达了”继续发，接收缓冲最终会耗尽。可靠排序解决了内容正确性，还没有解决**接收应用来不及消费**的问题。

朴素改进是“接收方满了再把数据丢掉”。它会触发无谓重传，且不能让发送方事先适应接收能力。TCP 用接收窗口 rwnd 通告可接受的字节范围；发送方依据窗口与已有在途数据决定还可以发多少。

## 一、接收窗口与累计确认各管一件事

Ack 表示“此前这些字节已经连续收到”；Window 表示“从 Ack 指出的起点，还愿意接受多少字节”。确认是对已接收进度的反馈，窗口是对后续接收能力的通告，二者不能互相替代。

给出 Ack=5001、rwnd=4000，说明通告的序号范围为 `[5001, 9001)`，即 5001～9000。它不说明接收应用已经处理了所有此前数据，也不保证路径能承受这么大的发送量。

## 二、滑动窗口不是“每次再发 rwnd 字节”

发送方已得到 Ack=5001，下一新字节 Seq=7001，因此还有 2000 字节已发但未累计确认。在忽略拥塞限制、没有窗口缩减等复杂情况的本题中，窗口右边界为 9001，还可新发 `9001 − 7001 = 2000` 字节。

| 状态量         | 含义                    | 本例      |
| -------------- | ----------------------- | --------- |
| 最早未确认字节 | 发送窗口的左端          | 5001      |
| 下一新字节序号 | 已发送范围的右端        | 7001      |
| 在途未确认量   | 两者之差                | 2000 字节 |
| 接收窗口右边界 | Ack + rwnd              | 9001      |
| 剩余新发送空间 | 右边界 − 下一新字节序号 | 2000 字节 |

若把“收到 rwnd=4000”理解为“这次还可以发 4000”，便忘了已有在途数据，超出了通告范围。真实实现还要按有效窗口更新规则处理旧 ACK、序号回绕和异常窗口改变，不能只比较任意一份包里的两个整数。

### 窗口怎样推进

接收方连续收到已有 2000 字节，回 Ack=7001。如果它尚未把字节交给应用，剩余容量可能只有 2000，则通告 `[7001, 9001)`，右边界不一定增加。等应用消费 2000 字节，rwnd 重新增到 4000，右边界才推进到 11001。

**ACK 增长不等于容量自动增加**。必须将“协议接收了多少”与“应用消费了多少”分开观察。

## 三、零窗口与失联不同

若接收方通告 rwnd=0，发送方应停止按普通规则注入新数据。零窗口表示暂时不愿接受更多字节，不等于连接一定断了。

接收应用稍后读走数据，窗口更新可能在途中丢失。若发送方永远等一个新通告，两端就可能僵住。TCP 使用零窗口探测相关机制，让发送方周期性探查窗口是否重新开放；探测并不等于普通无节制发送。[TCP 的窗口管理规则](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.8.6.1)区分了这些处理。

小块读取与小块发送还可能形成低效率的“糊涂窗口综合征”。接收方可避免只通告极小增量，发送方也可合并小块；Nagle 算法与延迟 ACK 会影响交互延时，但它们不是“TCP 一律等待攒满 MSS”这样的绝对规则。

## 四、窗口太小会限制高速长距离传输

路径可用速率为 100 Mbit/s，RTT 为 50 ms。带宽时延积是 `100000000 × 0.05 / 8 = 625000 字节`，约 610.35 KiB。

如果只能维持 65535 字节在途，在忽略丢包、报头与其他限制的估算下，窗口约束吞吐量不超过 `65535 × 8 / 0.05 ≈ 10.49 Mbit/s`。这不是网卡突然降速，而是确认返回之前没有足够多的数据在路上。

想达到路径速率，需要足够的接收缓冲、发送缓冲与拥塞窗口，而且应用持续供给数据。**窗口除以 RTT 是给定条件下的约束尺度，不是保证达到的实测吞吐量**。

### 窗口扩大选项怎样工作

TCP 报头 Window 字段为 16 位，窗口扩大选项在握手时协商一个移位计数 s。建立后，一方所通告的实际接收窗口按 `字段值 × 2^s` 解释；两个方向可使用不同移位计数。

例如 s=4、字段值 40000，对应 rwnd=640000 字节；这足以覆盖本例 625000 字节的尺度。移位不是给 ACK 和 Seq 一起乘 16，也不会凭空增加物理内存。SYN 中的窗口字段本身不按已协商的移位解释。[窗口扩大扩展](https://www.rfc-editor.org/rfc/rfc7323.html#section-2)还规定了协商与计数限制。

## 五、可靠重传需要测量 RTT

固定超时存在两种风险：太短会把正常延时当丢失并重复发送；太长则让真实丢失长期无法修复。TCP 用成功确认的数据样本估计 RTT，同时估计变化幅度，形成重传超时 RTO。

RTT 是一次往返观测，SRTT 是平滑估计，RTTVAR 是变化幅度估计，RTO 则是等待确认的阈值。它们单位都是时间，但用途不同。

### 首个样本的推演

按 RFC 6298 的基础算法，首个 RTT 样本 R=120 ms 时：SRTT=120 ms，RTTVAR=60 ms。若时钟粒度 G=1 ms，候选值为 `120 + max(1, 4×60) = 360 ms`。

该基础规范建议将计算出的不足 1 秒 RTO 向上取到 1 秒，因此本例按该规则使用 1000 ms。部分实现或场景可能有不同的最小定时策略；不要把课堂候选计算或某台机器的实现值直接当成所有 TCP 的唯一行为。[RTO 计算规范](https://www.rfc-editor.org/rfc/rfc6298.html#section-2)给出了算法与建议。

### 第二个样本为何先更新变化幅度

第二个 RTT 样本为 160 ms，使用 α=1/8、β=1/4。先用旧 SRTT 更新：

`RTTVAR = (3/4)×60 + (1/4)×|120−160| = 55 ms`。

再更新：`SRTT = (7/8)×120 + (1/8)×160 = 125 ms`。候选 RTO 为 `125 + 4×55 = 345 ms`，按上述建议下限仍为 1000 ms。平滑值不会因为一次较大样本立刻跳到 160 ms。

## 六、Karn 算法：重发后为什么样本有歧义

0 ms 发一段，1000 ms 超时重发，1100 ms 收到同一字节范围的确认。这个 ACK 可能对应原段的极迟到达，也可能对应重发段。RTT 应记 1100 ms 还是 100 ms？仅凭普通序号与 ACK，无法确定。

Karn 原则避免用有重传歧义的样本更新 RTT。超时后 RTO 通常退避加倍，以免路径已经拥塞时还不断快速重发；有可消除歧义的时间戳机制时，可以获得更明确的测量。

这个问题与前页模型中的“超时但没丢包”一致：**观察到超时，不足以说明是哪一段路径、哪一种队列发生了真实丢失**。

## 七、动手恢复一份窗口记录

### 先做一个 RTT 样本计算器

将下面代码保存后执行，并逐行核对 SRTT、RTTVAR 的更新次序。它只实现本页的基础数值模型，不读取真实网络，也不是完整 TCP 定时器。

```python
samples_ms = [120.0, 160.0, 100.0, 300.0]
srtt = None
rttvar = None
for sample in samples_ms:
    if srtt is None:
        srtt = sample
        rttvar = sample / 2
    else:
        rttvar = 0.75 * rttvar + 0.25 * abs(srtt - sample)
        srtt = 0.875 * srtt + 0.125 * sample
    candidate = srtt + max(1.0, 4 * rttvar)
    rto = max(1000.0, candidate)
    print("sample", sample, "SRTT", srtt,
          "RTTVAR", rttvar, "RTO", rto)
```

把最后的 300 改为 600，再比较变化。较大样本会同时改变平滑估计与波动估计；如果你只把 RTO 写成平均 RTT，无法给变化留出同样的余量。

**核验产物：**保留参数、输出，以及首两个样本的手算。说明这段代码缺少哪些真实机制，例如重传后的样本筛选、定时器启动与重置、超时退避及时间戳处理。运行一个数值模型不证明系统 TCP 内核实际使用了这些输出值。

## 八、独立迁移：是哪一个限制在起作用

### 确认、接收与业务完成是三个检查点

假设客户端的 2000 字节已经被服务器 TCP 累计确认，但服务器应用刚开始读取，还没有写入磁盘。此时传输层确认有效，应用业务仍可能失败。如果客户端页面直接用 ACK 判断“作业已保存”，服务器随后磁盘出错就无法给出真实业务结果。

更稳妥的应用协议需要规定业务成功响应，例如服务器在验证内容并完成规定保存步骤后，返回提交编号与结果。这个响应也通过网络传送，客户端仍要处理它丢失或连接中断后的不确定状态；不能只把一次重试无条件算成第二次提交。

这说明 rwnd 代表接收缓冲的协作，TCP ACK 代表传输接收进度，应用成功响应代表协议规定的业务状态。课程平台、支付或数据库交互都要把这些检查点分开。

不看答案，求解三个新条件。

1. 路径为 1 Gbit/s、RTT 80 ms，求带宽时延积。若有效接收窗口只有 1 MiB，估算它的窗口约束速率。
2. 第一个 RTT 样本为 80 ms，G=1 ms，求 SRTT、RTTVAR、候选 RTO 和按 RFC 6298 建议下限取值后的 RTO。
3. 接收方窗口很大，文件传输仍慢。除 rwnd 外，还应考虑哪些因素？不要用“大窗口一定快”作解释。
