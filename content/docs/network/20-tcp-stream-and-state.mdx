# TCP：字节流、连接与关闭

课程作业系统要传完整文件，逐块写可靠数据报协议会涉及许多共同问题。TCP 把可靠、有序的**字节流**提供给应用。它维护连接状态、排序与重传，但没有自动理解“这是一次作业提交”或“这是两条聊天消息”。

最容易出错的做法是：“发送方 `send` 两次，接收方 `recv` 两次就能读出两条消息。”先用反例检验：如果第一条消息被分成两段接收，或者两条消息一起进入接收缓冲，接收应用如何划分？

## 一、写入边界不是读取边界

发送方依次写入 `HELLO` 与 `OK`。接收方可能先读 `HE`，再读 `LLOOK`；也可能一次读 `HELLOOK`，或分更多次读。这些结果都可以对应同一条有序字节流。

TCP 段边界、应用 `send` 调用边界、应用 `recv` 调用边界是三个不同概念。TCP 可以分段与合并，接收调用最多取指定数量的当前可用字节，不负责重现对方调用次数。[TCP 的服务定义](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2)是有序、可靠字节流。

| 边界         | 由谁决定                 | 应用能否把它当作消息终点 |
| ------------ | ------------------------ | ------------------------ |
| 应用写入调用 | 发送应用与 API           | 不能据此推断远端读取边界 |
| TCP 段       | TCP 实现、MSS 与发送策略 | 不能作为通用应用消息边界 |
| 应用读取调用 | 接收缓冲及读取上限等     | 一次读取可能只是半条消息 |
| 应用协议消息 | 两端共同约定的编码       | 可以，但必须正确解析     |

### 怎样自己定义消息

常见方法包括固定长度、分隔符和**长度前缀**。固定长度简单但不灵活；分隔符需要转义或禁止负载含分隔符；长度前缀必须限制最大长度，防止错误长度让接收方无限等待或分配大量内存。

这里用四字节无符号大端整数表示后续消息字节数。长度为 6 的“网络”编码为 UTF-8 时恰为 6 字节；字符数 2 与字节数 6 不能混淆。

## 二、可运行的长度前缀接收器

以下是应用协议代码，TCP 可靠机制由操作系统实现。先把服务器保存为 `tcp-server.py`，在一个终端运行，再运行下面客户端。只使用本机回环地址与标准库。

```python title="tcp-server.py"
import socket
import struct

def recv_exact(sock, size):
    chunks = bytearray()
    while len(chunks) < size:
        part = sock.recv(size - len(chunks))
        if not part:
            raise EOFError("connection ended inside a message")
        chunks.extend(part)
    return bytes(chunks)

with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as listener:
    listener.bind(("127.0.0.1", 19020))
    listener.listen(1)
    listener.settimeout(10)
    print("listening", listener.getsockname(), flush=True)
    conn, peer = listener.accept()
    with conn:
        conn.settimeout(3)
        print("accepted", peer)
        for _ in range(2):
            size = struct.unpack("!I", recv_exact(conn, 4))[0]
            if size > 4096:
                raise ValueError("message too large")
            data = recv_exact(conn, size)
            print("bytes", size, "text", data.decode("utf-8"))
        print("peer finished sending", conn.recv(1) == b"")
        conn.sendall(b"accepted")
```

```python title="tcp-client.py"
import socket
import struct

with socket.create_connection(("127.0.0.1", 19020), timeout=3) as conn:
    for text in ["网络", "OK"]:
        data = text.encode("utf-8")
        conn.sendall(struct.pack("!I", len(data)) + data)
    conn.shutdown(socket.SHUT_WR)
    reply = bytearray()
    while True:
        part = conn.recv(1024)
        if not part:
            break
        reply.extend(part)
    print("reply", bytes(reply))
```

服务器的监听 socket 负责接受连接，`accept` 返回的 socket 对应这一次通信。多个客户端可以连同一监听端口，已建立连接由两端地址与端口等信息区分。`sendall` 完成是本地接口成功把所有字节送入传输过程，不是远端应用已经处理完业务的证明。[Python socket 接口](https://docs.python.org/3/library/socket.html)区分监听、连接与半关闭操作。

## 三、TCP 序号到底数什么

TCP 每个方向各有独立序号空间，按**字节**编号。一个段的 Seq 指向该段第一个数据字节；确认号 Ack 表示“下一字节期望的序号”，即累计确认之前的连续字节。

设首个应用数据字节编号为 1001，发送一段 6 字节的数据，覆盖 1001 至 1006。全部按序收到时，对方回 Ack 1007。若紧接着再发 2 字节，Seq 为 1007，收到后 Ack 为 1009。

纯 ACK 不占用新的序号；SYN 和 FIN 各占用一个序号位置，便于将建立、结束也纳入可靠确认。报头中的序号字段为 32 位，会回绕，必须按 TCP 的序号比较与报文寿命规则理解，不能用普通无限整数比较替代完整实现。

## 四、累计确认遇到缺口会怎样

接收方期望 1001，三段数据分别覆盖 `[1001, 2001)`、`[2001, 3001)`、`[3001, 4001)`；左端包含，右端不包含。中间段丢失。

| 到达事件           | 连续收到的范围      | 累计 Ack | 有 SACK 时可报告   |
| ------------------ | ------------------- | -------- | ------------------ |
| 第一段到达         | 到 2000 为止        | 2001     | 无需报告缺口后的块 |
| 第三段到达并被缓存 | 连续范围仍停在 2000 | 2001     | `[3001, 4001)`     |
| 缺失第二段补到     | 连续范围到 4000     | 4001     | 缺口填平           |

**选择确认 SACK**可以告诉发送方“缺口以后这些字节已收到”，帮助选择重传目标，但不改变累计 Ack 的含义。SACK 需要事先协商；接收方允许在特定情况放弃曾报告的缓存，因此发送方不能仅凭 SACK 就永久删除未被累计确认的数据。[SACK 规范](https://www.rfc-editor.org/rfc/rfc2018.html)明确保留累计确认机制。

TCP 向应用交付连续字节，缺口之后的字节即使到达，也通常不能越过缺口直接交给同一条字节流的应用。这种等待是传输层队头阻塞的来源，后面会与 QUIC 的多流比较。

## 五、三次握手是在同步什么

“连上服务器”不仅要确认地址存在，还要同步双方初始序号和有关能力，并让双方知道对方收到自己的建立请求。假设客户端 ISN 为 1000，服务器 ISN 为 9000。

| 次序 | 方向与字段                           | 收到后的关键含义                          |
| ---- | ------------------------------------ | ----------------------------------------- |
| 1    | 客户端发 SYN，Seq=1000               | 服务器知道客户端起点，客户端进入 SYN-SENT |
| 2    | 服务器发 SYN+ACK，Seq=9000，Ack=1001 | 确认客户端 SYN，并宣布服务器起点          |
| 3    | 客户端发 ACK，Seq=1001，Ack=9001     | 服务器得到自己 SYN 已被收到的确认         |

客户端收到有效 SYN+ACK 后可以进入 ESTABLISHED；服务器收到有效第三步 ACK 后完成相应转换。第三步可以携带应用数据。现实还有同时打开、重传、拒绝与扩展，本表只展示正常主动打开。

两个消息为什么不够？服务器发出 SYN+ACK，只能说明它发出了自己的序号；没有第三步，不能确定客户端已经收到并接受这个起点。握手还帮助处理延迟旧报文等问题，但不证明应用业务健康，也不等于身份认证。

## 六、全双工为何允许半关闭

TCP 可以同时双向传数据。“客户端不再发送作业内容”不一定意味着“客户端不再接收服务器结果”。一个方向发 FIN，只表示这个方向没有更多字节，不会自动关闭反向数据流。

前面的客户端 `shutdown(SHUT_WR)` 结束发送方向，仍接收 `accepted`；服务器读取到 `b""` 表示在已收到之前数据后，读到该方向的正常 EOF。单个 `recv` 返回少于请求长度仍只是部分数据；只有零字节在流 socket 中才表示正常读取结束。

### 一次正常关闭的序号推演

沿用客户端首字节 1001，假设共发 6 字节，所以接下来 Seq 为 1007。服务器反向首字节为 9001。

| 事件                   | 主要字段或结果            |
| ---------------------- | ------------------------- |
| 客户端结束发送         | FIN，Seq=1007             |
| 服务器确认客户端 FIN   | Ack=1008                  |
| 服务器仍发送三字节结果 | Seq=9001，覆盖 9001～9003 |
| 服务器也结束发送       | FIN，Seq=9004             |
| 客户端确认服务器 FIN   | Ack=9005                  |

常见正常关闭出现四个逻辑步骤，但 ACK 可以与 FIN 合并，双方也可以同时关闭，**不能规定任何关闭都恰好抓到四个包**。RST 是另一种异常终止信号，不是正常 FIN 收尾的同义词。

## 七、TIME_WAIT 为什么没有立刻消失

正常主动关闭一方通常经历 FIN-WAIT 状态，最终进入 TIME_WAIT；被动关闭一方通常经历 CLOSE-WAIT、LAST-ACK。应用长时间停在 CLOSE-WAIT 常提示它尚未完成本地关闭，应结合具体进程与状态判断。

TIME_WAIT 给旧报文消退留出时间，并允许在对方重发 FIN 时再次发送最后的确认。基础规范使用 2×MSL 的等待概念；MSL 是最大段生存时间的模型参数，不能把某个操作系统的一项默认秒数当成所有 TCP 的普遍常量。[连接关闭规范](https://www.rfc-editor.org/rfc/rfc9293.html#section-3.6)给出了状态处理。
