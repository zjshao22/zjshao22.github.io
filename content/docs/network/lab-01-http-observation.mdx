# 实验一：本机 HTTP、缓存与抓包

先预测：一份课件返回 404 时，TCP 一定断了吗？第二次访问比第一次快，一定是网络带宽变大了吗？用自己能控制的服务检验这些说法。

## 一、建立实验环境

准备 Python 3.8 或以上、浏览器与终端。下载 [HTTP 实验程序](/network-labs/http-lab.py)，保存为 `http-lab.py`。程序只监听 `127.0.0.1`，响应预先定义的资源，不读取你电脑的任意文件。

在文件所在目录运行：

```bash
python3 http-lab.py --port 8765 --revision 1
```

Windows 可用 `py -3` 替代 `python3`。若端口被占用，换为 8767，并在后续命令和 URL 中一起修改。结束时在运行服务的终端按 Ctrl+C。

本实验使用本机 HTTP，便于观察明文。它验证协议行为，不代表校园外网的传播、交换或拥塞，也不是生产网站的部署方式。

## 二、观察一次页面访问的多个请求

打开开发者工具的 Network 面板，先选择保留记录，再访问 `http://127.0.0.1:8765/`。服务主页引用一份 `/style.css`。

交出一张自己的记录表：请求路径、方法、状态、类型、传输大小、是否来自缓存。浏览器可能额外请求 favicon，数量以你实际结果为准。

| 要检验的预测           | 观察动作                 | 判断依据                   |
| ---------------------- | ------------------------ | -------------------------- |
| 页面只发一个请求       | 分别看文档与样式行       | 同一次页面显示涉及不同资源 |
| 200 证明拿到了正确课件 | 点击课件，检查内容与路径 | 状态与具体资源同时核对     |
| 404 代表网络断开       | 点击“无此资源”的链接     | 服务仍返回一个 HTTP 响应   |

<details>
<summary>提示：找不到样式行时</summary>

先确认记录是在导航前开始；取消类型过滤，检查是否命中缓存。不要为了得到预想结论而把未观察到的请求补进报告。

</details>

## 三、让条件请求可重复

浏览器缓存设置会影响结果，先用明确的命令控制条件。macOS/Linux 用 `curl`；PowerShell 使用 `curl.exe`。

```bash
curl -i http://127.0.0.1:8765/lesson.txt
curl -i -H 'If-None-Match: "lesson-v1"' http://127.0.0.1:8765/lesson.txt
curl -i http://127.0.0.1:8765/missing.txt
```

PowerShell 对引号处理可能不同。也可用下面的标准库客户端，避免 shell 转义影响实验：

```python
from http.client import HTTPConnection

for path, headers in [
    ("/lesson.txt", {}),
    ("/lesson.txt", {"If-None-Match": '"lesson-v1"'}),
    ("/missing.txt", {}),
]:
    connection = HTTPConnection("127.0.0.1", 8765, timeout=3)
    connection.request("GET", path, headers=headers)
    response = connection.getresponse()
    print(path, response.status, response.getheader("ETag"), response.read())
    connection.close()
```

先写预测：三次响应是否都有课件正文？服务器声明 `Cache-Control: no-cache`，意味着“不能存储”还是“使用前需验证”？

<details>
<summary>提示：把缓存副本与这次响应正文分开</summary>

第一次下载建立副本；第二次发送版本标识询问能否使用已有副本。304 不需要再传一次相同正文，客户端却仍能显示已有内容。

</details>

<details>
<summary>核对预期行为</summary>

版本 1 服务的三次响应应为 200、304、404。200 返回课件与 ETag，304 返回验证结果且无正文，404 返回“资源不存在”的说明。`no-cache` 要求重新验证，不等于禁止存储；`no-store` 才表达不存储的约束。

命令行第二次没有自动替你展示旧副本；它只显示本次 304 响应。完整缓存客户端会根据验证结果复用已有表示。

</details>

停止服务，以 `--revision 2` 重启，重复带 `"lesson-v1"` 的条件请求。记录新状态、ETag 和正文。这次应该得到新表示，而不是继续使用旧版本。

## 四、对照“响应慢”与“没有服务”

服务的 `/slow` 会故意等待约 0.4 秒后响应。观察 Network Timing，或运行：

```bash
curl -s -o /dev/null -w 'connect=%{time_connect} first=%{time_starttransfer} total=%{time_total}\n' http://127.0.0.1:8765/slow
```

Windows 将输出丢弃路径改为 `NUL`。每个时间是从请求开始累计的时刻，不要直接相加。

再停止服务，访问同一地址，记录浏览器错误或 curl 错误。解释为什么没有监听服务与一个正常返回 404 的服务不同。

<details>
<summary>核对比较</summary>

`/slow` 的等待来自程序人为延迟，不能当作真实链路排队；停止服务后通常表现为本机连接被拒绝，具体错误以环境为准。404 已有 HTTP 响应，而没有服务时未完成这次应用对话。

</details>

## 五、可选：将应用记录与报文对应

安装 Wireshark 并具有本机抓包权限时，选择回环接口。Linux 通常是 `lo`，macOS 通常是 `lo0`，Windows 需要可用的 loopback 捕获接口。显示过滤器用：

```text
tcp.port == 8765
```

重新运行标准库客户端，找到新连接的 SYN、SYN-ACK、ACK，再检查 HTTP 状态。必要时使用“Decode As”将该 TCP 端口解码为 HTTP。

记录源/目标 IP、源/目标端口、一个请求和响应的对应关系。TLS 尚未加入，所以这里能看明文 HTTP；不要由此推断 HTTPS 也能直接读出正文。

本机抓包受接口和卸载方式影响，校验警告或报文划分不一定与物理线上完全相同。不要强求“一条请求恰好一个 TCP 段”。

## 六、独立变化与提交

改变资源路径、服务版本和服务是否运行三项中的一项，先预测再运行；不得一次改变所有条件，否则难以判断原因。

提交你的环境、原预测、实际请求表、条件请求前后记录、一次慢响应与连接失败的对照、以及仍未验证的部分。若没有抓包条件，明确写“未做报文观察”，保留其他实际证据即可。

参考 [HTTP 缓存](/docs/network/25-http-cache-and-cdn/) 解释版本验证，参考 [诊断](/docs/network/31-diagnostics-and-management/) 写出下一步最小检验。
