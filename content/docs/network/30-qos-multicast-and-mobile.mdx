# 第三十节：QoS、组播与移动网络

下载大文件时，语音为什么可能卡住？一百人同时观看同一直播，必须传一百份相同数据吗？走出教学楼从 Wi-Fi 切到蜂窝网络，应用连接为什么有时继续、有时中断？

这些问题把我们带到三个扩展方向：怎样分享资源、怎样向多人分发、怎样在位置变化时维持服务。下面先把核心机制推演清楚，再给出进一步学习的入口。

## 一、吞吐量、延迟、抖动与丢失不是一个指标

文件下载关心完成时间与正确性；语音还关心数据能否在播放期限前到达。平均速率足够，也可能因瞬时排队或到达波动而卡顿。

**QoS（服务质量）**设计需要明确指标、流量条件和保障范围。提高优先级不能创造带宽；把所有流量都标为最高优先级，也就无法区分服务。

| 机制     | 要改变什么                       | 需要承担的代价             |
| -------- | -------------------------------- | -------------------------- |
| 调度     | 有多个待发包时先发谁             | 某些流可能等待更久         |
| 流量整形 | 把过快流量延迟到允许的发送时刻   | 引入等待和缓冲需求         |
| 流量监管 | 对不符合约定的流量丢弃或重新标记 | 可能触发应用重传或降低质量 |
| 准入控制 | 决定能否接纳新的资源请求         | 资源不足时拒绝新需求       |
| 增加容量 | 提高瓶颈可提供的服务量           | 成本及新的下游瓶颈         |

## 二、FIFO 与优先级怎样影响一个语音包

教学链路为 1 Mbit/s，不计首部差异。1500 B 下载包的发送时间是 `1500 × 8 / 1,000,000 = 12 ms`；200 B 语音包是 1.6 ms。

若语音包刚到时，已有五个下载包排在前面，且尚无包开始发送，FIFO 中它需先等约 60 ms，再发送自己的 1.6 ms。如果改成非抢占的优先调度，尚未发送的语音包可先于低优先级队列，但不能打断已经开始发送的一个下载包。

因此在“只有一个低优先级包正在发送、没有其他高优先级积压”的条件下，这份语音包最多仍需等待接近 12 ms，才得到发送机会。不能把“高优先级”写成零延迟。

严格优先级还可能使低优先级流量长期得不到服务。若高优先级需求持续超过链路容量，优先级本身也救不了全部语音请求，需限速、准入或增加容量。

## 三、按权重分享，而不是无限优先

公平排队按流或类别分队列，以某种公平规则调度。**加权公平排队（WFQ）**用权重体现期望份额；真实包调度近似理想流体分享，包大小与实现会影响瞬时结果。

教学模型：链路 8 Mbit/s，甲乙两个队列都持续有数据，权重为 1:3。理想长期份额为甲 2 Mbit/s、乙 6 Mbit/s。若调度是工作守恒的，乙没有数据时，甲可以利用空出来的能力，不需要让链路闲置。

一种理解 WFQ 的办法是给包计算**虚拟完成标签**：从该流的上一标签与到达时的虚拟时间中取较大者，再加上 `包长 / 权重`，优先发送完成标签较小的队头包。它用“按权重需要的虚拟服务量”近似理想分享；虚拟时间不是直接读出的现实毫秒数。

若初始虚拟时间为 0，甲乙各有连续 1000 B 的包同时到达，甲权重 1 的前两包标签为 1000、2000；乙权重 3 的前三包为约 333.3、666.7、1000。因此先选择乙的前两包；甲的第一包与乙第三包同值时由明确的平局规则处理。按字节与权重计算，才能避免把大小不同的包简单按个数轮流发送。

这里讨论的是一个瓶颈处的份额，不能保证甲在互联网全程都有 2 Mbit/s。下一跳可能更慢、策略不同或已经拥塞；端到端承诺需要沿途资源与策略一起成立。

## 四、令牌桶怎样允许有限突发

朴素限速“每秒不得超过 1000 B”若按整秒重置，可能在秒边界形成大突发。令牌桶以连续补充的令牌表达允许的平均速率与突发额度。

本节模型：令牌单位为字节，补充速率 `r = 1000 B/s`，容量 `b = 2000 B`，初始满桶。发送 L 字节需要 L 个令牌；令牌不能超过容量。作为监管器时，令牌不足就丢弃该包且不消耗令牌；作为整形器时，包可以等待足够令牌，但也受缓冲和截止时间约束。

| 到达时刻 | 包长   | 判断前的令牌 | 监管结果与剩余令牌 |
| -------- | ------ | ------------ | ------------------ |
| 0 ms     | 1500 B | 2000 B       | 允许，剩 500 B     |
| 200 ms   | 1000 B | 700 B        | 丢弃，仍有 700 B   |
| 500 ms   | 1000 B | 1000 B       | 允许，剩 0 B       |
| 1000 ms  | 600 B  | 500 B        | 丢弃，仍有 500 B   |

长期平均受补充速率约束，初始桶和积累令牌允许有限突发。在给定模型中，持续时间 t 内允许发送量受 `b + r × t` 这类上界约束，单位必须一致；它不意味着每个极短时间窗都只能按 r 发送。

如果 200 ms 的 1000 B 包改为排队整形，它最早到 500 ms 才有足够令牌；届时到来的下一包还要继续等待。整形改变了发送时间，不能沿用监管丢弃后的令牌表计算后续事件。

## 五、DiffServ 与 ECN 各传什么信息

DiffServ 用 DSCP 等分类信息选择相应的逐跳处理，并在边界分类、监管或重新标记。6 位 DSCP 不等于一个全球统一的“购买了多少带宽”字段；不同管理域可以有不同的策略和信任条件。[区分服务体系](https://www.rfc-editor.org/rfc/rfc2475.html)

若所有终端都能未经检查地给自己的下载标为最高等级，分类策略就会失效。因此网络边界通常需要明确哪些标记可被信任，以及如何处理不符合约定的流量。

**ECN**用拥塞标记代替某些丢包信号：支持该机制的网络节点可对合适的包标记拥塞，接收端反馈，发送端依相应传输协议的规则响应。它不会自动消除队列，也不是普通客户端“看到一个标记就由路由器替它降速”。[ECN 基础](https://www.rfc-editor.org/rfc/rfc3168.html)

QoS 调度改变资源分配；拥塞控制改变发送者给网络的负载；二者可以配合。IntServ/RSVP 等资源预留思路进一步涉及路径状态与准入，规模和部署约束需要另行分析，不能与 DSCP 标记混成一种机制。

## 六、同一份直播为什么可以在分叉处复制

**单播**面向一个目的接收位置；**广播**面向特定广播范围；**组播**面向一个接收组。广播不是“发给全互联网”，组播也不是“服务器列出所有收件 IP 后逐个复制”。

教学例：100 个接收者同时观看同一份 8 Mbit/s 直播，不计协议开销。源站逐个单播时总上行需求为 800 Mbit/s。若路径支持相应 IP 组播树，源站可发一个流，由树的分叉节点向各分支复制；共享一条树边的接收者可以复用这条边上的一份流。

这并不保证所有链路只需 8 Mbit/s：分支上的复制总量、其他业务、丢失与服务机制仍需核算。如果用户观看的是不同时间位置的点播，内容已不完全相同，就不能直接套用这个组播节省模型。

| 工作                     | IPv4 中的典型机制            | 不负责什么                   |
| ------------------------ | ---------------------------- | ---------------------------- |
| 主机表达对组的兴趣       | IGMP 与本地路由器交互        | 不独自构造整个互联网的分发树 |
| 路由器之间建立转发状态   | PIM 等组播路由机制           | 不自动提供可靠或加密内容     |
| 二层交换机避免无差别复制 | IGMP snooping 等观察成员信息 | 不等于路由器的跨网组播协议   |

IPv4 组播地址属于 `224.0.0.0/4`，但不同子范围有不同作用域与分配规则；不能任意拿一个地址就在生产网络广播内容。成员管理表示接收兴趣，不自动等同应用授权。[IGMPv3](https://www.rfc-editor.org/rfc/rfc3376.html)、[PIM-SM](https://www.rfc-editor.org/rfc/rfc7761.html)

IPv6 没有 IPv4 那样的广播地址，使用具有作用域的组播等机制。`ff02::1` 是链路范围所有节点组，`ff02::2` 是链路范围路由器组；成员发现使用 MLD 等机制，不能直接套用 ARP 或 IGMP 的名字。[IPv6 基础](https://www.rfc-editor.org/rfc/rfc8200.html)、[MLDv2](https://www.rfc-editor.org/rfc/rfc3810.html)

组播是否在校园或跨运营商网络可用，需要实际部署支持。公网视频常采用 CDN 和应用层分发；不能看到“直播”就断言使用了 IP 组播。

## 七、移动网络把接入位置与服务状态分开

Wi-Fi 与蜂窝都使用无线链路，但接入、资源分配、认证和移动性管理方式不同。Wi-Fi 常见竞争接入，现代系统也有调度与多用户机制；蜂窝网络通常由基站协调分配无线资源，不能简单背成“无线全靠碰撞重发”。

5G 的简化结构包括终端、无线接入网络和核心网。AMF 承担接入与移动性管理等控制工作，SMF 管理会话，UPF 承担用户流量转发等功能。用户数据不因为存在控制功能，就都必须经过控制功能处理。[5G 系统架构](https://www.etsi.org/deliver/etsi_ts/123500_123599/123501/18.10.00_60/ts_123501v181000p.pdf)

移动设备从基站甲移向乙时，系统需要发现新的无线条件、准备资源、转移接入并调整用户路径。某些会话连续性安排能够保持相应地址与会话，另一些条件下会改变；不能保证任何制式、任何切换都绝不丢包。

| 阶段             | 简化教学切换中的问题               |
| ---------------- | ---------------------------------- |
| 测量与选择       | 新接入是否有足够信号和资源？       |
| 准备与认证上下文 | 目标侧如何接受该设备及会话？       |
| 切换接入         | 在途数据暂存、丢失或重复如何处理？ |
| 更新路径         | 数据应继续发到哪个接入位置？       |
| 应用恢复         | 是否需要重传、重新连接或状态同步？ |

教学计算：媒体流为 8 Mbit/s，切换暂停交付 40 ms，按同一速率生成的数据约为 `8,000,000 × 0.040 / 8 = 40,000 B`。适当缓冲可能吸收短暂暂停，但会消耗延迟预算，也不保证补发后的链路有足够额外容量追上进度。

从 Wi-Fi 换成蜂窝还可能改变 IP 地址或 NAT 状态，普通 TCP 连接可能中断。QUIC 的连接标识与经过验证的路径迁移等机制可以在合适条件下帮助持续通信，但应用与实现仍必须支持；一个“5G”图标不是连接连续性的证明。

## 八、运行令牌桶模型，观察策略差异

下面程序是本节监管器的**离线策略实验**，不配置操作系统限速。补充速率取 1 B/ms，因此所有计算均为整数。

```python
capacity = 2000
tokens = capacity
last_ms = 0
events = [(0, 1500), (200, 1000), (500, 1000), (1000, 600)]

for now_ms, size in events:
    tokens = min(capacity, tokens + (now_ms - last_ms))
    last_ms = now_ms
    allowed = tokens >= size
    if allowed:
        tokens -= size
    print(now_ms, size, "allow" if allowed else "drop", tokens)
```

先手算，再运行核对。将容量改为 3000 B，保持速率不变；预测哪几个决定发生变化，并说明为什么“突发额度增加”不是“长期补充速率提高”。另做一份整形时序，把被延迟包的实际发送时刻列出。

## 九、独立迁移：无法靠一个优先级解决的问题

学校教学直播与批量备份共用一条出口。直播要求低延迟，备份允许晚一些完成。请设计分类、突发约束、调度和拥塞反馈；再解释直播需求超过出口总能力时应改变什么。

## 十、进一步深入的知识地图

本课程已经建立本科网络核心机制与这些扩展方向的基础。网络领域仍在发展，下面的分支需要围绕实际问题、实现与规范继续深入，不能把见过名称等同掌握。

| 方向           | 接下来具体研究什么                                            | 已有基础如何用上                   |
| -------------- | ------------------------------------------------------------- | ---------------------------------- |
| 低功耗与物联网 | 休眠、受限内存、低功耗链路、CoAP、RPL，或经消息代理的发布订阅 | 包开销、重传、路由与端到端身份     |
| 可编程与云网络 | 控制器一致性、EVPN、隧道端点、服务网格及隔离验证              | match—action、路由、TLS 与故障推演 |
| 广域流量工程   | MPLS、Segment Routing、路径约束、保护切换                     | FEC、容量、QoS 与路由控制          |
| 蜂窝与边缘系统 | 无线调度、切换、会话连续性、核心网与边缘应用协同              | 分层、控制/数据平面与延迟预算      |
| 大规模媒体     | 编码、实时反馈、拥塞公平、自适应码率与内容分发                | 速率、抖动、缓存和传输协议         |
| 高速与新型网络 | 光网络、卫星路径、专用互连及不同故障特征                      | 传播/发送时延、误码与带宽时延积    |

物联网的一个具体取舍：20 B 测量值若每次伴随 300 B 总开销，有效数据仅占 6.25%；批量发送可降低开销，却增加等待和丢失一批数据的影响。CoAP 的受限设备请求/响应设计与 RPL 的低功耗有损网络路由，分别处理应用交换和路径组织，不能用“都很轻量”代替机制分析。[CoAP](https://www.rfc-editor.org/rfc/rfc7252.html)、[RPL](https://www.rfc-editor.org/rfc/rfc6550.html)

选择一个方向，提出可测量的问题与失败情境，再列出需要的数据和验证方法。能够把基础机制迁移到新网络，才是继续学习这些分支的起点。
