# 第二十四节：DNS——名字怎样找到服务

更换服务器后，服务的地址变了，为什么学生收藏的名字还可以继续使用？名字与网络位置分开，使应用可以移动；但全世界的名字也无法只靠一张手工维护的地址表。

本节把 DNS 看成一个**按名字层次划分责任、通过查询取得记录的分布式数据库**。获得地址以后，连接、路由、TLS 和 HTTP 仍各自需要完成工作。

## 一、从一张地址表到分布式委派

朴素办法是每台电脑存一份“名字 → IP”文件。小型实验中它能工作，规模变大后就出现三个问题：谁负责修改、如何同步所有副本、单台维护服务器出故障怎么办？

DNS 使用有层次的名字。例如 `notes.study.example.` 从右向左属于根、`example`、`study` 等层次；末尾的点表示完整名字到达根。这里的 `.example` 是教学名字，不是学校真实域名。

**域**是名字树的一部分，**区域（zone）**是某组权威服务器实际负责的数据范围。一个域可以把子域委派出去，因此“域名后缀相同”不意味着全部记录由同一台服务器保存。

| 角色               | 持有什么或做什么             | 不应误解成什么                 |
| ------------------ | ---------------------------- | ------------------------------ |
| 本机存根解析器     | 代表应用发起查询             | 不一定自己遍历根服务器         |
| 递归解析器         | 帮客户端取得最终结果，并缓存 | 不拥有全世界所有域名的权威数据 |
| 根服务器           | 提供顶级域的委派信息         | 不保存每个网站的 IP            |
| 顶级域权威服务器   | 提供下一级区域的委派         | 不负责把网页传回浏览器         |
| 某区域的权威服务器 | 对自己的区域提供权威记录     | 不一定接受陌生客户端的递归请求 |

同一个服务可以有多个权威服务器；它们提供冗余。客户端配置的解析器可能来自校园网络、运营商，或浏览器的加密 DNS 设置，不能仅凭“浏览器访问了网站”断言用了哪一个。

## 二、递归与迭代是两种查询关系

**递归请求**表达“请给我最后的答案或失败结果”；**迭代查询**允许服务器回答“我不知道最终值，但下一步可以问谁”。常见情况是电脑向递归解析器提问，解析器再通过迭代查询走完委派链。

上述流程是**空缓存下的简化模型**。如果已有可用的父区域委派或目标记录，解析器不必每次从根开始。委派响应中的 NS 记录说明该问哪些名字服务器；必要的 glue 地址帮助解析器到达它们，但不能把所有附加记录都当成同等可信的最终答案。

DNS 常用 UDP 53，也使用 TCP 53；响应截断等情况可能促使客户端改用 TCP。不能背成“DNS 永远用 UDP”。传输成功也不证明回答正确，仍须检查名字、类型、状态及验证策略。

## 三、同一个名字可以有不同类型的答案

DNS 的查询单位包含名字和类型。查不到 A 记录，并不一定表示这个名字不存在：它可能只有 AAAA 或其他记录。

| 类型  | 内容                         | 用途或注意点                                                    |
| ----- | ---------------------------- | --------------------------------------------------------------- |
| A     | IPv4 地址                    | 为 IPv4 连接提供候选位置                                        |
| AAAA  | IPv6 地址                    | 为 IPv6 连接提供候选位置                                        |
| CNAME | 另一个规范名字               | 还须继续解析目标名字；常规 CNAME 所在名字不能同时随意放其他数据 |
| NS    | 区域的名字服务器             | 表达权威服务或委派关系                                          |
| MX    | 邮件交换服务器及优先级       | 值是主机名，需要进一步取得地址；较小优先级值优先                |
| PTR   | 地址对应的名字               | 用于反向查询，不保证与正向记录互为唯一对应                      |
| TXT   | 文本数据                     | 常承载验证和邮件策略信息，并非网页正文                          |
| SOA   | 区域管理参数                 | 包括区域版本等信息，也参与负缓存时间的确定                      |
| SRV   | 某服务的目标、端口及选择参数 | 应用必须支持它，不能假定浏览器对所有 URL 都查 SRV               |

一个名字可返回多个地址。客户端如何选择、是否尝试 IPv6、何时改用另一个地址，由客户端算法与网络条件共同决定；DNS 回答的第一行不一定是实际连接地址。

**NXDOMAIN**表示名字不存在；**NOERROR 且缺少所问类型的答案**可能是名字存在但该类型无数据；**SERVFAIL**表示解析未能完成，例如上游失败或验证失败。三者支持的诊断结论不同。

## 四、TTL 解决效率，也带来更新延迟

记录的 TTL 是允许缓存使用的时间上限，通常以秒计。缓存命中可减少查询数量和等待时间，但权威服务器更新记录不会把所有已有缓存瞬间清空。

以下是**教学构造**：解析器在 `t = 0 s` 收到 `notes.study.example A 192.0.2.10`，TTL 为 120 s；在 `t = 40 s`，权威服务器把它改成 `192.0.2.20`。忽略其他缓存、预取和特殊过期服务策略。

| 查询时刻 | 解析器可以怎样回答        | 剩余 TTL 或原因              |
| -------- | ------------------------- | ---------------------------- |
| 30 s     | 缓存中的 192.0.2.10       | 90 s                         |
| 80 s     | 缓存中的 192.0.2.10       | 40 s；尚不需要知道权威已更新 |
| 121 s    | 重新查询后得到 192.0.2.20 | 新结果按其新 TTL 开始计时    |

因此“我已经在服务器改了地址，你的查询还是旧的”不自动证明解析器坏了。计划迁移时，提前降低 TTL 才能让之后取得记录的缓存更早过期；在迁移一刻降低 TTL，不能追回先前按旧 TTL 缓存的记录。

**负缓存**也会缓存“名字不存在”或“某类型无数据”的结果。其时间受权威响应中的 SOA 参数等约束，不是永远保存失败。若在刚收到否定回答后创建了名字，其他客户端仍可能暂时取得缓存的否定结果。[负缓存规范](https://www.rfc-editor.org/rfc/rfc2308.html)说明了这类回答的处理。

## 五、DNSSEC 与加密 DNS 保护不同环节

DNSSEC 用签名及信任链帮助验证记录的来源和完整性，包含对不存在情况的认证；它**不隐藏查询名字**。验证需要可信锚点和正确的验证过程，单看响应里有签名记录不能宣称已验证成功。[DNSSEC 的能力与边界](https://www.rfc-editor.org/rfc/rfc4033.html)

DNS over HTTPS（DoH）把 DNS 消息放在 HTTPS 中传送，保护客户端到该解析器这一段通道；解析器仍能知道查询内容。DoH 不等于网站本身的 HTTPS，也不自动使所有权威数据带上 DNSSEC 签名。[DoH 规范](https://www.rfc-editor.org/rfc/rfc8484.html)

可以把它们分成两个检查：**回答是否能被验证**，以及**查询途中谁能读到内容**。它们可以结合使用。无论哪一种，都不能保证得到的服务一定诚实、应用一定没有漏洞。

## 六、观察一次真正的解析

在自己的电脑上查询公开示例域名，记录实际输出，不要把课堂示例地址复制成“实测”。macOS/Linux 若已有 `dig` 可运行：

```bash
dig example.org A
dig example.org AAAA
dig example.org MX
dig example.org A +tcp
```

Windows 可使用已有的工具：

```powershell
nslookup -type=A example.org
nslookup -type=AAAA example.org
```

分别记录查询类型、回答状态、答案记录、TTL、查询到的解析器和查询时间。连续两次查询时，TTL 或耗时可能变化，也可能因负载均衡、缓存刷新或不同上游而不同；**耗时较短本身不能证明缓存命中**。

若 `dig` 可用，可补做 `dig example.org A +trace`。它会尝试显示迭代过程；校园网络可能限制向外部 DNS 的直接查询，失败结果应如实保留，而不能改写为成功。浏览器也可能使用独立解析器，所以命令行查询成功不充分证明浏览器使用了同一个结果。

交出一张“实际输出字段 → 能支持的结论 → 尚不能确定的事情”表。若工具不可用，完成上一节的时序推演，并明确注明没有取得真实输出。

## 七、独立推演与迁移

一个教学解析器在 `t = 10 s` 缓存 `image.study.example CNAME edge.study.example`，TTL 60 s；同时缓存 `edge.study.example A 192.0.2.30`，TTL 20 s。假定无其他缓存、两条记录独立过期。

请解释 `t = 25 s` 与 `t = 35 s` 的查询分别需要哪些新查询。不要先展开答案。

<details>
<summary>第一层提示：把每条记录的过期时刻单独列出</summary>

CNAME 的过期时刻是取得时刻加 60；A 的过期时刻是取得时刻加 20。不能用较长的 TTL 替另一条记录延寿。

</details>

<details>
<summary>第二层提示：名字别名与目标地址是两步</summary>

只要 CNAME 仍可用，就还知道应解析哪个名字；但如果 A 已过期，仍须取得该名字的新地址记录。

</details>

<details>
<summary>核对完整推演</summary>

CNAME 到 70 s 过期，A 到 30 s 过期。25 s 时两者都有效，可使用缓存。35 s 时别名关系仍有效，目标地址需要重新查询；不必因为地址过期就从头遗忘整个委派树。

</details>

最后换一个情境独立回答：刚创建一个名字，有人持续看到 NXDOMAIN，有人已能访问；还可能存在哪些不同缓存位置？应收集哪些查询状态、TTL 和解析器信息？如果 DNS 已返回地址而连接超时，下一步为什么不应继续只改 DNS？

完成标志是能区分**名字不存在、类型无数据、解析失败、连接失败和 HTTP 错误**，并用观察支持自己的判断。DNS 的名字层次与委派基础可查阅[DNS 概念规范](https://www.rfc-editor.org/rfc/rfc1034.html)。
