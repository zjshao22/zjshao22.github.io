# 第十节：怎样找到一帧，怎样发现误码

接收端恢复了一串比特，但应用想得到的是一份完整消息。直接每 1000 B 切一次可以吗？如果第一帧长度不是 1000 B，或者某个字节丢失，后面的切分就都错位。链路层需要同时回答两个问题：**边界在哪里，以及这一帧是否受损？**

## 一、定界：边界必须和内容区分

一种办法是在首部写长度。接收端先读长度，再取指定数量的数据。它紧凑、易解析，但若长度字段本身受损，就可能误取后面的内容；设计还要考虑长度合法性、重新同步与完整性检查。

另一种办法用特殊标志定界。假设教学协议用字节 `7E` 表示边界，内容正好含有 `7E` 时，接收端会把内容误认为结束。禁止应用使用这个字节并不合理，协议应能传任意内容，这叫**透明传输**。

**字节转义**规定：内容里的 `7E` 改成 `7D 5E`；内容里的转义字节 `7D` 改成 `7D 5D`。这是 PPP 类字节填充的核心形式，即被转义字节与 `20` 做异或；实际 PPP 还可能转义额外控制字符。边界标志本身不转义。[RFC 1662](https://www.rfc-editor.org/rfc/rfc1662.html)规定了相关定界与透明性规则。

教学负载 `41 7E 7D 42` 的定界表示为：

| 部分      | 传送的字节 |
| --------- | ---------- |
| 开始标志  | 7E         |
| 原内容 41 | 41         |
| 原内容 7E | 7D 5E      |
| 原内容 7D | 7D 5D      |
| 原内容 42 | 42         |
| 结束标志  | 7E         |

这个小例子只演示定界和转义，**省略了 PPP 其他首部与 FCS**，不能当作一帧完整的实际 PPP 报文。

## 二、位填充解决同样的问题

位定界协议可以用 `01111110` 作标志。在两个标志之间的数据区，发送端遇到连续五个 1，就插入一个 0；接收端按规则删去这个 0。因此内容不能直接伪装成标志中的六个连续 1。

例如内容 `01111110` 经位填充变成 `011111010`。新增的 0 在第五个 1 后面；恢复内容时才删除它。位填充是对比特序列进行处理，字节转义是对字节进行处理，不能把两种规则同时套到同一个教学题里。

长度、标志和物理层定界是不同设计选择。以太网并不使用本页这套 `7D` 字节转义；其物理层和帧结构另有同步与边界机制。

## 三、检测：增加冗余才能识别受损

假设收到 `1011`。它可能就是发送的 `1011`，也可能来自发送的 `1001` 加一次翻转。没有冗余，接收方无法仅凭结果区分两者。

**奇偶校验**加一位，使整个码字中 1 的数量满足约定。例如偶校验为数据 `1011` 添加 `1`，使总共有四个 1。单个比特翻转会改变奇偶性，因而可检测；两个比特同时翻转可能保持奇偶性，因而漏检。

二维奇偶校验对行与列都加校验，能用错误的行列交点定位某些单比特错误。但更多错误可能形成相互抵消的模式。增加校验位提高能力，需要说明能保证检测或纠正哪类错误，不能只说“加了校验所以数据一定正确”。

## 四、CRC 是二进制多项式除法

CRC 把比特串看成系数为 0 或 1 的多项式。计算在模 2 下进行，加减都是 XOR，**没有进位和借位**。双方约定生成多项式 G；设它的次数为 r，发送端先给数据补 r 个 0，再除以 G，取 r 位余数替换补上的 0。

本节采用刻意很小的**教学 CRC**：数据 `1101`，生成式 `1011`，r = 3。生成式代表 x³ + x + 1。实际以太网 CRC 使用更长生成式，并有比特次序、初始值与结果处理等约定；不能把本例当成以太网 FCS 算法。

补零得到 `1101000`。每一步让除数最高位与当前余式最高位对齐：

| 步骤 | 当前值  | 对齐的 1011 | XOR 后  |
| ---- | ------- | ----------- | ------- |
| 1    | 1101000 | 1011000     | 0110000 |
| 2    | 0110000 | 0101100     | 0011100 |
| 3    | 0011100 | 0010110     | 0001010 |
| 4    | 0001010 | 0001011     | 0000001 |

余数为 `001`，发送码字为 **1101001**。接收端用同一生成式除码字；无错时余数为 000。余数非零说明检测到错误；余数为零只能说明**没有检测到错误**。

为什么会漏检？若翻转模式本身正好是生成式的倍数，其余数也是零，原码字加上这个错误模式仍能整除。CRC 的检测能力取决于生成式与错误模式；r 位 CRC 对长度不超过 r 的非零突发错误有保证，对任意长度任意模式不提供绝对保证。

## 五、校验和与 CRC 的差别

互联网校验和把数据按 16 bit 分组，做反码加法，再对结果取反。超出最高位的进位加回低位；奇数字节长度需按规则补零参与计算。接收端检查含校验和的反码和。[RFC 1071](https://www.rfc-editor.org/rfc/rfc1071.html)说明了计算方法。

例如 `0001` 与 `FFFE` 的反码和为 `FFFF`，所以校验和为 `0000`。若一字变大、另一字恰好等量变小，校验可能仍然成立。校验和常易于软件计算，但检测性质与 CRC 不同。

IPv4 首部校验和只保护 IPv4 首部；TCP/UDP 校验和还包含伪首部信息与传输数据。IPv6 基本首部不含 IPv4 那样的首部校验和。**哪部分数据被覆盖**与“采用哪种算法”一样重要。

CRC 与普通校验和都不能证明报文来自可信对方；攻击者可能重新计算它们。安全课程中的 MAC（消息认证码）与这里的 MAC（介质访问控制）同名缩写，却是不同概念。

## 六、检测到错误后怎么办

一种方式是丢弃受损数据，由链路层或端到端协议请求重传。另一种方式是增加足够冗余，接收方直接纠错。重传需要反馈和时间，纠错需要额外比特与运算；无线、卫星和实时应用可能作不同选择。

码字之间不同的比特数叫**汉明距离**。最小距离为 d 的码，能保证检测最多 d−1 位错误，或保证纠正最多 floor((d−1)/2) 位错误；这两个保证描述不同的使用方式，不能随意相加。

以偶校验 Hamming(7,4) 为例，位置 1、2、4 放校验位，3、5、6、7 放数据。数据 `1011` 对应位置 3=1、5=0、6=1、7=1：

| 校验位 | 检查的位置 | 算出的校验位 |
| ------ | ---------- | ------------ |
| p1     | 1、3、5、7 | 0            |
| p2     | 2、3、6、7 | 1            |
| p4     | 4、5、6、7 | 0            |

发送码字为 `0110011`。若第 6 位翻转，收到 `0110001`。检查得到 s1=0、s2=1、s4=1，按 s4 s2 s1 得 `110`，即 6；在“至多一位出错”的前提下翻转第 6 位可恢复。

普通 Hamming(7,4) 最小距离为 3。它的单错纠正解码器可能把双错误判成单错而进一步改坏数据；增加总奇偶位形成扩展码，可实现常见的单错纠正、双错检测。任何结论都带有错误数量前提。

## 七、动手：先预测，再用短程序核对 CRC

把以下代码保存为 `crc_demo.py`，用已安装的 Python 3 执行。它只实现本页教学除法，不是对网卡做实验。

```python
def remainder(value, generator):
    while value.bit_length() >= generator.bit_length():
        shift = value.bit_length() - generator.bit_length()
        value ^= generator << shift
    return value

generator = int("1011", 2)
data = int("1101", 2)
r = generator.bit_length() - 1
check = remainder(data << r, generator)
codeword = (data << r) | check
print(format(check, "03b"))
print(format(codeword, "07b"), remainder(codeword, generator))
for position in range(7):
    damaged = codeword ^ (1 << position)
    print(position, remainder(damaged, generator))
```

运行前预测余数、码字和逐位翻转是否检出。交出预测表与实际运行结果，再把生成式从 `1011` 改成 `1101`，重新计算。若没有 Python，可以按上一节表格手工除法，标明是推演。

### 把“检测到”与“能修好”分开

现在接收端只知道 CRC 余数非零。它没有获得“原码字一定是哪一条”的充分信息，不能直接把 CRC 余数当成应翻转的位置。Hamming 单错解码的综合征可以在指定错误模型下定位；CRC 检测结果与这个定位信息不是同一种对象。
